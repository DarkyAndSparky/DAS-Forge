Запуск эталонного приложения

npm install
npm install-scripts approve argon2 cpu-features ssh2   # один раз, из корня
cd examples/workshop
npm run cli -- config check
npm run cli -- user create-admin      # пароль (24 символа) показывается один раз
npm start                             # https://127.0.0.1:9002 (http://127.0.0.1:9001 перенаправляет на него), сертификат самоподписанный

Вход под созданным администратором; при первом входе система потребует сменить пароль. Раздел «Администрирование» — /admin.

Команды при работающем сервере. Окно с npm start занято сервером, в него команды не вводятся. Откройте второе окно консоли, перейдите в examples/workshop и запускайте npm run cli -- <команда> (например, npm run cli -- help). Подробнее — в главе «Командная строка».

Тесты: npm test из корня (ядро и workshop), только ядро — npm run test:core.

Минимальное приложение

import { config, database, auth, http, scheduler } from '@das-forge/core';

const appConfig = await config.loadConfig();             // app.config.js + DAS_* переменные
const db = await database.createSqliteAdapter(appConfig.database);

Порядок сборки в examples/workshop/src/context.js (единая точка для сервера и CLI): конфигурация → база и миграции → брендинг → авторизация → планировщик с копиями. Затем src/server.js: requestId() → securityHeaders() → сессии → маршруты → notFoundHandler() и errorPageHandler() последними → registerGracefulShutdown().

Модули ядра

Справочник по модулям @das-forge/core: для чего модуль, что даёт по умолчанию, как подключить и на что обратить внимание. Подробности по темам вынесены в отдельные руководства: Конфигурация, Безопасность, Администрирование, Переводы, Темы и оформление, CLI.

Пакет подключается целиком (import { auth, http } from '@das-forge/core') или по модулям (@das-forge/core/auth). Тяжёлые и нативные зависимости (argon2, sharp, jsdom, dompurify, qrcode, selfsigned, ssh2, ldapts, libheif-js, docx, i18next) подгружаются лениво, при первом использовании функции, а не при импорте.

config

Назначение. Единая проверенная конфигурация приложения. Данные валидирует Zod; интерфейсы (адаптер БД, провайдер аутентификации) проверяются отдельными assert…-функциями, а не схемами.

API.

ФункцияЧто делает
loadConfig({ cwd })читает файл конфигурации, накладывает значения по умолчанию и переменные окружения, проверяет; при ошибке бросает ConfigValidationError со списком полей
validateConfig(plain)синхронная проверка готового объекта (CLI config check, тесты)
applyEnvOverrides(obj)переопределения из DAS_* и других переменных (например, DAS_BACKUP_KEY → backup.encryptionKey)

Пример (workshop). examples/workshop/src/context.js: const appConfig = await config.loadConfig({ cwd: REPO_ROOT }).

Внимание. Полный список ключей и значений по умолчанию — в Конфигурации. Схема строгая: неизвестный ключ — ошибка. Заглушки секретов (KNOWN_PLACEHOLDER_SECRETS) не допускаются в production.

database

Назначение. Адаптер к node:sqlite (WAL) и помощники поверх него. adapter.snapshotTo(файл) — согласованная копия (VACUUM INTO); adapter.snapshotToAsync(файл, { check }) делает то же и integrity_check копии в рабочем потоке, не останавливая обработку запросов (только файловая база; в памяти — обычная копия). Плановое резервное копирование использует асинхронный вариант. Страницы: adapter.pageByExample(table, example, { pageSize, cursor, orderBy, direction, withTotal }) возвращает { rows, nextCursor, total? } — постраничный просмотр «после этой строки» по одному уникальному индексированному столбцу (по умолчанию id), устойчивый к добавлению и удалению строк; nextCursor (непрозрачная строка, годится для URL) передаётся как cursor, null — последняя страница. Для небольших списков остаётся queryByExample({ limit, offset }).

Адаптер. database.createSqliteAdapter({ file, walMode, normalizeValues }) возвращает объект с get, all, run, exec, transaction, queryByExample и закрытием. assertDatabaseAdapter(obj) проверяет, что объект соответствует интерфейсу.

ПомощникЧто делает
upsert(db, table, row, { conflictColumns, updateColumns })INSERT … ON CONFLICT DO UPDATE
addColumnIfMissing, addUpdatedAtTrigger, rebuildTableбезопасные миграции (идемпотентно; rebuildTable — 12 шагов SQLite)
addSoftDelete, softDelete, restoreDeleted, purgeDeletedмягкое удаление через deleted_at
queryByExample, countByExample, likeEscapeпараметризованные запросы по образцу; `deleted: 'exclude''only''include'`
createFtsIndex, ftsEscape, foldYoполнотекстовый поиск FTS5 с русской свёрткой (ё=е)
assertSafeIdentifier, normalizeLimitзащита идентификаторов и LIMIT

Внимание. Имена таблиц и столбцов проверяются (assertSafeIdentifier): передавайте их из кода, не из пользовательского ввода. Пустой образец в softDelete запрещён (скрыл бы всю таблицу). Значения всегда передаются параметрами.

Пример (workshop). examples/workshop/src/context.js создаёт адаптер; миграции — cli.runMigrations из каталога migrations (bin/app.js).

auth

Назначение. Пароли, сессии, вторые факторы, управление учётными записями.

Пароли. hashPassword (argon2id), verifyPassword (любая поддерживаемая схема, в том числе старые: pbkdf2Scheme, scryptScheme, scryptSaltColumnScheme для приложений, где соль лежит в отдельном столбце), checkPasswordPolicy, generateTempPassword (24 символа). configurePasswordConcurrency ограничивает число одновременных проверок; при перегрузке — PasswordBusyError (отвечайте 503).

Провайдер. createAuthProvider({ db, argon2Options, legacySchemes… }) объединяет проверку пароля, ленивую миграцию старого хеша при входе и создание сессий; assertAuthProvider проверяет интерфейс. Пример: examples/workshop/src/context.js.

Сессии. createSessionStore (SQLite, хеш идентификатора), destroyUserSessions, purgeExpiredSessions, hashSessionId. Подробнее — Безопасность.

Вторые факторы. TOTP: startTotpEnrollment, verifyTotpEnrollment, generateTotp/verifyTotp/matchTotpStep (шаг запоминайте, чтобы не принять код дважды), buildTotpUri; recovery-коды: generateRecoveryCodes, verifyAndConsumeRecoveryCode, countRemainingRecoveryCodes; listAuthenticators, removeAuthenticator (последний фактор нельзя удалить, если политика требует MFA). Секреты TOTP шифруются: sealSecret/openSecret, sealExistingTotpSecrets приводит все секреты к текущему ключу.

Сброс пароля по ссылке. createPasswordResetToken, peekPasswordResetToken (проверить, не сжигая), consumePasswordResetToken (одноразово), purgePasswordResetTokens (вызывайте из планировщика).

Управление пользователями. listUsers, getManagedUser, createManagedUser, renameUser, setUserEmail, changeUserRole, setUserDisabled, resetUserPassword, removeUser (mode: 'anonymize' по умолчанию или 'delete'), countActiveAdmins. Все операции отзывают сессии затронутого пользователя и не допускают потерять последнего активного администратора.

Парольная политика. createPasswordPolicy({ db, config, appName, blocklistFile }) даёт правила, которые администратор меняет в админке: get, set, reset, check (длина, классы символов, логин, часть e-mail, название приложения, список типовых) и checkFull (плюс запрет повторов по хешам прошлых паролей и список утёкших паролей из файла createPasswordBlocklist), isExpired (срок действия). Профили в PASSWORD_PROFILES (nist, fstec). Низкоуровневые checkPasswordPolicy, characterClasses; история хешей recordPassword, recentPasswordHashes, passwordExpired; массовая смена requirePasswordChangeForAll (в user-admin). Правила и коды ответа — в безопасности.

Известные устройства. recognizeDevice, describeAgent (auth/devices.js): браузер узнаётся по cookie das_device, в таблице login_devices только хеш; на этом построено письмо о входе с нового устройства.

Первый запуск. firstRunBootstrap(db, { argon2Options }) создаёт администратора с временным паролем, если пользователей нет; writeBootstrapCredentials(file, result) записывает данные в файл с правами только для владельца (не перезаписывает существующий).

Внимание.

  • Хеширование пароля выполняет AuthProvider приложения: createManagedUser принимает уже готовый passwordHash.
  • Сессия хранит снимок пользователя. Смена роли или имени без отзыва сессий оставит старые права: используйте функции выше или attachUser({ revalidate }).
  • Отдельный ключ auth.totpEncryptionKey обязателен для безопасной ротации sessionSecret.

http

Назначение. Всё, что нужно Express-приложению вокруг маршрутов.

ГруппаФункции
СерверapplyServerSettings, createHttpServer, listenServer, loadOrCreateTls, defaultCertDir, secureCookiePolicy
ЗапросrequestId, securityHeaders, createCompression, createCors, csrfProtection, createRateLimiter, createFailureTracker, clientKey
СессииcreateSessionMiddleware, attachUser, establishSession, endSession, requireAuth, requirePermission, deriveCookieSecret
Данныеserialize, findUnmappedFields, validateBody, validateQuery
ОтветыsendError, ERROR_CATALOG, errorText, resolveLocale, renderErrorPage, notFoundHandler, errorPageHandler, errorResponder
Жизненный циклregisterGracefulShutdown, registerFatalHandlers

Страницы статусов. Каталог ERROR_CATALOG содержит тексты для всех кодов 4xx и 5xx из списка MDN (ru/en), плюс общие записи 4xx/5xx и запись maintenance; тексты переопределяются через i18n.setTextOverrides({ errors: … }). Каждая страница показывает блок бренда приложения (brand — функция (req) => html, обычно () => branding.brandBlockHtml(db, vendorIdentity)) и маленькую строку «Powered by DAS-Forge» с логотипом ядра.

Формат ошибки. Ошибки валидации и отказы — { error: 'КОД', fields: ['имя поля'], message? }; браузер получает брендированную страницу, API — JSON (errorResponder решает по заголовку Accept). Коды ошибок стабильны, тексты берутся из каталога по языку запроса.

Порядок подключения (как в examples/workshop/src/server.js): requestId → ui.localeMiddleware → errorResponder → securityHeaders → сжатие → тела запросов → cookie-parser → csrfProtection → сессии → attachUser → баны → маршруты → страницы 404 и 500 последними.

Внимание.

  • requireAuth отвечает 401, requirePermission — 403; оба пишут ответ в формате ошибок.
  • Для serialize поле без объявленного права закрыто по умолчанию.
  • Режим reverse-proxy без server.trustProxy отвергается при запуске.
  • Лимиты запросов живут в памяти процесса.

policy

policy.createPolicy({ db, appName, theme, dependencySources, basePath = '/policy', secureCookie, platformCopyright = 'DAS-Forge contributors' }) — публичные страницы /policy (политика использования), /policy/cookies, /policy/components (перечень компонентов и лицензий по dependencySources), баннер cookie с согласием (POST /consent) и раздел админки. Тексты по умолчанию — DEFAULT_TEXTS, редактируются администратором и хранятся в policy_texts (языки ru и en; в админке язык текстов переключается вкладками, а не дублирует поля; есть текст лицензионного соглашения license — заготовка для владельца). Методы: mount(app), getText, setText, resetText, consentOf, bannerHtml, pageEnd. pageEnd(req, res, locale) — разметка конца страницы (ссылки и баннер): передавайте её в оболочку и страницы ошибок как bodyEnd.

Страница /policy/license состоит из двух частей. Сверху неизменяемая часть платформы: пояснение и оригинальный английский текст лицензии MIT (в обоих языках, перевод лицензии лицензией не является) с держателем прав platformCopyright. Под ней текст владельца приложения (по умолчанию заглушка), который правится в разделе «Политики» админки. Правка текста владельца часть платформы не затрагивает и убрать её нельзя. Остальные страницы политик такой части не содержат.

privacy

privacy.exportUserData({ db, findUserByIdFn, moduleRegistry, auditLogFn, auditQueryFn, listAuthenticatorsFn, userId }) собирает данные субъекта: учётную запись без секретов, сессии без идентификаторов, способы входа без секретов, записи аудита и данные модулей (dataSubject.export). privacy.eraseUserData({ …, userId, mode }) по умолчанию обезличивает (mode: 'anonymize'), удаление — явно ('delete'), потому что журнал аудита неизменяем; стёртые псевдонимы в аудите читаются как «[erased]». privacy.createErasureLedger(file) ведёт файл со списком стёртых, чтобы повторить стирание после восстановления старой копии (reapply). Пример подключения — examples/workshop/src/context.js.

privacy.buildProcessingRegistry({ moduleRegistry, config }) собирает реестр обработки персональных данных: записи платформы (учётные записи, сессии, журнал аудита, копии и другие) со сроками хранения из настроек и записи модулей из dataSubject.purpose, dataSubject.legalBasis и dataSubject.retentionDays. Основание обработки для данных платформы определяет владелец приложения, оно остаётся в реестре для заполнения. Модуль без цели или основания попадает в gaps. Формат: privacy.formatProcessingRegistry(реестр, { format: 'md'|'csv'|'json', lang: 'ru'|'en' }); в CSV значения, похожие на формулы, экранируются. В консоли: privacy registry.

Внимание. Ядро не отзывает письма из очереди: перед стиранием вызовите emailQueue.cancelForAddress(адрес), как делает workshop в context.js. Данные собственных таблиц приложение стирает через dataSubject.erase своего модуля.

audit

Журнал событий: audit.log(db, { actor, action, entity, entityId, result, meta, requestId, ip }), contextFromRequest(req) (актор, id запроса, IP), onEntry(fn) (подписка, чтобы копия ушла за пределы машины), запросы query, page (по курсору, стабильно при добавлении), count (фильтры: actor, action, actionPrefix, entity, entityId, result, since, until), tail, purgeOlderThan.

  • Цепочка хешей: каждая запись хранит хеш с учётом предыдущей; verifyChain(db) находит первую испорченную запись; anchor(db) — снимок головы цепочки для хранения вне базы (его пишет logs.logAuditAnchor по расписанию).
  • Псевдонимы: логины и IP хранятся как псевдонимы (pseudonymize), расшифровка через createResolver; eraseSubjects удаляет соответствие, и записи читаются как «[erased]», цепочка остаётся целой.
  • redactMeta заменяет значения под ключами, похожими на секрет, на [REDACTED].
  • Срок хранения — audit.retentionDays.

Пример: logAudit в examples/workshop/src/routes.js и задачи audit-gc, audit-anchor в server.js. CLI: audit tail|export|verify.

ldap

ldap.createLdapAuthenticator(config, { env, bindPassword, ldapts }) проверяет учётные данные в LDAP/AD и возвращает группы; roleFromGroups(groups, roleMapping, defaultRole) сопоставляет группы ролям; LdapConfigSchema — схема настроек (пароль привязки только как env:NAME). Пакет ldapts нужен только при включённом LDAP. Роль по умолчанию — viewer. Приложение само решает, создавать ли локальную запись пользователя при первом входе.

Вход в приложение. accounts.mountAccountRoutes(app, { directory }), где directory = { authenticate, source: 'ldap', allowedRoles } (authenticate берётся из createLdapAuthenticator). Неизвестное имя и учётная запись, созданная из каталога, проверяются в LDAP; при первом удачном входе запись создаётся (роль из roleMapping/defaultRole, пароль случайный, смена пароля не требуется) и привязывается к каталогу (таблица directory_links). Локальная учётная запись с тем же именем каталогом не проверяется и не захватывается. На любой отказ пользователь видит один ответ «неверные данные»; причина (directory_not_found, directory_unavailable, …) пишется в журнал. csv

csv.writeCsv(rows, { excel, delimiter, eol, bom, quoteAll, escapeFormulae }) — единственный писатель CSV в ядре (аудит в админке, реестр обработки и CLI audit export идут через него). Текст, который электронная таблица прочла бы как формулу (начало с =, +, -, @, табуляции, перевода строки, | и шаблоны вроде =cmd|…), получает апостроф; числа не меняются; защита включена по умолчанию (escapeFormulae: false отключает). bom: true нужен, чтобы Excel открыл UTF‑8 как UTF‑8; delimiter: ';' — для русской локали Excel. csv.parseCsv(input, { encoding, fallbackEncoding, delimiter, unescapeFormulae, limits }) принимает строку или байты: метка порядка байтов учитывается, иначе пробуется строгий UTF‑8, при неудаче — windows-1251 (то, что пишет русский Excel); разделитель (, ; табуляция) определяется по первой строке; пределы: 10 МиБ, 20 000 строк, 200 столбцов, 500 000 ячеек (CsvError со стабильным code: TOO_BIG, TOO_MANY_ROWS, TOO_MANY_COLS, TOO_MANY_CELLS, UNTERMINATED_QUOTE, BAD_ENCODING). Все ячейки — строки; числа и даты из текста понимает xlsx.mapRows. Известная неоднозначность: текст, который сам начинался с '-5, при записи не меняется, а при unescapeFormulae потеряет апостроф.

excel: 'ru' — для файла, который человек откроет двойным щелчком в Excel: метка UTF-8 (без неё кириллица превращается в кракозябры) и ; между полями (это разделитель списков русского Excel; с запятой всё попадает в одну колонку); excel: 'en' оставляет запятую. Так пишут выгрузки админки (язык интерфейса) и privacy registry --format csv. Для обмена между программами excel не нужен.

xlsx

Excel без внешних библиотек (SheetJS и exceljs отвергнуты: открытые уязвимости и размер); архив читают и пишут yauzl и yazl, которые в ядре уже есть, и подгружаются при первом использовании.

xlsx.buildWorkbook({ title, creator, created, sheets: [{ name, columns: [{ header, key, width, format, list, style, headerStyle }], rows, header, freezeHeader, freezeColumns, autoFilter, conditional, merges, tabColor, print }] }) возвращает Buffer (xlsx.XLSX_MIME — тип содержимого). format: text, number, integer, money, percent, date, datetime. Значение ячейки: строка, число, логическое, Date (UTC) или { formula, value } — формула с сохранённым значением; формулы принимаются только в таком виде и проверяются (нельзя ссылки на другие книги, HYPERLINK, WEBSERVICE, INDIRECT и подобные). Текст всегда записывается как текст, никогда как формула; текст, начинающийся с =, +, -, @, получает стиль «текст с апострофом», поэтому остаётся текстом и после правки в Excel (xlsx.isFormulaLike). Управляющие символы удаляются, ячейка не длиннее 32767 знаков, листов до 50, имена листов очищаются. list: ['новая', 'в работе'] делает в столбце выпадающий список (простые тексты без запятых и кавычек, всего до 255 знаков). В книгу пишутся свойства документа, а при наличии формул — пересчёт при открытии; сохранённый результат формулы может быть числом, строкой или логическим значением. Одни и те же данные дают один и тот же файл.

Вторая проверка схемой Zod. mapRows(rows, spec, { schema }): после правил столбцов (type, required, pattern, validate…) каждая строка проходит schema.safeParse(data), где schema — схема Zod или любой объект с safeParse. Схема видит только уже сопоставленные значения (не лист), может их преобразовать (в records попадает результат разбора) и проверить связи между полями (.refine). Каждое замечание схемы — ошибка SCHEMA со столбцом, на который указывает путь замечания, и текстом замечания в hint (до 200 знаков; тексты замечаний пишет приложение, в них не должно быть чужих данных). Исключение внутри схемы — SCHEMA_ERROR для строки; схема должна быть синхронной. Строка, не прошедшая схему, не считается принятой, поэтому её ключ unique не занимает место: настоящий дубль потом всё равно найдётся.

Журнал импорта. audit.logSpreadsheetImport(db, contextFromRequest(req), { buffer, fileName, read, mapped, error }) пишет в обычный журнал аудита (та же цепочка, псевдонимы и срок хранения) запись import.spreadsheet: размер и SHA-256 файла (по нему видно, какой именно файл загружали), формат, число листов и прочитанных строк, accepted и rejectedRows, счётчики кодов ошибок (errorCodes: { REQUIRED: 3 }) и предупреждений. Значений ячеек, заголовков и текстов подсказок в записи нет. Если файл отклонён ещё до сопоставления, передайте error: запись получит результат failure и errorCode. Имя файла сохраняется только если вы его передали (в имени бывает фамилия): оставляйте его, когда оно может содержать персональные данные.

Скрытые столбцы. skipHiddenColumns: true (readWorkbook, streamSheet, только .xlsx) не отдаёт значения скрытых столбцов: они остаются на своих местах пустыми (null), поэтому буквы столбцов, index в mapRows, объединения и таблицы по-прежнему верны, а скрытые данные не попадают в результат. Для .ods, .xlsb и .xls опция отклоняется с BAD_OPTION, а не игнорируется молча. Скрытые строки — отдельная опция skipHiddenRows.

Даты числом. dates: 'serial' (у readWorkbook, streamSheet, .xlsb, .xls) оставляет в датированных ячейках номер дня таблицы (45368 вместо даты 17.03.2024); по умолчанию 'date'. Для .ods недоступно (там даты хранятся текстом) и даёт BAD_OPTION; любое другое значение — RangeError.

Все пределы в одном файле. src/xlsx/limits.js (xlsx.DEFAULT_LIMITS, xlsx.STREAM_LIMITS, xlsx.WRITE_LIMITS, xlsx.LIMIT_NOTES): значения чтения можно поднимать через limits: {…} при вызове, пределы записи повторяют потолки Excel и не меняются. В LIMIT_NOTES для каждого предела сказано простыми словами, от чего он защищает.

Ссылки. Ячейка { value: 'Сайт', link: 'https://example.org/' } пишется как внешняя гиперссылка (если value пуст, показывается сам адрес; ссылка красится в синий, подчёркивания в безопасном наборе стилей нет). Разрешены только https:, http: и mailto:; всё остальное (javascript:, file:, data:, ftp:, UNC-пути, адрес с логином и паролем, пробелы и управляющие символы, длиннее 2000 знаков, больше 65 530 ссылок на лист) отклоняется с BAD_LINK. Ссылка ничего не открывает и не проверяет: это только запись в файл. Работает и в buildWorkbookStream.

Объединения (merges). Диапазон над строкой заголовка при включённом автофильтре отклоняется (BAD_SHEET): Excel показывает такие заголовки пустыми. Задайте autoFilter: false или объединяйте ниже заголовка.

Оформление. style столбца (и headerStyle для его заголовка) и style отдельной ячейки (значение в виде { value, style } или { formula, value, style }, например для цвета статуса) — только из безопасного набора: bold, italic, wrap (логические), color и fill (имя цвета: white black grey darkgrey green darkgreen red darkred yellow darkyellow blue darkblue orange darkorange или строго #RRGGBB), border ('thin' — рамка, 'bottom' — линия снизу), align (left center right), valign (top center bottom). Всё остальное, как и цвет не из этого вида, — ошибка BAD_STYLE (в файл ничего подставить нельзя). Стиль ячейки накладывается на стиль столбца; одинаковые стили делят один формат, а различных в книге не больше 1000. Стиль не отменяет защиту: текст, похожий на формулу, остаётся текстом. Цвет по правилу: conditional: [{ column: 'status', rules: [{ equals: 'Готово', style: { fill: 'green', color: 'darkgreen' } }, { contains: 'проср', style: { fill: 'red' } }] }] (столбец — по key или номеру с 0) красит ячейки по значению, поэтому цвет статуса не «залипает», когда человек правит ячейку (стиль ячейки, в отличие от этого, остаётся, как был). Условия: equals, notEquals, greaterThan, greaterOrEqual, lessThan, lessOrEqual (число или текст до 255 знаков), between: [от, до], contains: 'текст'; у правила ровно одно условие и style из bold, italic, color, fill, border (выравнивание и перенос правилом не задаются, BAD_STYLE). Правила действуют с первой строки данных до конца листа; не больше 20 правил на столбец и 50 столбцов. merges: ['A1:C1'] — объединение ячеек (номера строк считаются с заголовком; не больше 1000; пересекающиеся, перевёрнутые и из одной ячейки — BAD_SHEET), freezeColumns: n закрепляет первые n столбцов, tabColor красит вкладку, print: { orientation: 'landscape', paper: 'A4' | 'A3' | 'Letter', fitToWidth: true, repeatHeader: true } — печать по ширине страницы с повтором заголовка на каждой странице. Формулы: функции новее Excel 2007 (XLOOKUP, IFS, TEXTJOIN, MAXIFS, STDEV.S и другие) получают префикс _xlfn. автоматически (кроме текста в кавычках), иначе Excel показал бы #NAME?; функции, возвращающие массив (FILTER, SORT, UNIQUE, LET, LAMBDA, VSTACK и подобные), не поддерживаются — BAD_FORMULA, результат пишите значениями. Проверено открытием в LibreOffice, в самом Excel — нет.

xlsx.readWorkbook(buffer, { limits, sheets, fillMergedCells, macros, externalLinks, skipHiddenRows, display, locale, signal }) возвращает { sheets: [{ name, hidden, rows, merges, tables }], warnings } (tables — таблицы Excel листа, см. ниже; limits по умолчанию — xlsx.DEFAULT_LIMITS); строки — массивы значений (строка, число, логическое, Date, null). Читатель строгий: файл до 10 МиБ, до 200 частей, часть до 64 МиБ в распакованном виде, до 20 000 строк, 200 столбцов, 500 000 ячеек (всё меняется через limits); отказ для файлов не из Excel, старых .xls и зашифрованных, книг с макросами и внешними ссылками, XML с объявлением типа документа и сущностями (защита от XML-бомб). Формулы не вычисляются: берётся сохранённое значение, число таких ячеек — в warnings (FORMULAS_NOT_EVALUATED). Даты определяются по формату ячейки (встроенному и собственному, системы 1900 и 1904): время без даты приходит как Date на 1899‑12‑30, длительность [ч]:мм — числом (в сутках). Объединённые ячейки: значение есть только в левой верхней, диапазоны отдаются в merges, а fillMergedCells: true копирует значение в остальные. Макросы определяются по тому, что в файле есть на самом деле (проект макросов, листы макросов, тип главной части macroEnabled), а не по типам по умолчанию, которые тянут за собой шаблоны Excel (так procure‑it получал ложный отказ). Разбор XML линейный и строгий (невалидный XML — BAD_XML; любые префиксы пространств имён, ячейки без адреса, книга ищется через _rels/.rels; листы-диаграммы пропускаются с предупреждением NON_WORKSHEET_SKIPPED). Имена частей архива приводятся к одному виду (регистр, \\, ведущий /), поэтому макрос нельзя спрятать необычным написанием пути. Архив проверяется до распаковки: дубли имён (DUPLICATE_ENTRY), заявленные размеры, степень сжатия (ZIP_BOMB). skipHiddenRows пропускает скрытые строки, signal (AbortSignal) отменяет чтение, которое уступает циклу событий. Скрытые столбцы пока не пропускаются. Файл .xlsm по умолчанию отклоняется; macros: 'ignore' читает только ячейки, проект макросов не открывается и не запускается. Ошибка — xlsx.XlsxError со стабильным code (TOO_BIG, TOO_MANY_ROWS, MACROS, EXTERNAL_LINKS, UNSAFE_XML, LEGACY_OR_ENCRYPTED, NOT_A_WORKBOOK и другие): текст для человека делает приложение.

Правила у всех одни: те же пределы (limits), те же отказы (шифрование, макросы, внешние ссылки, XML с типом документа), формулы не вычисляются, а число таких ячеек идёт в warnings. .xlsb разбирается по записям с проверкой границ каждой записи (повреждённый файл — BAD_BINARY, а не догадка). .ods: повторы («миллион пустых строк» — так заканчивается любой .ods) не раскрываются, пока в строках нет данных, а данные считаются в пределы заранее; примечания, рисунки и вложенные таблицы не попадают в текст ячейки; скрытый лист определяется по стилю. Внешние ссылки по умолчанию отклоняются; externalLinks: 'ignore' читает сохранённые значения (ничего не загружается) и добавляет предупреждение EXTERNAL_LINKS_IGNORED. Старые .xls (Excel 97–2003, BIFF8 в контейнере OLE2) читает xlsx.readXls (и readSpreadsheet, format: 'xls'): контейнер разбирается с проверкой каждого сектора и цепочки (петля, выход за файл, заявленный размер больше фактического — BAD_CONTAINER), записи — с проверкой границ (BAD_BINARY); отказ для зашифрованных (FILEPASS, шифрованный .xlsx в том же контейнере), с макросами (проект макросов или лист макросов), со ссылками на другие книги (externalLinks: 'ignore' разрешает чтение сохранённых значений) и для версий Excel 5 и старше (UNSUPPORTED_FORMAT). Общие строки, продолжающиеся в CONTINUE (в том числе со сменой 8-/16-битного текста), даты по формату ячейки, RK/MULRK, результаты формул, объединения, скрытые листы и строки читаются так же, как в .xlsx. Для readXlsx/readWorkbook (только .xlsx) старые файлы по‑прежнему дают LEGACY_OR_ENCRYPTED.

Большие файлы построчно. xlsx.streamSheet(buffer, { sheet, limits, display, locale, skipHiddenRows, macros, externalLinks, signal }) открывает один лист .xlsx (по имени или по номеру с 0; без sheet — первый) и отдаёт строки по одной: const s = await xlsx.streamSheet(buf, { sheet: 'Заявки' }); for await (const { row, values, shown } of s.rows) { … }. Строка не копится: в памяти файл, общие строки и одна порция строк (на файле в 300 тысяч строк по 5 столбцов пик памяти был около 100 МБ против около 600 МБ у readWorkbook; читается медленнее, на этом файле 7 с против 4 с). row — номер строки листа с 1, пустые строки пропускаются, values без хвостовых пустых; s.merges, s.tables и s.warnings полные, когда строки прочитаны (tables — сразу). Лист распаковывается по ходу чтения и считается (limits.maxSheetBytes, по умолчанию 1 ГиБ; maxRows по умолчанию 1 048 576 и maxCells 20 млн — значения xlsx.STREAM_LIMITS); остальное как у readWorkbook: архив проверяется заранее, макросы, внешние ссылки, шифрование и тип документа в XML отклоняются, CDATA в потоковом листе не принимается (UNSAFE_XML), неизвестный лист — NO_SUCH_SHEET. Сам файл всё равно целиком в Buffer, поэтому для большой выгрузки поднимайте limits.maxBytes (10 МиБ по умолчанию). fillMergedCells в потоке не работает (объединения известны только после последней строки). Только .xlsx/.xlsm; .xlsb, .ods, .xls читаются целиком.

xlsx.buildWorkbookStream(book) пишет книгу потоком: rows листа может быть любым итерируемым или асинхронно итерируемым (курсор базы, генератор), строки превращаются в XML и сразу уходят в архив, Promise<Readable> отдаёт pipeline(await xlsx.buildWorkbookStream(book), res). Все проверки buildWorkbook (стили, формулы, имена, пределы) сохраняются; что неверно в самом листе (имя, стиль столбца, объединения), находится до первого байта, а неверная ячейка или ошибка источника посреди выгрузки обрывает поток с этой ошибкой, поэтому получатель обязан считать оборванный поток негодным файлом (не «почти готовым»). Части, зависящие от всех строк (стили, признак формул, диапазон автофильтра), пишутся в конце архива.

Значение «как показано». Опция display: true (и locale: 'en' | 'ru', по умолчанию 'en') добавляет к каждому листу матрицу shown — той же формы, что rows, но с текстом, который человек видит в ячейке: 1 234,50 ₽, 02.11.2026, 25,6%, ИСТИНА, #DIV/0!. Типизированные rows не меняются (цифра остаётся числом, дата — датой), shown лежит рядом, поэтому ничего не теряется. Работает для .xlsx/.xlsb/.xls (по числовому формату ячейки: разделы, условия [>100], дроби, E+, [h]:mm, AM/PM, месяцы по-русски, системные [$-F800]/[$-F400]) и .ods (берётся текст, который программа записала в ячейку). Текст остаётся как есть, числа — по формату; отступы для выравнивания (_), * ) отбрасываются, пробел в разделителе тысяч для ru неразрывный, как в Excel. Известные пробелы: цвета и символы-заполнители не воспроизводятся, General даёт до 15 значащих цифр (Excel обрезает по ширине столбца), календарные эры (e для тайваньского года) не поддержаны. Движок отдельно: xlsx.createFormatter({locale, date1904}).show(value, 'dd.mm.yyyy').

Файлы от посторонних. xlsx.readSpreadsheetIsolated(buffer, опции) — то же чтение, но в отдельном потоке: у него своя куча с потолком (maxMemoryMb, по умолчанию 512; файлу не хватило памяти — RESOURCE_LIMIT, а сервер не страдает), своё время (timeoutMs, по умолчанию 30 с; зависший разбор останавливается принудительно — TIMEOUT), пустое окружение (поток не видит секретов процесса) и остановка по signal. Ошибки — те же XlsxError с теми же кодами; результат тот же, включая format. Опции — те, что можно скопировать в другой поток (поэтому нельзя передать zip). Для файлов, которые загружают пользователи, берите его; обычный readSpreadsheet — для своих файлов. В обычный readSpreadsheet добавлены timeoutMs (читатель часто отдаёт управление, поэтому часы замечаются) и hiddenSheets: 'include' (по умолчанию) читает скрытые листы и сообщает об этом предупреждением HIDDEN_SHEETS_READ, 'skip' оставляет их (HIDDEN_SHEETS_SKIPPED): скрытый лист — это данные, которые автор файла не показывал, поэтому импорт должен либо показать их в предпросмотре, либо не брать.

mapRows: pattern — регулярное выражение приложения, которое запускается на тексте из файла, поэтому текст сначала проверяется по длине: по max столбца, а если его нет — не длиннее 1000 знаков (TOO_LONG); плохо написанное выражение не получит огромную ячейку. Флаги g и y в pattern отбрасываются (с ними test помнит позицию и на разных строках отвечает по-разному).

xlsx.mapRows(rows, { columns: { ключ: { header, type, required, max, min, allowed, pattern } } }) для импорта: находит строку заголовков (среди первых 10), сопоставляет столбцы по тексту заголовка (без учёта регистра, допускаются синонимы), приводит значения (string, number с десятичной запятой или точкой и разделителями тысяч, integer, date в виде ISO, ДД.ММ.ГГГГ или номера дня Excel, boolean) и возвращает { records, errors, missingColumns, unknownColumns, duplicateColumns, headerRow, truncated }; у столбца ещё default, unique (повтор — DUPLICATE) и normalize (например, привести «Используеться» к «используется» до проверки allowed); у каждой ошибки номер строки, ключ столбца и код (REQUIRED, TOO_LONG, NOT_A_NUMBER, OUT_OF_RANGE, NOT_A_DATE и т. д.). Ничего не сохраняется: приложение показывает предпросмотр и сохраняет после подтверждения. Загруженный файл сначала проверяйте files.acceptUpload.

Таблицы Excel и листы без заголовка. Читатель .xlsx отдаёт для каждого листа tables: [{ name, c1, r1, c2, r2, headerRow, totalsRow, columns }] (границы — как у merges: r с 1, c с 0; у остальных читателей поля tables нет). Таблица Excel — надёжная подсказка строки заголовков: mapRows(rows, spec, { table: sheet.tables[0] }) берёт первую строку таблицы как заголовок, читает только её ячейки и не берёт итоговую строку, а номера строк в ошибках остаются номерами листа. Другие подсказки: headerRow: 7 (номер строки заголовка прямо), header: false с firstRow (лист без заголовка: столбцы находятся по index). У столбца index — номер с 0 или буквы ('C'): столбец, который берётся, если текст заголовка не найден, а при header: false единственный способ. validate(значение, запись) выполняется последним и возвращает ничего (всё хорошо), строку-код ошибки или false (код INVALID). Если значение не входит в allowed и отличается от допустимого на пару букв («Используеться», «резрев»), в ошибке NOT_ALLOWED есть hint с ближайшим допустимым: превью может спросить «имелось в виду…».

Внимание. Читатель не доверяет файлу, но и не заменяет проверок приложения: значения из файла проходят ту же проверку (Zod), что и ввод в форме.

Одно объявление: текст до 300 символов, важность info, warning или critical, необязательное время окончания (после него баннер пропадает сам). info и warning читатель может скрыть крестиком; выбор помнится в его браузере, пока текст не изменится. critical скрыть нельзя. Текст экранируется. Состояние хранится в базе (app_settings), общее для всех процессов, процесс перечитывает его не реже раза в 2 секунды. Ошибки ввода: AnnouncementError с кодом MESSAGE_REQUIRED, MESSAGE_TOO_LONG, LEVEL_INVALID, UNTIL_INVALID.

Как подключить. Раздел «Объявление» в админке включается опцией announcement у createAdmin; баннер на страницах админки появляется сам. На страницы приложения его выводит оболочка: ui.renderAppShell({ ..., bannerHtml: announcement.bannerHtml(locale, { nonce }) }). Пример: examples/workshop/src/server.js кладёт функцию в res.locals.banner, а appShell в src/routes.js передаёт её результат оболочке. Страницы вне оболочки (вход, ошибки) баннер не показывают.

accounts

Назначение. Готовые маршруты и страницы учётной записи для приложения. accounts.mountAccountRoutes(app, { db, authProvider, appConfig, bans, onLock, emailService, logger, permissionsForRole, mfaRequiredForRole, appName, vendorIdentity, theme, brand, texts, pages, accountShell, accountPath, homePath, passwordChangePath, allowDuringPasswordChange }) подключайте после сессий.

Маршруты (JSON). Страницы. Ядро рисует GET /login (два шага, второй — код TOTP или восстановления), /forgot-password, /reset-password (токен в адресе после #, в логи не попадает), страницу обязательной смены пароля (passwordChangePath, по умолчанию /ui/password) и, если передан accountShell(req, res, { title, bodyHtml, activePath }), страницу «Аккаунт» (accountPath, по умолчанию /ui/account: пароль, e-mail, интерфейс, аутентификаторы, коды восстановления). Защита. Лимит запросов security.loginRateLimit; блокировка после неудачных входов по трём счётчикам (имя + адрес, имя, адрес; настраивается security.lockout) с записью auth.lockout в аудит; общий счётчик ошибок второго шага на пользователя; выравнивание времени ответа для неизвестного имени; новая сессия при каждом входе; секреты TOTP хранятся зашифрованными (ключи auth.totpEncryptionKey, previousTotpEncryptionKeys, секреты сессий). Пока включена обязательная смена временного пароля, закрыты все пути, кроме /password/change, /logout, /me, /login, /, /favicon.ico и перечисленных в allowDuringPasswordChange; браузер отправляется на passwordChangePath.

Что решает приложение. permissionsForRole(role) — права по роли; mfaRequiredForRole(role) — роли, которые не могут снять последний фактор. Возвращает { forgetLoginFailures(username), userPublicShape(user), totpKey }: первое вызывают после сброса пароля администратором. Все действия пишутся в аудит (auth.login, auth.login.totp, auth.password_change и другие).

Что требует внимания при разработке

  1. Порядок middleware важен: локаль → ошибки → заголовки → тела → cookie-parser → CSRF → сессии → attachUser → баны → маршруты → обработчики 404 и 500.
  2. Ядро — механизм, приложение — смысл. Права, роли, имена полей и тексты задаёт приложение (контракт Module), а не ядро.
  3. Хеширование паролей делает AuthProvider приложения; не храните пароль нигде, кроме хеша.
  4. Права поля вырезаются на сервере (serialize), а не скрываются в интерфейсе.
  5. Стирание должно отзывать письма из очереди и стирать данные собственных таблиц модуля.
  6. Загрузки только через acceptUpload, выдача только через sendUpload; каталог брендинга отделён от загрузок приложения.
  7. Задачи обслуживания (sessions-gc, audit-gc, bans-gc, metrics-gc, uploads-gc, очистка токенов сброса, резервные копии) регистрируйте в планировщике: ядро само их не запускает.
  8. Нативные пакеты после npm install требуют одобрения скриптов установки.

См. также: Конфигурация, Безопасность, Администрирование, Консольные команды.

Конфигурация

Назначение

Вся настройка приложения — один объект, проверяемый схемой Zod (ApplicationConfigSchema, packages/core/src/config/schema.js). Ошибка в ключе — ошибка запуска, а не молчаливое игнорирование: все объекты строгие (strictObject), опечатка sever.port не пройдёт.

Откуда берутся значения

Порядок, каждый следующий слой перекрывает предыдущий:

  1. значения по умолчанию из схемы;
  2. файл app.config.js в рабочей папке (или путь configPath; явно указанный, но отсутствующий файл — ошибка, отсутствие файла по умолчанию — нормально);
  3. overrides — объект, переданный в loadConfig (в основном для тестов);
  4. переменные окружения из списка ниже.
import { loadConfig } from '@das-forge/core';
const config = await loadConfig();                       // app.config.js + env
const config2 = await loadConfig({ overrides: { server: { port: 0 } } });

Пример файла — examples/workshop/app.config.js: имя, порт, база, резервная копия в data/backups, секрет сессии (только для локального примера).

Свои настройки приложение добавляет расширением схемы и передаёт её как schema:

const Schema = ApplicationConfigSchema.extend({ myApp: z.strictObject({ plantId: z.string() }) });
const config = await loadConfig({ schema: Schema });

Порты приложений платформы

Каждое приложение занимает два соседних порта в диапазоне 9xxx: HTTPS — 9N02, HTTP — 9N01, причём HTTP всегда только перенаправляет на HTTPS (обмен данными идёт лишь по HTTPS). Следующее приложение получает порты на 100 больше: шаг между приложениями — 100.

следующие9202, 9302, …9201, 9301, …

Редирект включается сам: порт HTTP — это server.port − 1, поэтому достаточно задать server.port. Реализация — http.createHttpRedirectServer и http.resolveRedirectPort, подключение — examples/workshop/src/server.js. За обратным прокси редирект выполняет прокси, слушатель не запускается. Запросы с телом (POST и т. п.) по HTTP не перенаправляются, а отклоняются кодом 426; остальные меры защиты от захода по HTTP — в разделе «Безопасность» («Заход по HTTP»).

Как открыть приложение для локальной сети (адрес, брандмауэр, сертификат, Docker) — «Эксплуатация» → «Доступ из локальной сети».

Внимание: в Docker-образе workshop по умолчанию DAS_PORT=9002 в режиме reverse-proxy (прокси сам отдаёт 443 и редирект); компоновка docker-compose.yml публикует 127.0.0.1:9002.

Безопасность

Сводный документ: что защищено по умолчанию, что обязано сделать приложение и как это проверить.

Модель угроз. Ядро рассчитано на веб-приложения внутри организации с входом по логину и паролю, возможно с двухфакторной проверкой. Защищаемся от: подбора паролей, кражи и подмены сессий, межсайтовых запросов (CSRF), внедрения разметки и скриптов, вредоносных загрузок, утечки полей, которые клиенту видеть нельзя, подмены журнала аудита и утечки секретов через конфигурацию и логи. Сервер доверяет только серверной сессии; всё, что приходит от клиента, считается недоверенным.

Пароли

  • Хеширование: argon2id (memoryCost: 19456, timeCost: 2, parallelism: 1 — настраивается в auth.argon2). Число одновременных проверок ограничено (maxConcurrent: 2, очередь maxQueue: 64, сверх неё ответ 503), чтобы пароли нельзя было использовать как способ нагрузить сервер.
  • Правила пароля: по умолчанию 12 символов для всех (NIST: длина важнее состава). Администратор меняет их в разделе «Парольная политика» без перезапуска: профили «NIST» (длина, без правил состава) и «ФСТЭК» (длина 12 и все четыре класса символов, алфавит от 70 знаков), своя минимальная длина, отдельная для администраторов (adminMinLength), число обязательных классов символов (строчные, заглавные, цифры, остальные). Всегда действуют: пароль не равен логину и текущему паролю, не содержит логин, часть e-mail до «@» и название приложения, не входит в список типовых; максимум 128 (maxLength, потолок 1024). Пока администратор ничего не сохранил, значения берутся из auth.passwordPolicy (конфигурация). Проверка (auth.createPasswordPolicy().check, низкоуровневая auth.checkPasswordPolicy) возвращает коды (TOO_SHORT, TOO_LONG, SAME_AS_USERNAME, SAME_AS_CURRENT, COMMON, TOO_FEW_CLASSES, CONTAINS_CONTEXT), а не тексты; страницы входа и аккаунта показывают их сами. Срок действия пароля (maxAgeDays) по умолчанию не ограничен (0): принудительная смена по сроку включается только если администратор задал число дней (профиль «ФСТЭК» ставит 90); просроченный пароль при входе работает как принудительная смена (аудит auth.password_expired), часы стартуют с первого входа после включения. Запрет повторов (historyCount, 0–24) сравнивает новый пароль с текущим и последними паролями учётной записи (хранятся только хеши). Список утёкших паролей: файл формата «Pwned Passwords» (SHA1:число, отсортирован по хешу) в auth.passwordBlocklistFile; ищется на диске двоичным поиском, наружу ничего не отправляется, нечитаемый файл не блокирует смену пароля; найденный пароль получает код LEAKED, повтор — REUSED. Уже заданные пароли задним числом не проверяются: кнопки «Потребовать смену пароля» в том же разделе разлогинят выбранных и заставят выбрать новый пароль.
  • Сгенерированные пароли — 24 символа без похожих знаков (первый администратор, временные пароли из админки и CLI, сброс). Пароль первого администратора записывается в файл с правами только для владельца; в консоль он выводится, пока не задано DAS_BOOTSTRAP_PRINT=false.
  • Временный пароль помечает учётную запись mustChangePassword. Приложение обязано пускать такого пользователя только на смену пароля (в workshop: /ui/password, остальное — редирект или 403 PASSWORD_CHANGE_REQUIRED). При смене временного пароля текущий вводить не нужно; новый не может совпадать с временным.
  • Старые схемы хешей приложений подключаются как «ленивая миграция» при входе (auth.createAuthProvider).

Сессии

  • Хранилище: express-session + auth.createSessionStore на SQLite. В базе лежит хеш идентификатора сессии, а не значение cookie.
  • Cookie: httpOnly, sameSite: 'lax', secure автоматически (по req.secure), подписана ключом из auth.sessionSecret (минимум 16 символов; предыдущие значения в previousSessionSecrets только проверяют подпись, поэтому смена секрета не разлогинивает пользователей).
  • Время жизни: sessionTtlMs (8 часов), простой sessionIdleTimeoutMs (1 час, 0 — выключено).
  • Новый идентификатор при каждом входе (защита от фиксации сессии, establishSession).
  • Отзыв: destroyUserSessions при смене пароля, роли, блокировке и удалении; администратор завершает сессию вручную («Безопасность»).
  • createSessionStore({ isUserActive }): запрос, который ещё выполнялся в момент отзыва, не может заново записать сессию удалённого или заблокированного пользователя.
  • http.attachUser({ revalidate(id, snapshot), cacheMs = 30000 }): роль и блокировка перечитываются из источника истины (кэш по сессии), поэтому пропущенный вызов отзыва не оставляет права навсегда. Приложение передаёт revalidate (в workshop: src/server.js).

Защита входа

  • Лимит запросов: общий security.rateLimit (100 за 60 с) и отдельный строгий security.loginRateLimit (10 за 60 с) для /login, /login/totp, /login/recovery. Состояние хранится в памяти процесса: при нескольких процессах за балансировщиком лимит действует на каждый процесс (общее хранилище подключается опцией store у express-rate-limit).
  • Самостоятельная регистрация (auth.registration.enabled, по умолчанию выключена): /register и письмо со ссылкой /register/confirm; до перехода по ссылке учётной записи нет, в базе лежит только хеш токена и хеш пароля. Фильтры от ботов: скрытое поле, минимальное время заполнения, не более 5 заявок с адреса в час, одно письмо на e-mail в 10 минут; занятые логин или e-mail не раскрываются (ответ тот же). Пароль проверяется общей политикой паролей. Переключатель requireEmailConfirmation: false создаёт учётную запись сразу и годится только для закрытой сети.
  • Блокировка после неудач: security.lockout — пятая неудача блокирует на 5 минут, каждая следующая удваивает до 24 часов (счётчик обнуляется после суток без неудач); блокировка по одному логину (общий бюджет) ограничена часом, чтобы посторонний не мог держать владельца снаружи сутки. Одинаковый ответ для неизвестного логина и неверного пароля, неизвестный логин тоже «платит» проверкой пароля (одинаковое время). В workshop бюджет считается по паре (логин, адрес): посторонний блокирует только свой адрес, владелец с другого адреса входит. Общий бюджет по логину в 6 раз шире и при срабатывании пишет в аудит auth.lockout; по адресу — отдельный бюджет (×4). Сброс пароля снимает блокировки логина (createFailureTracker().resetPrefix). Каждая новая блокировка вызывает onLock трекера (createFailureTracker({ onLock })); к нему подключают alerts.lockoutWatcher.
  • Баны (security.createBans): IP и пользователи, срок или бессрочно, проверка до маршрутов (bans.middleware() после attachUser). Нельзя забанить себя.
  • Многофакторная проверка: TOTP (otplib, секрет в БД зашифрован AES-256-GCM ключом auth.totpEncryptionKey; без него ключ выводится из sessionSecret, и смена секрета ломает TOTP — задавайте отдельный ключ и держите прежние в previousTotpEncryptionKeys), коды восстановления (разовые, наборы заменяются целиком), нельзя удалить последний фактор для роли, где MFA обязательна. Ошибки TOTP и кодов восстановления делят общий бюджет попыток с блокировкой.

Межсайтовые запросы (CSRF)

http.csrfProtection() без токенов, по заголовкам: безопасные методы пропускаются; Sec-Fetch-Site: cross-site отклоняется; Origin обязан совпасть с хостом запроса (или trustedOrigins), Origin: null отклоняется; для остальных запросов проверяется Referer. Запрос без этих заголовков (curl, межсерверный клиент) допускается только без cookie сессии. Нужен cookie-parser. Исключения — exemptPaths (например, вебхуки с собственной подписью).

Баны и LDAP: что учтено при аудите

  • Бан имени пользователя срабатывает и при входе: workshop (examples/workshop/src/routes.js, bans.check({ username }) в /login) не создаёт сессию забаненному и пишет в аудит auth.login с причиной banned. Промежуточный обработчик bans.middleware() видит пользователя только после входа и сам по себе вход не запрещает.
  • Бан по IP — по точному адресу (IPv4-mapped IPv6 приводится к IPv4); подсеть IPv6 одним баном не закрывается.
  • Кэш банов живёт cacheMs (5 с): бан из CLI в другом процессе начинает действовать с задержкой до этого срока.
  • LDAP: соединение обязано быть зашифрованным — ldaps:// или startTls: true; простой ldap:// разрешён только с явным allowPlaintext: true (пароли пойдут открытым текстом). Имя пользователя попадает в фильтр экранированным и подставляется функцией, поэтому $&, $' в имени не искажают фильтр. Если каталог остановил выдачу на лимите (несколько совпадений), ответ — AMBIGUOUS, а не «недоступно».

Отдельный адрес администрирования

Панель администрирования открывает полный доступ к учётным записям, копиям и настройкам, поэтому ей полезен адрес, недоступный остальной сети. С server.admin.port ядро поднимает второй слушатель (тот же сертификат, то же приложение), по умолчанию на 127.0.0.1; на обычном адресе приложения пути панели (/admin) отвечают 404, как несуществующие страницы. Обратиться к панели: с самой машины, через SSH-туннель (ssh -L 9103:127.0.0.1:9103 сервер, затем https://localhost:9103/admin) или через VPN-интерфейс, указав его адрес в server.admin.host. Вход выполняется на этом же слушателе (cookie привязана к имени хоста: при другом имени хоста нужно войти заново). Диагностика (категория «Hardening») предупреждает, если приложение слушает не только loopback, а панель не вынесена. Защита по сети дополняет, а не заменяет пароль и второй фактор.

Заголовки и CSP

http.securityHeaders() (на helmet): CSP default-src 'self', скрипты 'self' и nonce на запрос (res.locals.cspNonce), object-src 'none', frame-ancestors 'none', form-action 'self', base-uri 'self'; X-Frame-Options: deny, Referrer-Policy: same-origin, COOP/CORP same-origin, Permissions-Policy без камеры, микрофона, геолокации и платежей; HSTS только для запросов по HTTPS (год; includeSubDomains включается явно). Стили допускают 'unsafe-inline'. Все свои inline-скрипты страниц подписывайте nonce.

CSP в режиме отчёта. Действующая политика разрешает встроенные стили (style-src 'unsafe-inline'). Чтобы понять, что мешает её ужесточить, включите security.csp.reportOnly: true: рядом уходит второй заголовок Content-Security-Policy-Report-Only со стилями только из 'self' и nonce, без 'unsafe-inline'. Ничего не блокируется; нарушения браузер присылает на security.csp.reportPath (http.cspReports), и они пишутся в аудит как security.csp_violation (директива, что заблокировано, страница, строка). Одинаковая пара «директива и адрес» записывается раз в час, всего не больше 60 записей в минуту, тело отчёта не больше 8 КБ. Когда отчёты затихнут, 'unsafe-inline' для стилей можно убирать.

Очистка при выходе. auth.clearSiteDataOnLogout: true добавляет к ответу выхода Clear-Site-Data: "cache", "storage": браузер забывает кэш страниц и хранилище сайта (на общем компьютере после выхода не остаётся чужих данных). Работает только по HTTPS; cookie не трогаются, поэтому метка устройства для письма о новом входе сохраняется.

CORS

http.createCors({ origins }): разрешены только точно перечисленные источники; по умолчанию пусто (запросы с других источников не разрешаются).

Клиент ↔ сервер: нулевое доверие

  • http.serialize(row, { viewerPermissions, fieldPermissions }) отдаёт только поля, на которые у зрителя есть право: поле с правом, которого нет, вырезается на сервере, а не прячется в интерфейсе. Поле без объявленного права по умолчанию закрыто.
  • Вход валидируется Zod-схемами (http.validateBody); ошибка — единый формат { error, fields: [...] }.
  • Запись «умных» полей, которых нет в схеме, игнорируется (в workshop CreateAssetSchema не принимает cost).
  • Права проверяются на сервере для каждого маршрута (requireAuth, requirePermission); скрытый пункт меню — не защита.

Загрузки файлов

files.acceptUpload — единственная точка приёма: лимит размера (обязательный), тип по содержимому (magic bytes), проверки архивов (zip-bomb guard, реальная распаковка для проверки CRC и имён), очистка SVG (DOMPurify + JSDOM, без внешних ссылок, лимит размера), обязательное перекодирование растров (убирает хвосты полиглотов и EXIF/GPS), запись под сгенерированным именем, квоты каталога. Выдача — files.sendUpload с заголовками nosniff, CSP: sandbox, Cross-Origin-Resource-Policy, Content-Disposition (вложением, кроме обычных картинок). Имя и тип от клиента — только справка.

Секреты и шифрование

  • В конфигурации секреты только как env:NAME (или файл); значения в файле конфигурации не хранятся.
  • TOTP-секреты: AES-256-GCM (формат enc:v1:…), ключ через HKDF-SHA256, ротация списком ключей.
  • Резервные копии: опциональное шифрование .zip.enc (AES-256-GCM, ключ из фразы через scrypt; фраза от 16 символов, из DAS_BACKUP_KEY или DAS_BACKUP_KEY_FILE).
  • Журнал и консоль: значения под ключами вроде пароля, токена, секрета заменяются на [REDACTED] до записи.

Возраст ключей: при замене ключа запишите дату в security.secretsRotation.sessionSecretCreatedAt / totpKeyCreatedAt / backupKeyCreatedAt; doctor предупредит, когда ключ старше maxAgeDays (365 по умолчанию). Замена totpEncryptionKey и backupKey требует перешифровки существующих данных — сначала сделайте копию.

Аудит

audit.log пишет события в append-only таблицу с цепочкой хешей: изменение или удаление записи ломает цепочку (audit.verifyChain, кнопка в админке). Логин и IP хранятся как псевдонимы с отдельной таблицей соответствий; при стирании данных пользователя соответствие удаляется, а цепочка остаётся целой. Администрирование

Админ-панель /admin: что она включает по умолчанию, что должно быть в приложении, чтобы она заработала, и как добавить свои разделы.

Принцип: приложение расширяет админку, а не пишет свою

Администрирование, оформление и поведение учётной записи общие для всех приложений платформы, их даёт ядро. Приложение не повторяет их у себя, а:

  • подключает готовые разделы опциями createAdmin (пользователи, аудит, резервные копии, задачи, о системе и остальные из таблицы ниже);
  • добавляет только то, что есть лишь у него: свои разделы через sections, свои тексты через texts, свои цвета и логотип через оформление;
  • оставляет в своём меню предметные страницы и одну ссылку «Администрирование».

Пользователи, журнал аудита, состояние системы, миграции, резервные копии и расписание задач находятся только в администрировании. Дублировать их страницами приложения не нужно: так у каждого приложения был бы свой вариант одного и того же, а исправление пришлось бы вносить в каждое. Нужна возможность, которой нет в разделе, — её добавляют в ядро (опцией раздела), а не в приложение. Страницы администрирования узнаются без взгляда на адрес: под логотипом стоит метка «Администрирование».

Общий вид страниц

Длинные списки (пользователи, аудит, баны, сессии, инциденты, алерты, очередь почты) выводятся по 25 строк с кнопками «Назад» и «Вперёд» и показывают «Показано N из M». Кнопка «Развернуть» превращает список в один длинный: следующие страницы подгружаются сами при прокрутке. Без JavaScript работают обычные ссылки. Правило для своих разделов: любой список, который может вырасти, выводится через admin/paging.js (pageParams, pagerFor, у тела таблицы data-paged="имя"); источник данных принимает limit, offset и отдаёт общее число.

Даты в таблицах выводятся элементом <time datetime="…">: без JavaScript виден UTC (27.10.2026 15:57:40 UTC, у английского языка 2026-10-27 15:57:40 UTC), а скрипт оболочки показывает их в часовом поясе браузера (27.10.2026 20:57:40), точное UTC-значение остаётся во всплывающей подсказке. Для своих страниц: ui.timeHtml(значение, locale) и ui.TIME_SCRIPT (оболочка подключает скрипт сама). Пустая таблица показывает подсказку, что делать дальше. Широкие таблицы прокручиваются внутри карточки на узком экране. Заголовки таблиц пишутся обычным регистром. Целочисленные данные на графиках имеют целые отметки оси.

Группы меню. Меню разбито на группы: «Пользователи» сразу под «Обзором», затем «Безопасность» (аудит, баны и сессии, парольная политика, инциденты, реестр обработки, политики), «Система» (алерты, логи, конфигурация, о системе), «Обслуживание» (резервные копии, режим обслуживания, объявление, задачи, почта, рассылка) и «Прочее» (оформление и разделы приложения из sections). Пустые группы не показываются.

Поиск по разделам. Над меню на каждой странице есть поле «Найти раздел…» (/admin/search?q=, при controlPath ищет и в области управления). Он ищет разделы, а не значения настроек: по названию и по словам, под которыми раздел обычно ищут («пароль», «копия», «логотип», «утечка», «503»; русские и английские слова заданы для каждого раздела в src/admin/search.js). Регистр и «ё» не важны, найденный раздел должен содержать все слова запроса, найденные по названию идут первыми. Показываются только включённые разделы; разделы приложения из sections ищутся по названию. Введённый текст выводится экранированным.

Область управления приложением. Опция controlPath (например '/control') выносит шесть разделов «Обслуживания» в отдельную область со своим меню, своей меткой «Управление приложением» и своей начальной страницей: /control/backups, /control/maintenance, /control/announcement, /control/tasks, /control/mail, /control/broadcast. В меню администрирования тогда остаётся ссылка «Управление приложением →», а в меню управления — «Администрирование →». Оповещения о режиме обслуживания, упавших задачах и зависшей почте показываются на «Обзоре» администрирования и на начальной странице управления и ведут в область управления. Остальные разделы остаются под /admin. Без controlPath (по умолчанию) всё лежит под basePath, как и раньше; в таблице ниже для шести разделов подставьте controlPath вместо /admin, если он задан. Доступ в обе области даёт один и тот же permission. В examples/workshop включено controlPath: '/control'.

Раздел без своей опции в меню не показывается. Первым пунктом меню идёт ссылка «← В приложение» (адрес задаёт appUrl, по умолчанию /ui).

Шапка каждой страницы администрирования устроена одинаково: под логотипом метка «Администрирование» (чтобы раздел узнавался без взгляда на адрес), логотип и название ведут в приложение, имя пользователя — в настройки учётной записи (accountUrl), рядом кнопка «Выйти». В настройках учётной записи кнопка выхода продублирована отдельным пунктом.

Требования к приложению

Что должно быть смонтировано до createAdmin(...).mount(...) (в таком порядке, как в examples/workshop/src/server.js):

  1. Идентификатор запроса и локаль: ui.localeMiddleware(), иначе админка выберет язык по умолчанию.
  2. Сессии: http.createSessionMiddleware, затем http.attachUser(); пользователь должен иметь permissions с admin.access.
  3. CSRF-защита и cookie-parser (все изменяющие запросы админки — POST, проверка происхождения запроса включается в http).
  4. CSP с nonce (res.locals.cspNonce): страницы админки подставляют его в свои скрипты.
  5. Для «Оформления»: каталог загрузок uploadsDir, пакет multer (peer-зависимость ядра для загрузки файлов), sharp для перекодирования растров, jsdom и dompurify для очистки SVG.
  6. Для «Безопасности»: security.createBans(db) и app.use(bans.middleware()) после attachUser.
  7. Для «Обзора» с графиками: admin.createMetrics(db) и app.use(metrics.middleware()) как можно раньше; очистку старых данных запускайте задачей планировщика (metrics.purge()). Клик по графику (или кнопка ⤢ в его заголовке) открывает график крупно; при наведении на столбец или точку показывается метка и значение.
  8. Каждое приложение само назначает право admin.access роли администратора. В workshop: permissionsForRole в examples/workshop/src/routes.js.

Функциональность по умолчанию

Обзор

Плитки: время работы, память, размер базы, число пользователей, сессий и записей аудита, версия Node.js, PID процесса, куча Node, нагрузка CPU за минуту (на Windows плитки нет, там показатель всегда ноль), свободная и общая память системы, свободное место на диске с базой; «Миграции» только пока есть ожидающие применения (опция migrations). При наличии metrics — графики с выбором периода «24 часа / 7 дней / 30 дней» (?period=24h|7d|30d, время UTC; за 7 дней точка — 6 часов, за 30 дней — сутки): запросы, ошибки клиента (4xx), ошибки сервера (5xx), среднее время ответа, успешные и неудачные входы (по журналу аудита), а также уровни, которые панель сама замеряет раз в 5 минут: активные сессии, размер базы и очередь почты (последние два — когда есть файл базы и очередь). Часы без данных остаются пустыми, а не нулевыми. Серверный SVG, без библиотек; данные хранятся 35 дней (retentionDays). Свои уровни пишет metrics.set(имя, значение), свои счётчики — metrics.inc(имя); ряд для графика даёт metrics.periodSeries(имя, период, { mode: 'sum'|'last' }), среднее — metrics.periodAverage(суммы, число, период).

Аудит

Таблица записей с фильтрами (кто, действие, объект и его номер, запрос, результат, даты; кнопки «Сегодня» и «7 дней»); номер записи ведёт на карточку события /admin/audit/event/<номер>: все поля, подробности (meta) таблицей «поле, значение», хеши и переходы «все события этого запроса», «история объекта», «действия этого пользователя»; постраничность «Дальше →», проверка цепочки хешей («Проверить цепочку»). Две вкладки: «Все события» и «Входы» (?view=logins) — только события auth.login*: вход, второй фактор, код восстановления, блокировки; фильтры и экспорт работают в обеих. Экспорт: CSV (GET /admin/audit.csv, защита от формул в ячейках) и JSON (GET /admin/audit.json), оба по текущему фильтру, потоком и без обрезания, с подробностями (meta) и хешами (hash, prevHash). Каждый экспорт пишет в аудит admin.audit.export с числом строк. Те же записи, включая входы, уходят в общий пул журналов потоком audit (logs.mirrorAuditToLogs, режим logging.auditMirror: minimal — без имён и адресов, full — полностью, off).

Кто был объектом события. Для событий над пользователем журнал сам сохраняет его логин на момент события (в meta.username, как псевдоним: при стирании персональных данных он превращается в «[erased]»). В таблице и карточке рядом с user#5 показано (alice), поэтому запись читается и после переименования или удаления учётной записи. Для других объектов приложение передаёт entityLabel в audit.log (название на этот момент, попадает в meta.target; персональных данных туда не класть).

Роль «аудитор». Если приложение передало в createAdmin параметр auditAccess: { read: 'audit.read', export: 'audit.export' }, пользователь с правом audit.read (без admin.access) видит только раздел «Аудит»: журнал, сводку, карточку события и живую ленту. Меню у него состоит из ссылки «в приложение» и «Аудит»; остальные разделы администрирования отвечают ему «нет доступа». Кнопки выгрузки CSV/JSON и сами адреса /admin/audit.csv и /admin/audit.json требуют отдельного права audit.export. Владельцы admin.access по-прежнему могут всё. Без параметра auditAccess аудит доступен только администраторам. В примере workshop роль auditor получает оба права: npm run cli -- user create имя --role auditor.

Безопасность

Баны (IP или пользователь; срок вида 30m, 2h, 7d, пусто — бессрочно), снятие бана, список активных сессий с принудительным завершением. Нельзя забанить себя: ни свой логин, ни свой текущий IP. Маршруты: POST /admin/security/bans, POST /admin/security/bans/:id/lift, POST /admin/security/sessions/:id/revoke. В аудит: admin.session.revoke и записи самих банов.

Пользователи

Поиск, список, блокировка и разблокировка (POST /admin/users/:id/disable|enable). Нельзя заблокировать себя; при блокировке сессии пользователя завершаются. С userManagement у каждой чужой записи есть кнопка «Действия», она открывает окно с формами: логин и e-mail (/profile), роль (/role), сброс пароля (/reset: временный пароль, который показывается один раз на странице-результате и нигде не хранится, или одноразовая ссылка на почту пользователя), снятие блокировки входа (/unlock, если приложение передало userManagement.onUnlock: сбрасывает счётчики неудачных попыток входа этой записи в работающем приложении, без перезапуска), выход из всех сессий с необязательным требованием сменить пароль (/logout), обезличивание или полное удаление (/remove): перед выполнением открывается предупреждение, а кнопка подтверждения активируется через 5 секунд (без JavaScript вместо окна работает галочка подтверждения). Обезличенная запись показывается как «обезличен» и больше не редактируется и форма создания (/create, временный пароль показывается один раз). К своей записи действия не применяются; последнего активного администратора понизить, отключить или удалить нельзя; при смене прав и сбросе пароля сессии пользователя завершаются. В аудит: admin.user.create, admin.user.update, admin.user.reset_password, admin.user.force_logout, admin.user.unlock, admin.user.delete, admin.user.disable, admin.user.enable; пароли и токены туда не попадают. Те же правила действуют в командах user ... (CLI).

Карточка и «давно не входили». Имя пользователя в списке — ссылка на карточку (GET /admin/users/:id): даты последнего входа, последней активности и смены пароля, второй фактор, сессии (без идентификаторов), известные устройства (браузер и система, первый IP) и последние события с переходом в журнал. Отчёт GET /admin/users/inactive?days=90 показывает активные учётные записи без входов и активности за N дней (или ни разу не входившие и созданные раньше) и позволяет отключить их всех одним действием (stepUp; сессии закрываются, пользователь получает письмо, последний администратор и вы пропускаются; в журнале admin.user.disable с причиной inactive_<N>d и итог admin.user.disable_inactive). Источники: успешные входы в журнале (при сроке хранения журнала старые входы исчезают), сессии, устройства.

Второй фактор и письма пользователю. В действиях над учётной записью (при userManagement): «Сбросить второй фактор» (POST /admin/users/:id/reset-mfa: удаляет аутентификатор и коды восстановления, завершает все сессии; пароль остаётся) и «Выпустить новые коды восстановления» (POST /admin/users/:id/recovery-codes: прежний набор заменяется, новые коды показываются один раз и нигде не пишутся, нужен подтверждённый аутентификатор). Оба идут через stepUp, нельзя на себя, пишутся в журнал (admin.user.reset_mfa, admin.user.recovery_codes). О каждом действии администратора над учётной записью (отключение и включение, смена роли, временный пароль, завершение сессий, сброс второго фактора, новые коды) пользователю уходит письмо, если у него есть адрес и почта включена; письмо не содержит ни пароля, ни кодов, а его сбой не мешает действию (в журнале notified: true/false).

Парольная политика

Профиль («NIST» или «ФСТЭК»; профиль «ФСТЭК» — ориентир по методическому документу ФСТЭК России от 12.04.2026, мера ИАФ.3, сверяйте с документом), минимальная длина, отдельная длина для администраторов и число обязательных классов символов (POST /admin/password-policy); «Вернуть значения из настроек» стирает сохранённое. Правила хранятся в базе (app_settings, ключ password_policy) и действуют сразу в каждом процессе. Ниже две кнопки «Потребовать смену пароля»: у всех или только у администраторов (роль из userManagement.adminRole); выбранные разлогиниваются и при следующем входе задают новый пароль, ваша учётная запись не затрагивается. Аудит: admin.passwordpolicy.set, admin.passwordpolicy.reset, admin.passwordpolicy.require_change. Включается опцией passwordPolicy: auth.createPasswordPolicy({ db, config: appConfig.auth.passwordPolicy, appName, blocklistFile: appConfig.auth.passwordBlocklistFile }). Срок действия пароля по умолчанию не ограничен (0 дней); число дней задаётся там же, по истечении срока вход ведёт на форму смены пароля. Запрет повторов помнит от 0 до 24 прошлых паролей. Файл утёкших паролей задаётся в конфигурации (auth.passwordBlocklistFile, опция blocklistFile у createPasswordPolicy).

Реестр обработки

Включается опцией processingRegistry (функция, возвращающая реестр; собирается при каждом открытии). Таблица: что обрабатывается, цель, данные, основание, срок хранения, удаление; язык — языка интерфейса. Над таблицей перечислены модули без цели или основания обработки. Скачивание GET /admin/registry.md, .csv, .json (в CSV значения, похожие на формулы, экранируются). В аудит: admin.registry.export. Тот же реестр даёт команда privacy registry.

Инциденты

Журнал инцидентов безопасности (/admin/incidents, нужна опция incidents). Инцидент: название, описание, тяжесть (низкая, средняя, высокая), признак «затронуты персональные данные», время обнаружения (по умолчанию сейчас), статус (открыт, регулятор уведомлён, закрыт), даты первичного и уточняющего уведомлений, принятые меры. Если персональные данные затронуты, от момента обнаружения считаются два срока: первичное уведомление (24 часа) и уточнённые сведения (72 часа); просроченные подсвечиваются. Сроки взяты из createIncidentRegister(db, { firstNoticeHours, detailsHours }); действующие требования закона и порядок уведомления сверьте с юристом. Журнал только фиксирует и напоминает, ничего никому не отправляет. Маршруты: POST /admin/incidents/declare, POST /admin/incidents/:id. В аудит: privacy.incident.declare, privacy.incident.update (без текста описания и мер). Важность в списке показана цветным значком (высокая красный, средняя янтарный, низкая синий). На «Обзоре» пока есть незакрытые инциденты, показывается оповещение со ссылкой сюда: красное, если среди них есть высокой важности или просрочен срок уведомления, иначе янтарное.

Резервные копии

Список копий из всех мест назначения и кнопка «Запустить» (POST /admin/backups/run). Восстановление из копии из админки намеренно недоступно: только из CLI. В аудит: admin.backup.run.

Вверху раздела карточка автобэкапа: переключатель «Делать копию каждый день», время суток (время сервера), следующий запуск, срок хранения и места назначения. Форма (POST /admin/backups/schedule) пишет в app_settings (schedule:backup); пока администратор ничего не менял, действуют backup.enabled и backup.schedule из конфигурации. Нужны backups.schedule и backups.info. В аудит: admin.backup.schedule.

При опции backups.verify у каждой копии кнопка «Проверить» (POST /admin/backups/verify): открывается архив и проверяется база (с ключом шифрования, если копия зашифрована). Принимается только путь из списка копий, любой другой отклоняется. В аудит: admin.backup.verify.

Алерты

Последние 200 алертов, новые сверху: время, важность (инфо, предупреждение, критично), событие с пояснением, число повторов и признак отправленного письма (при сбое письма видно код ошибки). Модуль и источники — в разделе «Алерты» главы «Эксплуатация».

Логи

О системе

Одна страница из трёх блоков:

  • Health: статус, база, время работы приложения (about.health).
  • Диагностика (doctor): проверки по категориям с итогом OK/предупреждения/ошибки; запускается кнопкой (POST /admin/about/doctor), результат кэшируется на странице (about.doctor). В аудит: admin.about.doctor. Ниже кнопки — переключатель автоматического запуска (about.doctorSchedule): флажок «Запускать автоматически каждый день» и время (по времени сервера); показано время следующего запуска. Если в конфигурации задан не ежедневный cron, он показан рядом и сохраняется, пока время не задано. Сбои автоматической проверки превращаются в алерты (см. «Эксплуатация»).

Политики

Режим обслуживания

Включается опцией maintenance (maintenance.createMaintenance({ db })). Пока режим включён, все, кроме администраторов (право admin.access), получают страницу «Ведутся работы» со статусом 503 и заголовком Retry-After; клиенты API получают JSON { error: 'MAINTENANCE' }. Открытыми остаются /health, /login*, /logout, /branding/logo и /policy, чтобы администратор мог войти и выключить режим. В форме задаются сообщение (до 500 символов) и ожидаемое окончание; окончание только показывается посетителям и задаёт Retry-After, режим само не выключает. Состояние хранится в базе (app_settings), поэтому переживает перезапуск и общее для всех процессов; процесс перечитывает его не реже раза в 2 секунды. В аудит: admin.maintenance.enable, admin.maintenance.disable. Middleware подключается после сессий: app.use(maintenance.middleware({ vendorIdentity, brand, bodyEnd })).

Объявление

Включается опцией announcement (announcement.createAnnouncement({ db })). Форма: текст (до 300 символов), важность («Информация», «Предупреждение», «Важно (нельзя скрыть)») и необязательное время окончания по UTC; кнопка «Снять объявление» убирает его сразу. Над формой показано, как баннер выглядит сейчас. Баннер виден над страницами админки и, если приложение передало его оболочке, над страницами приложения (см. «Модули ядра», announcement). В аудит: admin.announcement.set, admin.announcement.clear.

Задачи

Расписание показано cron и словами («каждый день в 03:00», «каждую неделю: в воскресенье, 04:30»; незнакомые формы разбираются по полям). Опция taskSchedules включает форму «Изменить расписание»: пять полей cron либо время суток, действует сразу, хранится в app_settings (task_schedule:<имя>) и переживает перезапуск; «Вернуть исходное» возвращает расписание, с которым задача зарегистрирована. В аудит: admin.task.schedule, admin.task.schedule_reset. Задачи с собственным переключателем (backup, alerts-doctor) настраиваются в «Резервных копиях» и «О системе»; опция managedTasks ведёт туда.

Включается опцией scheduler: { listJobs, runNow } (обычно методы scheduler.createScheduler()). Таблица: имя, расписание, последний запуск, длительность, результат, ошибка. Кнопка «Запустить сейчас» отправляет POST /admin/tasks/:name/run (защита stepUp, как у других изменяющих действий) и пишет в аудит admin.task.run. Планировщик создаётся после админки, поэтому приложение передаёт ссылку через держатель: const schedulerHolder = { current: null }, в createAdmin — scheduler: { listJobs: () => schedulerHolder.current.listJobs(), runNow: n => schedulerHolder.current.runNow(n) }, после создания планировщика — schedulerHolder.current = scheduler. Пример: examples/workshop/src/server.js. Если последний запуск задачи завершился ошибкой, на «Обзоре» появляется предупреждение со ссылкой на раздел.

Рассылка

Служебное письмо пользователям, например о плановых работах (/admin/broadcast, появляется вместе с разделом «Почта», когда в опции mail передан service). Выбираются получатели (все или одна роль; действующие учётные записи с адресом e-mail), язык письма, тема (до 150 знаков, одна строка) и текст (до 5000 знаков). Каждому уходит отдельное письмо, адреса других получателей не видны; письма идут через очередь почты с повторами и подчиняются её лимиту на адрес. Кнопка «Отправить тест мне» отправляет письмо только вам; «Отправить всем» просит подтверждение и показывает, сколько писем поставлено в очередь, пропущено по лимиту и не удалось. За один раз не больше 5000 получателей. Почта должна быть включена (email.enabled). В аудит: admin.broadcast.send (число получателей, итоги, роль, язык и тема, без текста письма), admin.broadcast.test. Рассылка по расписанию не поддерживается: письмо уходит сразу; для предупреждения на экране есть «Объявление».

Почта

Включается опцией mail: { queue, service }. Показывает счётчики очереди (ожидают, отправлены, с ошибкой) из queue.stats() и последние письма из queue.list(): получатель с маскировкой (a***@example.com), тема, статус, число попыток, ошибка. Тексты писем не показываются и не хранятся в отображении. Раздел только для чтения; повторная отправка делается средствами очереди. Письма с ошибкой дают предупреждение на «Обзоре». Форма «Проверка отправки» (при mail.service.sendTest, то есть с включённой почтой) отправляет одно тестовое письмо на указанный адрес сразу, минуя очередь, и показывает настоящий результат: «отправлено» или код ошибки SMTP (текст ответа сервера и пароли не показываются). Нужно повторное подтверждение пароля. В аудит: admin.mail.test (адрес сокращён). Если у очереди есть cancel, у ожидающего письма появляется кнопка «Отменить», а над таблицей — «Очистить завершённые» (старше суток); действия идут через stepUp и попадают в журнал. Повтор неудавшихся недоступен: содержимое письма стирается сразу.

Конфигурация

Включается опцией config (объект appConfig). Показывает плоский список ключей и значений только для чтения. Значения секретов скрываются по имени ключа (secret, password, token, apikey, privatekey, encryptionkey, credential, authorization, key); имена вроде keyFile, keyPath, keyLength, maxKeys не скрываются. Скрываются только непустые строки; ссылки вида env:NAME остаются видимыми, так как секрета не содержат. Править конфигурацию здесь нельзя: источник — файл и переменные окружения (см. «Конфигурация»). Как добавить свой раздел

Передайте пункт меню в sections и смонтируйте собственные маршруты с теми же защитами (guard из mount):

const admin = createAdmin({ db, sections: [{ path: '/admin/reports', label: 'Отчёты' }] });
const { guard, page } = admin.mount(app, { requireAuth, requirePermission });
app.get('/admin/reports', ...guard, (req, res) => page(req, res, { active: '/admin/reports', title: 'Отчёты', bodyHtml: '<p>…</p>' }));

Для изменяющих запросов добавляйте ...stepUp после ...guard, Cache-Control: no-store страница ставит сама. Ссылки приложения в меню оболочки приложения передаются как extraNav (см. Переводы): в workshop пункты «Система» и «Администрирование» собраны в APP_NAV (examples/workshop/src/routes.js).

Безопасность раздела

  • Вход: действующая сессия и право admin.access; без сессии — вход, без права — 403 с брендированной страницей.
  • Изменяющие действия — только POST; CSRF проверяется общим middleware http.
  • Опасные действия подтверждаются диалогом (data-confirm); для повторной проверки MFA передайте stepUp.
  • Каждое действие пишется в аудит с актором, IP и идентификатором запроса.
  • Весь вывод экранируется; скрипты идут с nonce; Cache-Control: no-store на страницах.
  • Загрузки логотипа проходят files.acceptUpload: тип по содержимому, очистка SVG, обязательное перекодирование.

Что требует внимания

  • Забыли bans.middleware() — баны создаются, но не действуют.
  • Забыли attachUser() или права admin.access у роли — раздел отвечает 401/403.
  • Без metrics.middleware() на «Обзоре» нет графиков (плитки остаются).
  • «О системе»: about.packageJsonPath должен указывать на package.json приложения; для монорепозитория nodeModulesDir принимает массив каталогов. Без доступа в интернет проверка обновлений вернёт «нет данных».
  • Если приложение называется иначе, чем в fallbackName, меню покажет fallbackName, пока администратор не зададит название.

Переводы

Выбор языка

ui.localeMiddleware({ fallback = 'ru', secure = false }) задаёт req.locale. Порядок:

  1. параметр ?lang=ru|en в любом адресе. Выбор запоминается в cookie das_lang на год (SameSite=Lax, Path=/, Secure при https);
  2. cookie das_lang;
  3. заголовок Accept-Language (первый из ru/en);
  4. fallback.

Cookie-parser для этого не нужен. Подключайте middleware сразу после идентификатора запроса, до всего, что рендерит страницы (в workshop: src/server.js, app.use(uiModule.localeMiddleware())).

import { ui } from '@das-forge/core';
app.use(ui.localeMiddleware({ fallback: 'ru', secure: true }));

Оболочка, страницы ошибок, политики и админка читают req.locale сами. Атрибут lang документа совпадает с языком содержимого.

Переключатель языка

ui.langSwitchHtml(locale, { param = 'lang', href }) возвращает одну кнопку с флагом текущего языка. Нажатие переключает на другой. Работает без JavaScript: это обычная ссылка с ?lang=. Оболочка (renderAppShell) и страницы ошибок уже содержат кнопку; на своих страницах вне оболочки вставляйте её сами:

`<div class="bar">${ui.langSwitchHtml(loc)}${ui.themeToggleHtml(loc)}</div>`

Пример: examples/workshop/src/pages.js, функция pageShell.

Заменяются только указанные ключи, остальные остаются встроенными. Для всего процесса сразу (админка, страницы ошибок, страницы политик, письма): i18n.setTextOverrides({ errors: { ru: { 404: { title: 'Нет такой страницы' } } }, email: { en: { alert: (d) => ({ subject, lead, body }) } } }) — у ошибок заменяются отдельные поля кода, у писем целиком сценарий (функция); createAdmin({ texts }) сильнее общих замен. Подписи и тексты приложения: контракт Module

Модуль приложения объявляет translations: { ru: {...}, en: {...} } и navigation: [{ path, label, permission }], где label — ключ из словаря. Реестр собирает словари всех модулей; два модуля не могут задать один ключ разными значениями (ошибка при регистрации).

// examples/workshop/src/modules/reporting-module.js (фрагмент)
translations: { ru: { reporting: 'Отчёты' }, en: { reporting: 'Reports' } },
navigation: [{ path: '/ui/reporting', label: 'reporting', permission: 'read:basic' }],

Ссылки приложения вне модулей передаются в оболочку как extraNav; подпись может быть объектом:

{ path: '/ui/reports', label: { ru: 'Отчёты', en: 'Reports' }, permission: 'read:finance' }

Элемент с permission скрыт, если права нет (по умолчанию доступ закрыт). Для строк вне оболочки есть ui.translate(moduleRegistry, locale, key).

Модуль i18n (на i18next)

Для всех остальных текстов приложения ядро даёт @das-forge/core/i18n на i18next: пространства имён, подстановки с экранированием HTML, русские формы множественного числа через Intl.PluralRules, запасной язык. Библиотека подгружается при первом создании, при импорте ядра не загружается.

import { i18n } from '@das-forge/core';

const t18 = await i18n.createI18n({
  locales: ['ru', 'en'],
  defaultLocale: 'ru',
  namespaces: {
    app: {
      ru: { hello: 'Привет, {{name}}', nav: { home: 'Главная' } },
      en: { hello: 'Hello, {{name}}', nav: { home: 'Home' } },
    },
  },
});

t18.t('en', 'nav.home');                       // 'Home'
t18.t('de', 'nav.home');                       // язык по умолчанию: 'Главная'
t18.t('en', 'hello', { name: '<img onerror=x>' }); // 'Hello, &lt;img onerror=x&gt;'
const t = t18.translator('en', 'app');         // переводчик, привязанный к языку

Подстановки экранируются (escapeValue: true): значение из базы нельзя превратить в разметку.

Тест на полноту

Чтобы непереведённая строка не прошла незамеченной, добавьте в тесты приложения проверку:

expect(t18.missingKeys()).toEqual([]);

Примеры, прогоняемые тестами: packages/core/test/i18n.test.js.

Как сейчас переведён workshop

Все страницы workshop берут тексты из каталога (examples/workshop/src/messages.js: i18next, пространство workshop, ключи вида login.title, группы по страницам — login, forced, forgot, reset, account, audit, system, realtime, users, home, reports). Страница просит слова по ключу, тексты, нужные браузерному скрипту, передаются в него как JSON (scriptTexts), подстановки в диалогах делает небольшая функция fmt в браузере. Заголовки окон и пункты меню (APP_NAV) тоже двуязычные. Подмены готового HTML словарём нет: строка без ключа не может «остаться английской молча», а полноту проверяет тест. Тексты ошибок, которые возвращает JSON API (data.message), остаются на языке сервера: перевод ответов API workshop не делает.

Для нового приложения: тексты через каталог (req.t('ключ') или, если страницы строятся синхронно, i18n.createI18nSync({ i18next, namespaces }) и i18n.translator(locale, 'пространство')), оба языка в одном пространстве имён, missingKeys() в тесте. Образец — messages.js и test/messages.test.js в workshop.

Правила для новых текстов

  1. Каждый текст сразу на двух языках. Один язык без второго — ошибка.
  2. Не склеивайте фразы из кусков: порядок слов в языках разный. Один ключ — одна фраза с подстановкой.
  3. Подстановки — только через {{имя}}: так значение экранируется.
  4. Заголовок страницы (<title>), aria-label, подсказки и сообщения об ошибках переводятся так же, как текст страницы.
  5. Числа и даты форматируйте через Intl с языком запроса, а не вручную.
  6. Тексты внутри клиентских скриптов передавайте с сервера (атрибут data-* или JSON), а не пишите английскими строками в коде скрипта.
  7. Текст ошибки API — код ошибки (INVALID_UPLOAD), а человекочитаемая подпись берётся из словаря по коду.

Как добавить третий язык

  1. Добавить код в locales у createI18n и набор ключей во все пространства.
  2. Расширить localeMiddleware: сейчас он принимает только ru и en (регулярное выражение cookie и проверка ?lang= в ui/locale.js).
  3. Добавить словари в ERROR_CATALOG, словари админки и DEFAULT_TEXTS политик; таблица policy_texts ограничивает язык значениями ru и en (ограничение CHECK), понадобится миграция.
  4. Добавить флаг в ui/lang-switch.js.

Пока эти места в ядре жёстко задают два языка: третий язык требует правок ядра, а не только приложения.

Переключатель темы

ui.themeToggleHtml(locale) — одна кнопка-иконка с двумя состояниями: светлая и тёмная. Клик переключает между ними; пока выбор не сделан, тема следует системе, и кнопка показывает её. Вернуть режим «как в системе» можно на странице «Аккаунт» (блок «Интерфейс»). Выбор хранится в localStorage под ключом adm-theme (если хранилище недоступно, кнопка работает до перезагрузки).

Скрипт переключателя (THEME_SCRIPT) подключает ui.themeHead(...). Поэтому любая страница, которая вызывает themeHead, получает и стиль, и скрипт; отдельно подключать скрипт нельзя, иначе клик сработает дважды. Страницы под строгим CSP получают скрипт с nonce: передайте nonce: res.locals.cspNonce.

// страница вне оболочки (examples/workshop/src/pages.js, pageShell)
`<head>${ui.themeHead({ ...brand.theme, nonce })}</head>
 <body><div class="bar">${ui.langSwitchHtml(loc)}${ui.themeToggleHtml(loc)}</div>…`

Как приложение подставляет свою палитру

Параметр theme принимают createAdmin(...), renderAppShell(...), renderErrorPage(...) и обработчики ошибок:

theme: {
  tokens:     { accent: '#e94560' },        // светлая схема и общие значения
  darkTokens: { bg: '#0f1117' },            // переопределения только для тёмной
  cssUrl:     '/css/admin-extra.css',       // необязательно: шрифты и точечные правила, грузится после базового CSS
}

Значения токенов проверяются: допускаются цвета (#rrggbb, rgb(), rgba()), var(--своя) и значения из букв, цифр и символов # ( ) . , % / _ ' " + -. Точка с запятой, фигурные скобки и разметка запрещены: тема — настройка, но значение, которое выходит за рамки объявления, было бы внедрением CSS. Имя токена: строчные буквы, цифры, дефис, до 40 символов. Неверное значение вызывает TypeError при построении страницы.

Два способа сопоставления с палитрой приложения:

  1. Литеральные значения (рекомендуется): скопируйте цвета из CSS приложения. Они следуют переключателю темы ядра и не зависят от загрузки CSS приложения.
  2. var(--своя) и cssUrl: страницы ядра используют живые переменные приложения. Тогда тёмная схема определяется механизмом приложения, а не переключателем ядра.

Цвета приложения не хранятся в ядре. Контраст проверяйте сами: текст на поверхности не ниже 4.5:1, приглушённый не ниже 3:1, текст кнопки на акценте не ниже 3:1 (формула WCAG; для var() и rgba() проверка вручную).

Название, логотип и акцент: «Оформление»

В карточке «Цвет акцента» над выбором цвета стоит предпросмотр: два макета (светлая и тёмная тема) — шапка с логотипом и названием, вкладки с активной, три карточки с акцентной полосой и кнопка. Он обновляется сразу при вводе названия, выборе цвета и выборе файла логотипа, до сохранения; выбранный файл читается в браузере (FileReader) и никуда не отправляется, пока не нажата «Загрузить».

Раздел админ-панели /admin/appearance меняет то, что видит пользователь в меню и на странице входа. Включается опцией:

adminModule.createAdmin({
  db,
  appearance: { uploadsDir: ctx.uploadsDir, fallbackName: 'Workshop' },
});

Подробности раздела — в Администрировании. Устройство:

  • Хранение. Настройки лежат в таблице app_settings под ключом company_branding (схема CompanyBrandingSchema): name, logoFile, logoFileDark, accent, accentDark, а также ссылочные logoUrl/logoUrlDark. Файлы логотипов лежат в uploads/branding/, отдельно от загрузок приложения.
  • Применение. branding.themeWithBranding(db, baseTheme) добавляет акцент поверх темы приложения (светлый в tokens, тёмный в darkTokens), а цвет текста на кнопке вычисляет по контрасту (branding.readableOn). branding.brandingHtml(db, { fallbackName }) строит блок «логотип + название»; если логотип один, он используется в обеих темах, а название экранируется. В workshop оба вызываются на каждый запрос: examples/workshop/src/routes.js, appShell и brandOf.
  • Выдача логотипа. GET /branding/logo/light и GET /branding/logo/dark публичны: страница входа показывает логотип до входа. Админка монтирует маршрут сама. Ответ идёт с защитными заголовками выдачи файлов, Cache-Control: public, max-age=0, must-revalidate; в адресе картинки стоит ?v=<время изменения>.
  • Загрузка. PNG, JPG или SVG до 2 МБ через files.acceptUpload (тип по содержимому, очистка SVG, обязательное перекодирование растровых картинок). Старый файл удаляется после успешной записи.
  • Сброс. Возвращает название и акценты по умолчанию; логотипы убираются отдельной кнопкой.

Логотип производителя и страницы ошибок

defineVendorIdentity({ name, repoUrl, assetsDir }) задаёт неизменяемую «личность» приложения: она лежит в файлах репозитория, поэтому никакое действие в интерфейсе не изменит, что страница «О системе» называет продуктом. Логотипы ищутся в assetsDir (обычно assets/brand) в порядке: logo.svg, logo.png, logo.jpg, logo.jpeg для светлой темы и logo-dark.* для тёмной. Если тёмного варианта нет, берётся светлый. Предпочитайте SVG.

Страницы ошибок и страница обслуживания (http.errorResponder, notFoundHandler, errorPageHandler, maintenance.middleware) и страницы входа показывают тот же блок бренда, что и оболочка. Блок строит branding.brandBlockHtml(db, vendorIdentity): название и логотип из «Оформления», а если они не заданы, название и логотип производителя из defineVendorIdentity. Приложение передаёт его функцией brand: () => branding.brandBlockHtml(db, vendorIdentity); без brand на страницах ошибок стоит логотип производителя. Внизу каждой страницы стоит маленькая строка «Powered by DAS-Forge» с логотипом ядра; её рисует ui.poweredByHtml(locale), и отключить её настройками нельзя.

Что требует внимания

  • Не передавайте в tokens значения из пользовательского ввода. Проверка спасает от выхода из объявления, но не от нечитаемой темы.
  • Значение токена — цвет, размер или шрифт, а не ресурс: url(…), image-set(…), expression(…) и @import отклоняются. cssUrl — путь на этом сервере или адрес https://…; //хост, http:, data: и javascript: отклоняются.
  • Если у приложения свой CSS (cssUrl), тёмная схема может расходиться с переключателем ядра; проверяйте обе.
  • Страницы вне оболочки (вход, смена пароля) не получают тему автоматически: вызывайте themeHead сами и передавайте им тему из themeWithBranding.
  • Акценты администратора не проходят проверку контраста: цвет текста на кнопке подбирается автоматически, но светлый акцент на светлом фоне ссылок может читаться плохо.

Как вызвать команды, когда сервер уже запущен

Окно консоли, где идёт npm start, занято сервером: пока он работает, команды в него не вводятся. Так и задумано, закрывать его не нужно.

  1. Оставьте окно с сервером как есть.
  2. Откройте второе окно консоли (Windows: Win+R, cmd, Enter).
  3. Перейдите в папку приложения: cd C:\путь\до\das-forge-core\examples\workshop.
  4. Запускайте команды: npm run cli -- help, npm run cli -- maintenance status, npm run cli -- sessions list.

Два дефиса -- обязательны: они отделяют параметры npm от параметров приложения (без них --status и подобные флаги перехватывает сам npm). Без npm то же самое: node bin/app.js <команда>.

Оба окна работают с одной базой, поэтому изменения вроде maintenance on или announcement set запущенный сервер подхватывает сам через пару секунд. Исключение — backup restore: он подменяет файл базы, перед ним сервер остановите (Ctrl+C в его окне).

Docker

В корне — Dockerfile и docker-compose.yml эталонного приложения.

  • Образ на node:26-bookworm-slim, процесс под пользователем node, tini как точка входа.
  • Все данные — в examples/workshop/data: монтируйте один том туда.
  • DAS_HTTPS_MODE=reverse-proxy, DAS_TRUST_PROXY=true: контейнер говорит по HTTP в закрытой сети, прокси обязан ставить X-Forwarded-Proto и X-Forwarded-For.
  • HEALTHCHECK опрашивает /health; при остановке он сразу отвечает 503, и оркестратор перестаёт слать трафик.
  • Секрет сессии — через DAS_SESSION_SECRET_FILE (Docker secret), не в образе.

Одной командой из любой оболочки (скрипты scripts/docker-start.mjs и scripts/docker-test.mjs, без bash и $PWD):

npm run docker:start     # создаёт secrets/session_secret.txt (если нет), собирает, запускает, ждёт /health
npm run docker:logs      # лог контейнера: в нём баннер с логином и временным паролем первого администратора
npm run docker:stop      # остановить и удалить контейнер (том с данными остаётся)
npm run docker:test      # все тесты в чистом Linux-контейнере; --core — только ядро; --image <имя> — другой образ

После docker:start приложение отвечает на http://127.0.0.1:9002 (режим reverse-proxy: в production перед ним ваш TLS-прокси; открыть для сети без прокси — раздел «Доступ из локальной сети»). Свой администратор вместо первого: docker compose exec workshop node bin/app.js user create-admin. Секрет сессии скрипт создаёт один раз (48 случайных символов, права только владельцу, в git не попадает); существующий файл не трогает.

То же вручную:

mkdir secrets && printf '%s' "<32+ случайных символов>" > secrets/session_secret.txt
docker compose build && docker compose up -d && docker compose ps
curl http://127.0.0.1:9002/health
docker compose exec workshop node bin/app.js user create-admin

Ручной вариант того, что делает npm run docker:test (часть проверок прав файлов на Windows пропускается). Команда выполняется из корня репозитория, одной строкой, в PowerShell:

docker run --rm -it -v "${PWD}:/src:ro" node:26-bookworm-slim bash -c "mkdir /app && tar --exclude=node_modules -C /src -cf - . | tar -C /app -xf - && cd /app && npm install && npm install-scripts approve argon2 && npm rebuild argon2 && npm test"

В PowerShell нужны именно фигурные скобки: запись $PWD:/src он читает как переменную с диском и ломает путь. В bash/zsh (Linux, macOS, Git Bash) то же самое с "$PWD:/src:ro"; в cmd — "%cd%:/src:ro". Копия в /app делается без node_modules, поэтому нативные сборки (argon2, sharp) собираются заново под Linux, а ваши Windows-версии остаются нетронутыми.

Если тега node:26-bookworm-slim нет — node:current-bookworm-slim. Команды Docker в этой документации проверены чтением, не запуском; первый ваш запуск — их проверка.

Доступ из локальной сети

По умолчанию приложение слушает только 127.0.0.1: открыть его можно лишь на той же машине. Чтобы коллеги в локальной сети (дом, офис) могли зайти, нужны четыре вещи: слушать внешний адрес, открыть порты в брандмауэре, выпустить сертификат на адрес или имя сервера и разрешить этот адрес для редиректа с HTTP. Порты приложения: HTTPS 9N02 и HTTP 9N01 (только редирект), у workshop это 9002 и 9001. Наружу, в интернет, порты не пробрасывайте: для доступа извне используйте VPN.

Дальше в примерах адрес сервера 192.168.1.50, имя forge-srv. Свой адрес покажет ipconfig (Windows, строка «IPv4-адрес») или ip -4 addr (Linux).

1. Слушать адрес локальной сети

В app.config.js или переменной окружения:

server: { host: '0.0.0.0', port: 9002, allowedHosts: ['192.168.1.50', 'forge-srv'] }
DAS_HOST=0.0.0.0        # все интерфейсы; или конкретный адрес сетевой карты: DAS_HOST=192.168.1.50

allowedHosts нужен для редиректа с http://адрес:9001 на HTTPS: адрес из заголовка Host ему доверяют только из этого списка (иначе редирект уводит на https://localhost:9002, что у коллеги открывает его собственный компьютер). Если включена почта, в email.baseUrl пропишите тот адрес, по которому пользователи открывают приложение: ссылки в письмах строятся из него.

2. Открыть порты в брандмауэре

Открывайте только для локальной подсети, а не для всех.

Windows (PowerShell от администратора):

New-NetFirewallRule -DisplayName "DAS-Forge workshop" -Direction Inbound -Protocol TCP -LocalPort 9001,9002 -Action Allow -Profile Private -RemoteAddress LocalSubnet
# убрать правило:
Remove-NetFirewallRule -DisplayName "DAS-Forge workshop"

Профиль Private значит, что сеть в Windows названа «Частной». Если она «Общедоступная», правило не сработает: поменяйте тип сети в параметрах Windows или добавьте Public в -Profile, понимая, что в чужой сети порт будет виден.

Linux, ufw:

sudo ufw allow from 192.168.1.0/24 to any port 9001,9002 proto tcp
sudo ufw status

Linux, firewalld:

sudo firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="192.168.1.0/24" port port="9001-9002" protocol="tcp" accept'
sudo firewall-cmd --reload

Подсеть (192.168.1.0/24) возьмите свою: первые три числа вашего адреса и /24. В домашней сети роутеру ничего открывать не нужно: проброс портов нужен только для доступа из интернета, а он здесь не нужен.

3. Сертификат на адрес сервера

Сертификат, который создаётся при первом старте, выписан только на localhost, 127.0.0.1 и ::1. По адресу локальной сети браузер покажет предупреждение «имя не совпадает». Выпустите новый, с адресом и именем сервера (приложение при этом остановите, потом запустите снова):

node bin/app.js cert generate --force --common-name forge-srv --alt-names 192.168.1.50,forge-srv,forge-srv.local
node bin/app.js cert info        # проверьте строку subjectAltName

Предупреждение «самоподписанный сертификат» остаётся, пока на каждом компьютере сертификат не добавлен в доверенные: node bin/app.js cert trust печатает инструкцию для вашей системы. Для организации лучше сертификат от своего удостоверяющего центра: режим server.https.mode: 'standalone' с certPath и keyPath (см. «Безопасность»).

4. Docker

Образ рассчитан на обратный прокси, а docker-compose.yml публикует порт только на 127.0.0.1. Для сети есть два пути.

  • Рекомендуемый: TLS-прокси перед контейнером (Caddy, nginx, Traefik). Прокси слушает 443 на адресе сервера, отдаёт сертификат организации, ставит X-Forwarded-Proto и X-Forwarded-For и ходит к 127.0.0.1:9002. В docker-compose.yml ничего менять не нужно, брандмауэр открывает порт 443 для подсети.
  • Напрямую, без прокси (для проверки): контейнер сам отдаёт HTTPS с самоподписанным сертификатом. В docker-compose.yml замените ports и environment, затем выпустите сертификат на адрес сервера (пункт 3, команда внутри контейнера: docker compose exec workshop node bin/app.js cert generate --force --common-name forge-srv --alt-names 192.168.1.50,forge-srv) и перезапустите контейнер:
    ports:
      - "9002:9002"
      - "9001:9001"
    environment:
      DAS_HTTPS_MODE: self-signed
      DAS_TRUST_PROXY: "false"
      DAS_SESSION_SECRET_FILE: /run/secrets/session_secret

Не открывайте в сеть порт 9002 режима reverse-proxy без прокси: по обычному HTTP пароли идут открытым текстом. Порты контейнера публикует Docker, но брандмауэр хоста всё равно должен разрешать их подсети (пункт 2). Docker Desktop в Windows при установке добавляет свои правила, но проверьте, что подсеть не заблокирована.

Резервные копии

Расписание backup.schedule, хранение retentionDays, шифрование backup.encryptionKey (≥ 16 символов, DAS_BACKUP_KEY). Приёмники: local, mount (смонтированная сеть, markerFile подтверждает монтирование), sftp (отпечаток ключа сервера обязателен) (s3 и webdav пока не поддерживаются, конфигурация с ними отклоняется). Хотя бы одну копию храните вне сервера.

Расписание любой задачи меняется в админке («Задачи»), без правки кода: форма с cron или временем суток, «Вернуть исходное» отменяет изменение. Копию можно проверить кнопкой «Проверить» в «Резервных копиях».

Автобэкап включается, выключается и переносится на другое время суток в админке («Резервные копии»), без правки конфигурации и перезапуска. Каталог локального приёмника, которого ещё нет (до первой копии), диагностика показывает предупреждением, а не ошибкой.

Правила:

  1. раз в период проверяйте восстановление: backup verify <файл> и пробный backup restore на тестовой копии;
  2. после восстановления выполните privacy reapply-erasures;
  3. без encryptionKey копии содержат всё открыто — защищайте приёмник.

Восстановление uploads после успешного восстановления базы может не удаться: тогда база новая, а файлы прежние. Откат базы ядро не делает, сообщение об ошибке описывает состояние — сверьте каталог вручную и повторите backup restore.

Метрики для Prometheus

В настройках: observability.metrics.enabled: true (по умолчанию выключено) и пакет @prometheus-io/client (устанавливается вместе с ядром). Эндпоинт /metrics отвечает, только если запрос пришёл с адреса из allowIps (по умолчанию с этой же машины) или с заголовком Authorization: Bearer <токен> (observability.metrics.token, от 16 знаков); всем остальным он отвечает 404, как несуществующая страница. Отдаётся: число запросов по методу, шаблону маршрута и классу статуса, длительность запросов, метрики процесса (память, процессор, задержка цикла событий), das_sessions_active, das_mail_queue_pending, das_mail_queue_failed, das_last_backup_age_seconds (нет, пока копий нет), das_bans_active (действующие блокировки), das_security_incidents_open (незакрытые инциденты), das_alerts_24h (тревоги за сутки), das_maintenance_mode (1 при включённом режиме обслуживания). Показание, чьей таблицы ещё нет, просто не выводится. Прометею нужен доступ по HTTPS к порту приложения: при самоподписанном сертификате укажите в его настройке tls_config либо корневой сертификат, либо insecure_skip_verify только в доверенной сети. Пример сборщика:

scrape_configs:

    scheme: https
    metrics_path: /metrics
    authorization: { type: Bearer, credentials_file: /etc/prometheus/workshop.token }
    tls_config: { ca_file: /etc/prometheus/workshop-cert.pem }
    static_configs: [{ targets: ['workshop.example.local:9002'] }]

Графики запросов и ошибок на «Обзоре» админки работают независимо от метрик. В панелях Grafana используйте источник Prometheus.

Как проверить, что алерты работают

В workshop есть рабочий пример: команды alerts test и alerts list (examples/workshop/src/alerts-commands.js, подключены в bin/app.js).

cd examples/workshop
node bin/app.js alerts test --severity critical --message "проверка"   # настоящий алерт
node bin/app.js alerts list                                            # последние алерты
  1. alerts test проходит тот же путь, что и сервер: запись в таблицу alerts, строка лога, письмо контактам. Команда сама пишет, было ли письмо: «No mail» значит, что почта выключена или security.incidentContacts пуст.
  2. С включённой почтой письмо ставится в очередь; доставляет его работающий сервер (цикл очереди). Если сервер остановлен, письмо ждёт в очереди.
  3. Откройте админку → «Алерты»: запись видна там, с важностью и признаком «письмо отправлено».
  4. Повтор команды с тем же --key в другом запуске создаёт новую запись: кеш повторов живёт в памяти одного процесса. Проверить сам кеш можно на работающем сервере или тестом packages/core/test/alerts.test.js.
  5. Реальные источники проверяются так: задайте копии неверный путь назначения и дождитесь запуска по расписанию (сбой копии — критический алерт); десять блокировок входа за десять минут дают критический алерт; нарушенная цепочка аудита ловится задачей alerts-audit-chain.

Обновление

  1. сделайте копию (backup run);
  2. выкатите новую версию — миграции применяются при старте (или отдельно migrate); Перед применением ожидающих миграций ядро само делает согласованную копию базы (VACUUM INTO + проверка целостности) в папку pre-migrate рядом с файлом базы, хранятся 5 последних; если копию сделать не удалось, ничего не применяется. Откат при неудачной миграции — восстановлением из этой копии.
  3. doctor и /health;
  4. при проблеме — откат образа и backup restore.

Миграции необратимы: откат кода без отката данных возможен только если схема совместима.

Доступ к админке на отдельном адресе

Если задан server.admin.port (см. безопасность), панель доступна только на этом порту. Релизы и обновление ядра

Ядро (@das-forge/core) публичное и публикуется на npm. Приложения платформы подключают его обычной зависимостью и обновляют обычным npm update.

Какие версии публикуются. Каждая поставка при разработке повышает патч-номер (0.1.135, 0.1.136…): это промежуточные сборки, они нигде не публикуются. В npm попадают только релизы: версия x.y.z без суффикса с записью в CHANGELOG.md и тегом vX.Y.Z. Номера между релизами пропускаются — это нормально. Пока основная версия 0, поднятие второго числа (0.2.0 → 0.3.0) означает возможные ломающие изменения, третьего (0.2.0 → 0.2.1) — только исправления и совместимые добавления; запись ^0.2.0 в приложении пропускает только исправления.

Как выпустить релиз (раз в этап, а не на каждую поставку):

  1. node scripts/version.mjs set 0.2.0, затем в CHANGELOG.md заголовок ## [0.2.0] — дата с описанием (ломающие изменения — отдельным списком);
  2. npm run release:check — проверяет версию, запись в CHANGELOG, лицензию и publishConfig;
  3. закоммитьте, git tag v0.2.0, git push origin v0.2.0;
  4. workflow .github/workflows/release.yml повторяет проверки, прогоняет тесты, публикует пакет и создаёт GitHub Release с текстом из CHANGELOG. Для публичного репозитория в npm записывается provenance (подтверждение, что пакет собран из этого коммита); для приватного — публикация без него.

Разовая подготовка

  1. Зарегистрируйтесь на npmjs.com и включите двухфакторную аутентификацию (для публикации она обязательна).
  2. Создайте организацию das-forge (бесплатна для публичных пакетов): так пакет получит имя @das-forge/core. Если имя занято, выберите другое — оно прописано в packages/core/package.json и в импортах приложений.
  3. Создайте токен доступа (Granular access token: Read and write, только пакет @das-forge/core, срок — до года) и сохраните его в репозитории GitHub как секрет NPM_TOKEN (Settings → Secrets and variables → Actions).
  4. Выпустите первый релиз по инструкции выше.

Как обновить приложение

  1. прочитайте записи CHANGELOG.md между вашей и новой версией, особенно «ломающие изменения»;
  2. npm update @das-forge/core (в пределах ^0.2.0) или npm install @das-forge/core@0.3 (смена второго числа);
  3. npm test, затем «Обновление» выше: копия, выкатка, doctor, /health;
  4. раздел админки «О системе» показывает установленную и последнюю версии пакета в реестре (кнопка «Проверить обновления»).

Закрытые сборки: разработка идёт в приватном репозитории, в публичный попадают релизы вместе с тегами и CHANGELOG.

Остановка

registerGracefulShutdown перестаёт принимать запросы, закрывает потоки SSE событием shutdown, ждёт завершения до shutdownDrainTimeoutMs. Для Docker stop_grace_period ≥ этого значения.

Сборка и зависимости

  • Образ закреплён тегом node:26-bookworm-slim; для воспроизводимости закрепите его digest (FROM node:26-bookworm-slim@sha256:…) после первой удачной сборки: digest в среде разработки получить нельзя.
  • В CI действия (actions/checkout, actions/setup-node) указаны по тегу v4; замена на SHA коммита — на стороне владельца репозитория.
  • Лицензия libheif-js (LGPL) требует юридической оценки; список лицензий компонентов показывает раздел «О системе»; проверка — license-checker.

Внимание

  • Планировщик живёт в процессе: два экземпляра на одной базе запустят задания дважды.
  • Не удаляйте first-run-admin.txt из каталога данных, не прочитав пароль; после входа — удалить.
  • Потеря sessionSecret без previousSessionSecrets — все выходят из системы; потеря totpEncryptionKey — настройка TOTP заново.

Сеть за прокси

npm берёт настройки прокси из своей конфигурации, а встроенный fetch Node их не видит. Если в «О системе» или в диагностике реестр npm и nodejs.org недоступны, причина показана в сообщении и во всплывающей подсказке значка (ENOTFOUND, ETIMEDOUT, ошибка сертификата). За прокси запускайте приложение с NODE_USE_ENV_PROXY=1 и HTTPS_PROXY=http://адрес:порт; если прокси проверяет TLS своим сертификатом, добавьте NODE_EXTRA_CA_CERTS=путь\к\сертификату.pem. Без сети проверка уязвимостей показывает последний удачный результат с датой.

Проверка уязвимостей

Категория «Dependencies» диагностики (health.dependencyChecks, health.nodeVersionChecks; включается security.dependencyAudit) отвечает на два вопроса: нет ли в установленных пакетах известных уязвимостей и не вышла ли для вашей ветки Node.js новая версия с исправлениями безопасности.

Как работает. Список пакетов берётся из package-lock.json рядом с приложением (то, что реально установлено, без пакетов для разработки). Он уходит одним запросом в реестр npm (POST /-/npm/v1/security/advisories/bulk, тот же источник, что у npm audit); совпадение версии с диапазоном уязвимых проверяет semver. Процессы не запускаются, npm на сервере не нужен.

Без сети. Реестр недоступен — проверка не падает: показывается последний успешный результат с датой (он хранится в базе) и предупреждением «не удалось обновить»; если успешной проверки ещё не было, — «не проверено» с причиной. Причина пишется в журнал. Пустой результат старше последней успешной проверки не выдаётся за «всё хорошо»: в таком случае статус «предупреждение». Без package-lock.json проверка тоже честно сообщает «не проверено».

Версия Node.js. Версия сверяется с индексом релизов nodejs.org (dist/index.json): если для вашей ветки есть более новая версия с пометкой «security», выводится предупреждение. Даты окончания поддержки ветки индекс не содержит, их эта проверка не знает. Без сети — предупреждение «не проверено» и запись в журнал.

Что делать с находкой. Обновить пакет (npm update, для зависимостей ядра — само ядро), а если исправления нет или уязвимость недостижима в вашем приложении, принять её на срок в security.dependencyAudit.ignore с причиной и датой пересмотра. Принятие не прячется: в сводке остаётся «N accepted».

Расписание. Диагностика запускается сама раз в сутки (alerts.doctorSchedule), включается и переносится в разделе «О системе»; результат с ошибками становится алертом. Для проверки в любой момент — кнопка в «О системе» или команда doctor. Данные о пакетах уходят в публичный реестр npm: если внешние запросы с сервера нежелательны, выключите проверку (security.dependencyAudit.enabled: false) и сверяйте зависимости в CI.

Разработка ядра

Принципы

  1. Ядро выносит общее, чтобы приложения не изобретали одно и то же; по умолчанию даёт рабочее поведение, приложения настраивают его через коннекторы и опции.
  2. Администрирование, оформление и учётная запись общие: приложение подключает разделы ядра и расширяет их (sections, texts), но не делает собственных страниц пользователей, аудита, состояния системы и резервных копий (см. Администрирование).
  3. Сначала готовая зависимость из docs/dependencies-target.md; собственный код — только с обоснованием.
  4. Безопасность по умолчанию: строгие схемы, проверка на сервере, минимум доверия вводу.
  5. Каждое изменение с тестом; отрицательные сценарии обязательны.

Порты

Приложение платформы: HTTPS на 9N02, HTTP на 9N01 с обязательным перенаправлением на HTTPS; следующее приложение — на 100 больше (workshop 9002/9001, IT Assets 9102/9101, далее 9202/9201 …). Подробности — в «Конфигурации».

Проверка новой версии

Как принять архив с новой версией ядра и убедиться, что она работает. Каждый архив открывается в чистой папке, старая не заменяется: так можно вернуться к предыдущей версии и не тащить за собой чужие файлы. Команды для Windows (CMD); на Linux и macOS те же, меняются только пути.

1. Распаковать и перейти в папку

Распакуйте архив в новую пустую папку, например C:\Users\<имя>\Downloads\das-forge-core-0.1.264. Внутри будет папка das-forge-core.

cd C:\Users\<имя>\Downloads\das-forge-core-0.1.264\das-forge-core

2. Поставить зависимости

Папки node_modules в архиве нет, она ставится каждый раз заново (около 30 секунд).

npm install

npm напишет, что установочные скрипты трёх пакетов заблокированы. В новой папке это бывает каждый раз: разрешение из прошлой папки сюда не переносится.

npm install-scripts approve cpu-features ssh2 argon2

Команда называется install-scripts (во множественном числе, через дефис). Без этого шага не соберётся argon2, а с ним вход в систему.

3. Проверить lock-файл и поставить по нему

npm run lock:check
npm ci

lock:check отвечает «lock file is in step with the package.json files». Если он перечисляет расхождения, в архиве поменялись зависимости без обновления package-lock.json: дальше не идите и сообщите разработчику. npm ci ставит ровно то, что записано в lock-файле.

4. Статическая проверка и тесты

npm run lint
npm test
  • npm run lint (ESLint). Ошибок (error) должно быть 0. Предупреждения (warning) сборку не ломают, но их число не должно расти от версии к версии.
  • npm test запускает все тесты ядра и примера. В конце смотрите строки Test Files и Tests: должно быть failed отсутствует или 0. Пропущенные (skipped) допустимы.

Если что-то упало, сохраните вывод целиком (в CMD: npm test > test.log 2>&1) и передайте файл test.log.

5. Сценарии в браузере (e2e)

Это тесты, где настоящий браузер открывает приложение, входит под администратором, нажимает кнопки и проверяет, что страницы ведут себя как нужно. Ловят то, чего не видят обычные тесты: сломанный скрипт на странице, пропавшую кнопку, неверный редирект.

Что нужно один раз (браузер скачивается в общую папку пользователя, а не в проект, поэтому повторять для каждой версии не надо):

npx playwright install chromium

Запуск из корня das-forge-core:

npm run test:e2e

Playwright сам поднимает приложение на пустой временной базе (папка во временных файлах системы) с известным администратором e2eadmin, порт 4399. Ваша рабочая база и настоящие пользователи не затрагиваются. Если порт занят, задайте другой: set E2E_PORT=4400 перед командой.

Что проверяется сейчас (файлы examples/workshop/e2e/*.e2e.js):

ФайлСценарий
admin-users.e2e.jsадминистратор создаёт, правит, сбрасывает пароль и удаляет учётную запись; у своей строки кнопок действий нет; гость не открывает раздел «Пользователи»
admin-sections.e2e.jsстраницы входа и «Забыли пароль»; разделы «Задачи», «Почта», «Конфигурация»; вкладка «Входы» и экспорт JSON в аудите; режим обслуживания (посетителям 503, администратор его выключает)
admin-paging.e2e.jsдлинный список разбит на страницы, кнопка «Развернуть» догружает остальное; реестр обработки открывается и скачивается как CSV

Сценариев пока немного, список будет расти вместе с разделами админки. Правило для новых разделов: страница с интерактивным скриптом (живая лента, постраничная загрузка, диалоги) получает свой сценарий, потому что обычные тесты не запускают браузерный код.

Если сценарий упал. Playwright кладёт отчёт в examples\workshop\test-results\: снимок экрана и трассу (trace.zip). Посмотреть трассу пошагово:

npx playwright show-trace examples\workshop\test-results\<папка сценария>\trace.zip

Для передачи достаточно снимка экрана и текста ошибки из консоли.

Тонкости:

  • Сценарии нажимают кнопки по английским названиям (locale: 'en-US' в playwright.config.js). Поменяли название кнопки в англоязычных текстах, поправьте и сценарий.
  • Приложение отдаёт самоподписанный сертификат, поэтому браузер запускается с ignoreHTTPSErrors.
  • На CI e2e идут только на Linux в одном браузере (Chromium).

6. Запуск для ручной проверки

npm start

Приложение (workshop) откроется на https://127.0.0.1:9002 (HTTP на 9001 только перенаправляет). Команды управления вводятся в строке > внизу окна, см. «Командная строка». Базу и сертификаты приложение создаёт в examples\workshop\data внутри этой папки. Чтобы сохранить данные предыдущей версии, скопируйте её папку examples\workshop\data в новую до первого запуска. Если не копировать, всё создастся заново: пользователи и журнал будут пустыми.
