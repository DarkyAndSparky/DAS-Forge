## 2. Что в порядке

- **Сессии (VERIFIED):** подсунутая cookie при входе заменяется новым идентификатором; `HttpOnly; Secure; SameSite=Lax`; после выхода старая cookie даёт 401; пока ожидается смена пароля, `/admin` отвечает 403.
- **Вход (VERIFIED):** чужой `Origin` на `/login` — 403; пятая подряд неудача с адреса — 429; неизвестное имя блокируется как настоящее (оракула перебора имён нет).
- **Заголовки и ввод (VERIFIED):** CSP с nonce и `frame-ancestors 'none'`, HSTS (при `X-Forwarded-Proto: https`), COOP/CORP, `nosniff`, `X-Frame-Options: DENY`; тело 3 МБ — 413; обход путей — 404; `TRACE` — 404; `/metrics`, `security.txt`, `robots.txt` выключены по умолчанию.
- **SVG-вычистка (VERIFIED):** внешние ссылки, `foreignObject`, `animate`, внешний DTD, `xml-stylesheet`, `onload`, `javascript:` убираются.
- **Архивы (VERIFIED):** честная zip-бомба (600 МБ, коэффициент 1028×) отклонена за 3 мс; архив с ложным каталогом (заявлено 1000 байт, внутри 300 МБ) пропускает первая охрана, но `verifyZipData` ловит за 14 мс, прирост памяти ~1 МБ.
- **Почта (VERIFIED):** перевод строки в теме схлопывается в одну строку (внедрения заголовка нет); получатель с `\r\n` или списком адресов отклоняется; HTML уведомления экранируется.
- **SSRF (VERIFIED частично):** формы `::ffff:7f00:1`, `::ffff:a9fe:a9fe` обрабатываются верно (непроверенные диапазоны — S-04).
- **Сущности (READ + тесты):** описание без имени права для действия не создаётся («нет умолчания "для всех"»); запись и удаление проверяют право до изменения; чужая организация даёт 404; версия проверяется в транзакции; ворота Zod режут лишние поля и огромные значения до базы.
- **Загрузки, база, криптография (READ):** тип по содержимому, имя не от клиента, `sandbox`-CSP и `attachment` для не-изображений; запросы через `?`, имена через `assertSafeIdentifier`, сортировка и фильтры по белому списку; токены сброса пароля хешем и атомарно; копии AES-256-GCM, scrypt N=2^17, заголовок в AAD; TOTP AES-256-GCM с HKDF; argon2id 19 МиБ, t=2 (минимум OWASP); SFTP-копии с обязательным отпечатком хоста.
- **Журналы (READ):** приёмники stdout, файл, syslog (RFC 5424) и HTTP (Loki, Elasticsearch/OpenSearch, Splunk HEC, NDJSON) с повторами; `mirrorAuditToLogs` шлёт хеши записей аудита вовне; `alerts` с webhook, эскалацией и heartbeat; баны IP и пользователей; админ-слушатель с `allowedNets`.
- **Репозиторий (READ):** ESLint + `tsc`, инвариантный тест «нет `innerHTML`», ADR, `CLAUDE.md`, CodeQL, gitleaks, Trivy, SBOM, provenance, Dependabot.
- Пакет `@prometheus-io/client` проверен в реестре: официальный (организация Prometheus, SLSA provenance, создан 2026-08-21).

## 9. WAF и SIEM

**Поправка к прежним выводам.** Основа для SIEM уже есть (см. раздел 2). Не прочитано: `HTTP_FORMATS` целиком и какие события безопасности реально попадают в журнал (CSRF-отказы, `Host`, отказы загрузок, лимиты, отчёты CSP): NOT VERIFIED.

SIEM: строить своё не нужно, нужны профиль и содержание.

| № | Приоритет | Что сделать |
|---|---|---|
| W-01 | средний | Документ «профиль журналов»: какие приёмники включать в production (syslog или Loki вне машины), включить `audit.mirror`, проверять доставку (метрика потерь приёмника) |
| W-02 | средний | Каталог событий безопасности (имя, поля, уровень) и тест, что каждое событие эмитируется: отказ входа, блокировка, создание администратора, смена пароля и MFA, восстановление копии, провал `audit verify`, отказ CSRF/Host, отказ загрузки и SSRF, лимит запросов, отчёт CSP |
| W-03 | низкий | Поля в стандарте ECS или OCSF как необязательный формат приёмника |
| W-04 | средний | Набор правил обнаружения в формате Sigma (всплеск неудач входа, вход администратора с нового адреса, восстановление копии, провал цепочки аудита, массовые 4xx на загрузках) |
| W-05 | низкий | Для одного сервера: Loki + Grafana + Alertmanager или агент Wazuh; Elastic и Splunk без команды — перебор |

WAF: на уровне прокси, не в ядре. Не закроет S-01, S-03, S-17, R-01…R-03 (корректные с точки зрения сигнатур запросы, ошибки логики и ресурсов); SQLi/XSS-сигнатуры малополезны (параметризация). Даёт: отсечение сканеров, виртуальные патчи на время закрытия уязвимости в зависимости, ограничения размеров и скоростей, фильтры ботов и стран.

| № | Приоритет | Что сделать |
|---|---|---|
| W-06 | высокий | Сначала правильный прокси, а не WAF: перезапись `X-Forwarded-For`, лимит тела по маршрутам (малый для SVG и JSON), таймауты, админка только из своей сети (A-01) |
| W-07 | средний | CrowdSec или fail2ban с чтением журналов DAS и блокировкой на границе (баны внутри приложения есть, но на границе дешевле) |
| W-08 | средний | Профили `deploy/`: nginx или Caddy + Coraza (совместим с OWASP CRS 4.x), `DetectionOnly`, уровень паранойи 1, 1–2 недели настройки исключений для маршрутов DAS, затем блокировка |
| W-09 | низкий | Apache: `mod_security2` или Coraza через прокси; поддержка версии 2 прекращена Trustwave, развитие у OWASP (NOT VERIFIED на ноябрь 2026) |
| W-10 | не делать | Встроенный regex-WAF в ядре: обходится, нагружает процессор (ReDoS), ломает легальный ввод |

## 10. Критика предложений (не удалено)

- «Опубликовать репозиторий — критично» верно, только если проект публикуется; иначе срочность ниже, но README на GitHub всё равно нужно убрать или привести в порядок, чтобы не вводить в заблуждение.
- Приоритеты — оценка по выборочному чтению кода; часть «пробелов» могла быть закрыта кодом, который не открывался. Оценка S-17 основана на самодельном стенде по структуре теста `entities-routes.test.js`, не на вашем приложении.
- OIDC и passkeys добавляют зависимости и поверхность атаки; ваше правило «своё лучше готового — только с объяснением» важнее моего «обязательно». Возможно, достаточно OIDC-клиента без SAML.
- Вынос тяжёлых зависимостей в необязательные ломает идею «всё из коробки» и умножает конфигурации для проверки одним разработчиком; `jsdom` и `sharp` и так грузятся по требованию, выигрыш может быть меньше заявленного.
- Закрепление actions по SHA создаёт ручную работу без Dependabot: сначала Dependabot, потом SHA.
- Генератор приложений и команда обновления ядра преждевременны, пока API «может меняться» (0.1.x): сначала стабильный контракт.
- Клиентский слой (htmx или компоненты) противоречит осознанному принципу «без клиентского каркаса»; не навязывать, пока `apps/` пуст.
- Captcha, SEO, CMS: документация и ADR описывают только внутренние приложения; требования для публичных сайтов выведены из постановки владельца, продукт их пока не обещает. Позиционирование надо решить первым.
- HTTP/2, HTTP/3, ACME: задача прокси, не ядра; в «современных RFC» я записал это как недостаток зря (N-07 помечен «не в ядро»).
- RFC 9457 заменой ломает клиентов и тесты; только как выбор по `Accept` (N-01).
- Windows-служба: «работает на Windows» в `CLAUDE.md` может быть про машину разработки, не про сервер.
- Доступность: страницы в браузере не открывались; вывод «не подтверждено» относится к автоматике в репозитории.
- S-03 за прокси слабее, чем в тесте (там `X-Forwarded-For` подделывался напрямую); пункты про копии требуют уже имеющегося доступа к хранилищу копий; S-01 главный, потому что не требует привилегий кроме права загрузки.
- Решение «WAF не нужен ядру» верно, но «профиль WAF на прокси» я недооценил в первом ответе: для публичных сайтов он нужен (W-06…W-08).
- Объём отчёта создаёт иллюзию, что надо делать всё; для одного разработчика осмысленный порядок — раздел 13.

## 11. Сборка 0.1.372 (`das-linux`): замечания по упаковке

12 970 файлов, 221 МБ вместе с `node_modules`. **Это не Linux-сборка:** `node_modules/.bin/*` — оболочки Windows (`exec node.exe`), на Linux `eslint` и другие команды не запускаются (`node.exe: not found`). Лучше собирать архив без `node_modules` (установка `npm ci` на целевой системе) или собирать `node_modules` на Linux.

Новый код 0.1.369–0.1.372 (READ + тесты): ворота Zod перед `entity.validate` (решение владельца); `mountEntityPages` (значения экранируются `esc()`, форма с `_version`, CSRF-поле по умолчанию пустое и полагается на CSRF-слой приложения: проверить, что `…/new`, `…/:id`, `…/delete`, `…/restore` не попали в `exemptPaths`); `planEntitySync`/`applyEntitySync` (DDL из описания, только добавляет); `openApiOf`/`jsonSchemaOf`/`typeScriptOf`.

## 12. Цепочки атак (для приоритизации)

1. **Отказ плюс обход защиты:** S-01 (заморозка) → перезапуск процесса → S-02 (счётчики перебора обнулены).
2. **Подмена данных через копию:** доступ к хранилищу копий и ключу → подложенная база → при восстановлении свой администратор и чистый журнал. Закрывается R-02 и R-01.
3. **Тихое переписывание журнала:** запись в базу → пересчёт цепочки; обнаруживается только при настроенном внешнем приёмнике (R-01).
4. **Захват или вывод из строя администратора:** распределённый перебор и блокировка в нужный момент (S-03) при необязательном втором факторе (S-15).
5. **Чтение чужих данных без права:** членство в нескольких организациях → перебор через `total` (S-17).
6. **Цепочка поставок:** незакреплённые actions (C-02), скрипты установки (R-04), долгоживущий токен публикации (C-05).
