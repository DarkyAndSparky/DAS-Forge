# IT Assets (stage 25) как первый потребитель платформы сущностей

Дата: 2026-11-20. Источник: архив `it-assets-stage25.zip` (ветка dev, версия β1·26w41). Прочитаны README, CHANGELOG, SCHEMA.md, схема БД, репозитории пользователей и организаций, middleware аутентификации; приложение не запускалось, тесты не прогонялись. Все числа посчитаны по файлам архива.

## Размер и состав
- Сервер около 10,3 тыс. строк JS, клиент (`public/js`) около 10,9 тыс., тесты около 11,4 тыс. 109 маршрутов, 17 таблиц.
- Таблицы: `assets`, `asset_photos`, `asset_relations`, `asset_versions`, `history`, `organizations`, `org_inv_rules`, `filials`, `locations`, `employees`, `categories`, `type_codes`, `users`, `accounts`, `api_keys`, `settings`, `audit_log`, `sessions`.
- Расхождение в документации приложения: README говорит 792 теста, CHANGELOG 810 (не проверялось, какое верно).

## Что уже есть в ядре (в IT Assets написано своё)
Сессии и CSRF, лимиты запросов, хранилище сессий, LDAP, аудит, резервные копии, проверки здоровья, журнал, сертификаты, санитарная обработка, запись xlsx, обработка изображений и HEIC, уведомления, ключи API. После переписывания это уходит из приложения (оценка: большая часть серверного кода вне предметной области).

Активы (вкладки `os`/`small`/`infra`, категория, тип, статус, инвентарные номера по правилам организации), связи между активами, версии записи, история событий, фото, QR и инвентаризация сканированием, импорт CSV и конвертер Excel, филиалы, локации, сотрудники, массовые операции (перемещение, правка полей).

## Находки, важные для платформы
1. **Поля, зависящие от типа устройства.** 17 фиксированных колонок `meta_*`, а какие показывать, задаёт схема полей на тип (`field_schemas`, правится администратором в рабочем приложении). В дескрипторе (ADR-0012) такого нет: нужен механизм «варианты по значению поля» с набором дополнительных полей, хранимых в JSON-колонке, и схемой, которую можно править без выпуска версии. Это главный пробел дескриптора.
2. **Секреты в открытом виде.** `accounts.password` и `assets.meta_password` хранятся как обычный текст. Нужен тип поля `secret`: шифрование AES-GCM ключом ядра, показ только по праву, запись обращений в аудит. Это не перенос, а исправление.
3. **Вход по PIN.** Пользователи входят по `pin` (колонка `users.pin`), с принудительной сменой заводского значения. Платформа использует парольную политику и argon2 ядра; миграция PIN в пароли — отдельный шаг с участием пользователей.
4. **Идентификаторы UUIDv7 (текст).** Ссылки (`ref`) должны поддерживать и текстовые идентификаторы, не только целые.
5. **Снимки имён.** `org`, `filial`, `location`, `responsible` хранятся дважды (id и имя на момент записи), чтобы закрытый справочник не терял историю. В платформе это функция поля `ref` (`snapshot: true`) либо мягкое удаление справочника.
6. **Организация сейчас одна на пользователя** (`users.org_id`, «пусто» = без ограничения). Это основа для мультиарендности, но модель «один человек в нескольких организациях» её не покрывает.
7. **Роли `admin`/`operator`/`viewer`** плюс флаг `can_view_accounts`: переносится в права ядра (`permissions`), флаг становится правом.
8. **Клиент: самописное SPA на 10,9 тыс. строк**, часть мест с `innerHTML` (под защитой DOMPurify). Заменяется страницами и компонентами `das-*` (D3): самый большой объём работы и самый заметный выигрыш.

## Что нужно от платформы для переписывания (порядок)
1. B1 дескриптор с типами `text`, `enum`, `ref` (текстовые id), `date`, `money`, `json`, `file`, `secret`, `ip`, `mac` и вариантами по значению поля.
2. Мультиарендность: организации, группы доступа, выбор активной организации.
3. B2 CRUD и страницы, B4 компоненты, B6 вложения (фото), B7 история и версии, B9 импорт, C1 ключи API.
4. Специфика приложения поверх платформы: инвентарные номера по правилам организации, QR и сканирование, связи активов.
