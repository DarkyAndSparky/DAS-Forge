# Эксплуатация

## Требования к серверу

Node.js ≥ 26, постоянный том для каталога данных (база, копии, загрузки, сертификаты), обратный прокси с TLS перед приложением в режиме `reverse-proxy`, часы с синхронизацией времени (сессии, журналы, ссылки в письмах).

## Docker

В корне — `Dockerfile` и `docker-compose.yml` эталонного приложения.

- Образ на `node:26-bookworm-slim`, процесс под пользователем `node`, `tini` как точка входа.
- Все данные — в `examples/workshop/data`: монтируйте **один** том туда.
- `DAS_HTTPS_MODE=reverse-proxy`, `DAS_TRUST_PROXY=true`: контейнер говорит по HTTP в закрытой сети, прокси обязан ставить `X-Forwarded-Proto` и `X-Forwarded-For`.
- `HEALTHCHECK` опрашивает `/health`; при остановке он сразу отвечает 503, и оркестратор перестаёт слать трафик.
- Секрет сессии — через `DAS_SESSION_SECRET_FILE` (Docker secret), не в образе.

Одной командой из любой оболочки (скрипты `scripts/docker-start.mjs` и `scripts/docker-test.mjs`, без `bash` и `$PWD`):

```bash
npm run docker:start     # создаёт secrets/session_secret.txt (если нет), собирает, запускает, ждёт /health
npm run docker:logs      # лог контейнера: в нём баннер с логином и временным паролем первого администратора
npm run docker:stop      # остановить и удалить контейнер (том с данными остаётся)
npm run docker:test      # все тесты в чистом Linux-контейнере; --core — только ядро; --image <имя> — другой образ
```

После `docker:start` приложение отвечает на `http://127.0.0.1:9002` (режим `reverse-proxy`: в production перед ним ваш TLS-прокси; открыть для сети без прокси — раздел «Доступ из локальной сети»). Свой администратор вместо первого: `docker compose exec workshop node bin/app.js user create-admin`. Секрет сессии скрипт создаёт один раз (48 случайных символов, права только владельцу, в git не попадает); существующий файл не трогает.

То же вручную:

```bash
mkdir secrets && printf '%s' "<32+ случайных символов>" > secrets/session_secret.txt
docker compose build && docker compose up -d && docker compose ps
curl http://127.0.0.1:9002/health
docker compose exec workshop node bin/app.js user create-admin
```

Ручной вариант того, что делает `npm run docker:test` (часть проверок прав файлов на Windows пропускается). Команда выполняется из корня репозитория, одной строкой, в PowerShell:

```powershell
docker run --rm -it -v "${PWD}:/src:ro" node:26-bookworm-slim bash -c "mkdir /app && tar --exclude=node_modules -C /src -cf - . | tar -C /app -xf - && cd /app && npm install && npm install-scripts approve argon2 && npm rebuild argon2 && npm test"
```

В PowerShell нужны именно фигурные скобки: запись `$PWD:/src` он читает как переменную с диском и ломает путь. В bash/zsh (Linux, macOS, Git Bash) то же самое с `"$PWD:/src:ro"`; в cmd — `"%cd%:/src:ro"`. Копия в `/app` делается без `node_modules`, поэтому нативные сборки (argon2, sharp) собираются заново под Linux, а ваши Windows-версии остаются нетронутыми.

Если тега `node:26-bookworm-slim` нет — `node:current-bookworm-slim`. Команды Docker в этой документации проверены чтением, не запуском; первый ваш запуск — их проверка.

## Доступ из локальной сети

По умолчанию приложение слушает только `127.0.0.1`: открыть его можно лишь на той же машине. Чтобы коллеги в локальной сети (дом, офис) могли зайти, нужны четыре вещи: слушать внешний адрес, открыть порты в брандмауэре, выпустить сертификат на адрес или имя сервера и разрешить этот адрес для редиректа с HTTP. Порты приложения: HTTPS `9N02` и HTTP `9N01` (только редирект), у workshop это 9002 и 9001. Наружу, в интернет, порты **не пробрасывайте**: для доступа извне используйте VPN.

Дальше в примерах адрес сервера `192.168.1.50`, имя `forge-srv`. Свой адрес покажет `ipconfig` (Windows, строка «IPv4-адрес») или `ip -4 addr` (Linux).

### 1. Слушать адрес локальной сети

В `app.config.js` или переменной окружения:

```js
server: { host: '0.0.0.0', port: 9002, allowedHosts: ['192.168.1.50', 'forge-srv'] }
```

```bash
DAS_HOST=0.0.0.0        # все интерфейсы; или конкретный адрес сетевой карты: DAS_HOST=192.168.1.50
```

`allowedHosts` нужен для редиректа с `http://адрес:9001` на HTTPS: адрес из заголовка `Host` ему доверяют только из этого списка (иначе редирект уводит на `https://localhost:9002`, что у коллеги открывает его собственный компьютер). Если включена почта, в `email.baseUrl` пропишите тот адрес, по которому пользователи открывают приложение: ссылки в письмах строятся из него.

### 2. Открыть порты в брандмауэре

Открывайте только для локальной подсети, а не для всех.

**Windows** (PowerShell от администратора):

```powershell
New-NetFirewallRule -DisplayName "DAS-Forge workshop" -Direction Inbound -Protocol TCP -LocalPort 9001,9002 -Action Allow -Profile Private -RemoteAddress LocalSubnet
# убрать правило:
Remove-NetFirewallRule -DisplayName "DAS-Forge workshop"
```

Профиль `Private` значит, что сеть в Windows названа «Частной». Если она «Общедоступная», правило не сработает: поменяйте тип сети в параметрах Windows или добавьте `Public` в `-Profile`, понимая, что в чужой сети порт будет виден.

**Linux, ufw:**

```bash
sudo ufw allow from 192.168.1.0/24 to any port 9001,9002 proto tcp
sudo ufw status
```

**Linux, firewalld:**

```bash
sudo firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="192.168.1.0/24" port port="9001-9002" protocol="tcp" accept'
sudo firewall-cmd --reload
```

Подсеть (`192.168.1.0/24`) возьмите свою: первые три числа вашего адреса и `/24`. В домашней сети роутеру ничего открывать не нужно: проброс портов нужен только для доступа из интернета, а он здесь не нужен.

### 3. Сертификат на адрес сервера

Сертификат, который создаётся при первом старте, выписан только на `localhost`, `127.0.0.1` и `::1`. По адресу локальной сети браузер покажет предупреждение «имя не совпадает». Выпустите новый, с адресом и именем сервера (приложение при этом остановите, потом запустите снова):

```bash
node bin/app.js cert generate --force --common-name forge-srv --alt-names 192.168.1.50,forge-srv,forge-srv.local
node bin/app.js cert info        # проверьте строку subjectAltName
```

Предупреждение «самоподписанный сертификат» остаётся, пока на каждом компьютере сертификат не добавлен в доверенные: `node bin/app.js cert trust` печатает инструкцию для вашей системы. Для организации лучше сертификат от своего удостоверяющего центра: режим `server.https.mode: 'standalone'` с `certPath` и `keyPath` (см. «Безопасность»).

### 4. Docker

Образ рассчитан на обратный прокси, а `docker-compose.yml` публикует порт только на `127.0.0.1`. Для сети есть два пути.

- **Рекомендуемый: TLS-прокси перед контейнером** (Caddy, nginx, Traefik). Прокси слушает 443 на адресе сервера, отдаёт сертификат организации, ставит `X-Forwarded-Proto` и `X-Forwarded-For` и ходит к `127.0.0.1:9002`. В `docker-compose.yml` ничего менять не нужно, брандмауэр открывает порт 443 для подсети.
- **Напрямую, без прокси** (для проверки): контейнер сам отдаёт HTTPS с самоподписанным сертификатом. В `docker-compose.yml` замените `ports` и `environment`, затем выпустите сертификат на адрес сервера (пункт 3, команда внутри контейнера: `docker compose exec workshop node bin/app.js cert generate --force --common-name forge-srv --alt-names 192.168.1.50,forge-srv`) и перезапустите контейнер:

```yaml
    ports:
      - "9002:9002"
      - "9001:9001"
    environment:
      DAS_HTTPS_MODE: self-signed
      DAS_TRUST_PROXY: "false"
      DAS_SESSION_SECRET_FILE: /run/secrets/session_secret
```

Не открывайте в сеть порт `9002` режима `reverse-proxy` без прокси: по обычному HTTP пароли идут открытым текстом. Порты контейнера публикует Docker, но брандмауэр хоста всё равно должен разрешать их подсети (пункт 2). Docker Desktop в Windows при установке добавляет свои правила, но проверьте, что подсеть не заблокирована.

### Проверка и разбор неполадок

С **другого** компьютера сети:

```powershell
Test-NetConnection 192.168.1.50 -Port 9002        # TcpTestSucceeded : True
curl.exe -k https://192.168.1.50:9002/health      # {"status":"ok"}
```

| Что видно | Причина и что делать |
|---|---|
| таймаут, страница не открывается | брандмауэр сервера (пункт 2) или сеть названа «Общедоступной»; проверьте, что адрес верный |
| «соединение отклонено» | приложение слушает `127.0.0.1` (пункт 1) или не запущено |
| предупреждение «имя не совпадает» | в сертификате нет адреса или имени, по которым открывают (пункт 3) |
| предупреждение «самоподписанный» | ожидаемо; добавьте сертификат в доверенные (`cert trust`) |
| `http://адрес:9001` уводит на `localhost` | адрес не в `server.allowedHosts` (пункт 1) |
| вход не срабатывает по `http://` в Docker | режим `reverse-proxy` без прокси: используйте TLS-прокси или режим `self-signed` (пункт 4) |
| порт занят | `doctor` покажет проверку «Port availability»; смените `server.port` на следующий по схеме |

Команды этого раздела проверены чтением кода и документации, не запуском: в среде разработки нет ни Windows, ни Docker, ни локальной сети. Если что-то из них не работает так, как описано, это находка для документации.

## Резервные копии

Расписание `backup.schedule`, хранение `retentionDays`, шифрование `backup.encryptionKey` (≥ 16 символов, `DAS_BACKUP_KEY`). Приёмники: `local`, `mount` (смонтированная сеть, `markerFile` подтверждает монтирование), `sftp` (отпечаток ключа сервера обязателен) (`s3` и `webdav` пока не поддерживаются, конфигурация с ними отклоняется). Хотя бы одну копию храните вне сервера.

Расписание любой задачи меняется в админке («Задачи»), без правки кода: форма с cron или временем суток, «Вернуть исходное» отменяет изменение. Копию можно проверить кнопкой «Проверить» в «Резервных копиях».

Автобэкап включается, выключается и переносится на другое время суток в админке («Резервные копии»), без правки конфигурации и перезапуска. Каталог локального приёмника, которого ещё нет (до первой копии), диагностика показывает предупреждением, а не ошибкой.

Правила:
1. раз в период проверяйте восстановление: `backup verify <файл>` и пробный `backup restore` на тестовой копии;
2. после восстановления выполните `privacy reapply-erasures`;
3. без `encryptionKey` копии содержат всё открыто — защищайте приёмник.

Восстановление `uploads` после успешного восстановления базы может не удаться: тогда база новая, а файлы прежние. Откат базы ядро не делает, сообщение об ошибке описывает состояние — сверьте каталог вручную и повторите `backup restore`.

## Метрики для Prometheus

В настройках: `observability.metrics.enabled: true` (по умолчанию выключено) и пакет `@prometheus-io/client` (устанавливается вместе с ядром). Эндпоинт `/metrics` отвечает, только если запрос пришёл с адреса из `allowIps` (по умолчанию с этой же машины) или с заголовком `Authorization: Bearer <токен>` (`observability.metrics.token`, от 16 знаков); всем остальным он отвечает 404, как несуществующая страница. Отдаётся: число запросов по методу, шаблону маршрута и классу статуса, длительность запросов, метрики процесса (память, процессор, задержка цикла событий), `das_sessions_active`, `das_mail_queue_pending`, `das_mail_queue_failed`, `das_last_backup_age_seconds` (нет, пока копий нет), `das_bans_active` (действующие блокировки), `das_security_incidents_open` (незакрытые инциденты), `das_alerts_24h` (тревоги за сутки), `das_maintenance_mode` (1 при включённом режиме обслуживания). Показание, чьей таблицы ещё нет, просто не выводится. Прометею нужен доступ по HTTPS к порту приложения: при самоподписанном сертификате укажите в его настройке `tls_config` либо корневой сертификат, либо `insecure_skip_verify` только в доверенной сети. Пример сборщика:

```yaml
scrape_configs:
  - job_name: workshop
    scheme: https
    metrics_path: /metrics
    authorization: { type: Bearer, credentials_file: /etc/prometheus/workshop.token }
    tls_config: { ca_file: /etc/prometheus/workshop-cert.pem }
    static_configs: [{ targets: ['workshop.example.local:9002'] }]
```

Графики запросов и ошибок на «Обзоре» админки работают независимо от метрик. В панелях Grafana используйте источник Prometheus.

## Журналы

Приёмники `logging.sinks`: stdout, файл с ротацией, syslog (udp/tcp/tls), HTTP (ndjson, Loki, Elastic, Splunk HEC). Один приёмник — вне хоста. Потоки: `app`, `access`, `audit`, `security`. Аудит ведётся цепочкой хешей: якорь `audit anchor` храните там, куда сервер не дотянется, сверяйте `audit verify --anchor-id … --anchor-hash …`.

## Алерты

Модуль `alerts` превращает сбой в запись, строку лога и письмо контактам из `security.incidentContacts`, не заваливая почту повторами.

```js
const alerts = alertsModule.createAlerts({ db, email: emailService, contacts: config.security.incidentContacts, logger });
const scheduler = schedulerModule.createScheduler({ onError: alerts.onJobError });
alerts.watch(scheduler, { doctor, doctorSchedule: config.alerts.doctorSchedule, auditSchedule: config.alerts.auditSchedule });
const onLock = alerts.lockoutWatcher({ threshold: 10, windowMs: 10 * 60_000 });
const tracker = http.createFailureTracker({ onLock });   // каждый новый lock-out
alerts.raise({ key: 'my-check', severity: 'critical', title: 'Что случилось', message: 'Подробности' });
```

| Источник | Что считается алертом | Важность |
|---|---|---|
| задача планировщика (`onError`) | задача выбросила ошибку (по расписанию; ручной `runNow` возвращает ошибку вызывающему) | `backup` — критично, остальные — предупреждение |
| `lockoutWatcher` | не меньше `lockouts.threshold` блокировок входа за `lockouts.windowMinutes` (похоже на подбор пароля) | критично |
| `checkAuditChain` | цепочка аудита нарушена (расписание `auditSchedule`) | критично |
| `checkDoctor` | проверка диагностики со статусом «ошибка» (расписание `doctorSchedule`); проверка «Port availability» пропускается | критично |
| `raise` | всё, что вызовет приложение | по аргументу |

Правила: один и тот же `key` в пределах `cooldownMinutes` не отправляется повторно, а увеличивает счётчик `repeats` строки (после перезапуска процесса первое повторение объявляется ещё раз — безопаснее пропуска); письмо идёт через очередь и повторы почты, критичное письмо не режется почасовым лимитом на получателя; сбой письма не теряет алерт и записывается в `notify_error`; `raise` не бросает исключений. Без адресов или при выключенной почте алерты остаются в таблице `alerts`, логе (`warn` или `error`, сообщение `ALERT`) и разделе админки «Алерты». Записи старше `keepDays` удаляет ночная задача. Каждый алерт пишет в аудит `alert.raised`.

Настройка — раздел `alerts` конфигурации (глава «Конфигурация»).

### Как проверить, что алерты работают

В workshop есть рабочий пример: команды `alerts test` и `alerts list` (`examples/workshop/src/alerts-commands.js`, подключены в `bin/app.js`).

```bash
cd examples/workshop
node bin/app.js alerts test --severity critical --message "проверка"   # настоящий алерт
node bin/app.js alerts list                                            # последние алерты
```

1. `alerts test` проходит тот же путь, что и сервер: запись в таблицу `alerts`, строка лога, письмо контактам. Команда сама пишет, было ли письмо: «No mail» значит, что почта выключена или `security.incidentContacts` пуст.
2. С включённой почтой письмо ставится в очередь; доставляет его работающий сервер (цикл очереди). Если сервер остановлен, письмо ждёт в очереди.
3. Откройте админку → «Алерты»: запись видна там, с важностью и признаком «письмо отправлено».
4. Повтор команды с тем же `--key` в другом запуске создаёт новую запись: кеш повторов живёт в памяти одного процесса. Проверить сам кеш можно на работающем сервере или тестом `packages/core/test/alerts.test.js`.
5. Реальные источники проверяются так: задайте копии неверный путь назначения и дождитесь запуска по расписанию (сбой копии — критический алерт); десять блокировок входа за десять минут дают критический алерт; нарушенная цепочка аудита ловится задачей `alerts-audit-chain`.

## Обновление

1. сделайте копию (`backup run`);
2. выкатите новую версию — миграции применяются при старте (или отдельно `migrate`); Перед применением ожидающих миграций ядро само делает согласованную копию базы (`VACUUM INTO` + проверка целостности) в папку `pre-migrate` рядом с файлом базы, хранятся 5 последних; если копию сделать не удалось, ничего не применяется. Откат при неудачной миграции — восстановлением из этой копии.
3. `doctor` и `/health`;
4. при проблеме — откат образа и `backup restore`.

Миграции необратимы: откат кода без отката данных возможен только если схема совместима.

|---|---|
| audit | `npm audit --omit=dev --audit-level=high` (high и critical в рабочих зависимостях) и `npm audit signatures` (подписи реестра у каждого установленного пакета) |
| lockfile | пакеты в `package-lock.json` только из реестра npm по HTTPS и с контрольной суммой (`lockfile-lint`) |
| codeql | статический анализ кода (набор `security-extended`) |
| secrets | `gitleaks` по всей истории: удалённый позже секрет всё равно считается утёкшим |
| image | образ Docker собирается и проверяется Trivy на HIGH и CRITICAL |

Две защиты работают в самом приложении и настраиваются в `auth` и `security`:

- **`/.well-known/security.txt`** (RFC 9116, `security.securityTxt`): исследователь находит, куда написать об уязвимости. Отдаётся только при заданном контакте, срок действия по умолчанию 180 дней от запроса; продлевайте явным `expires`.
- **Вход с нового устройства.** Браузер узнаётся по случайному номеру в cookie `das_device` (в базе только его хеш, `login_devices`), а не по адресу и User-Agent: смена сети не вызывает письма. Первый браузер учётной записи запоминается молча. Вход с другого браузера пишет в аудит `auth.login.new_device` и, если включены почта и `auth.newDeviceNotice`, отправляет владельцу письмо (время, адрес, «Chrome / Windows»). Сбой отправки вход не ломает. Cookie `das_device` перечислена в тексте политики cookie.
- **`auth.hostCookiePrefix`**: cookie сессии `__Host-das_session`. Включайте, когда приложение отдаётся только по HTTPS.

Проверки запускаются на каждый push и pull request и раз в неделю: новые уязвимости появляются без изменений в репозитории. При релизе `release.yml` строит SBOM в формате CycloneDX (`sbom.cdx.json`, рабочие зависимости пакета) и прикладывает его к GitHub Release.

**Шаги вне репозитория (делаются в настройках GitHub и npm):**

1. В `SECURITY.md` замените `<SECURITY_CONTACT>` адресом для сообщений; в настройках репозитория включите *Security → Private vulnerability reporting*.
2. *Settings → Advanced Security*: включите Dependabot alerts и Dependabot security updates, secret scanning и push protection, code scanning.
3. *Settings → Branches*: правило для `main` и `dev` (обязательные проверки `test`, `audit`, `lockfile`, `codeql`; запрет force-push; для `main` pull request).
4. Двухфакторная аутентификация на аккаунте GitHub и npm; для организации — обязательная.
5. Публикация без долгоживущего токена: на npmjs.com у пакета включите *Trusted Publisher* (GitHub Actions, репозиторий, файл `release.yml`), после чего секрет `NPM_TOKEN` не нужен.
6. Если репозиторий принадлежит организации, для `gitleaks` нужен секрет `GITLEAKS_LICENSE`; для личного аккаунта не нужен.
7. Закрепите действия на хеши коммитов: теги в workflow можно переписать, хеш нельзя. Выполните в корне `npx pin-github-action .github/workflows/*.yml`; версию рядом оставьте комментарием, Dependabot будет обновлять оба значения. Так же закрепите точные версии `@cyclonedx/cyclonedx-npm` и `lockfile-lint`, когда убедитесь, что шаги работают.

## Доступ к админке на отдельном адресе

Если задан `server.admin.port` (см. [безопасность](04-security.md)), панель доступна только на этом порту. Пример для сервера в сети: приложение слушает `0.0.0.0:9002`, админка `127.0.0.1:9103`; с рабочего места `ssh -L 9103:127.0.0.1:9103 user@сервер`, затем `https://localhost:9103/admin`. За обратным прокси (режим `reverse-proxy`) проксируйте путь `/admin` на порт админки или не публикуйте его вовсе. Порт админки в Docker не публикуйте наружу (`127.0.0.1:9103:9103` в `docker-compose.yml`).

## Релизы и обновление ядра

Ядро (`@das-forge/core`) публичное и публикуется на npm. Приложения платформы подключают его обычной зависимостью и обновляют обычным `npm update`.

**Какие версии публикуются.** Каждая поставка при разработке повышает патч-номер (0.1.135, 0.1.136…): это промежуточные сборки, они нигде не публикуются. В npm попадают только релизы: версия `x.y.z` без суффикса с записью в `CHANGELOG.md` и тегом `vX.Y.Z`. Номера между релизами пропускаются — это нормально. Пока основная версия 0, поднятие второго числа (0.2.0 → 0.3.0) означает возможные ломающие изменения, третьего (0.2.0 → 0.2.1) — только исправления и совместимые добавления; запись `^0.2.0` в приложении пропускает только исправления.

**Как выпустить релиз** (раз в этап, а не на каждую поставку):

1. `node scripts/version.mjs set 0.2.0`, затем в `CHANGELOG.md` заголовок `## [0.2.0] — дата` с описанием (ломающие изменения — отдельным списком);
2. `npm run release:check` — проверяет версию, запись в CHANGELOG, лицензию и `publishConfig`;
3. закоммитьте, `git tag v0.2.0`, `git push origin v0.2.0`;
4. workflow `.github/workflows/release.yml` повторяет проверки, прогоняет тесты, публикует пакет и создаёт GitHub Release с текстом из CHANGELOG. Для публичного репозитория в npm записывается provenance (подтверждение, что пакет собран из этого коммита); для приватного — публикация без него.

**Разовая подготовка**

1. Зарегистрируйтесь на [npmjs.com](https://www.npmjs.com/signup) и включите двухфакторную аутентификацию (для публикации она обязательна).
2. Создайте организацию `das-forge` (бесплатна для публичных пакетов): так пакет получит имя `@das-forge/core`. Если имя занято, выберите другое — оно прописано в `packages/core/package.json` и в импортах приложений.
3. Создайте токен доступа (Granular access token: Read and write, только пакет `@das-forge/core`, срок — до года) и сохраните его в репозитории GitHub как секрет `NPM_TOKEN` (Settings → Secrets and variables → Actions).
4. Выпустите первый релиз по инструкции выше.

**Как обновить приложение**

1. прочитайте записи `CHANGELOG.md` между вашей и новой версией, особенно «ломающие изменения»;
2. `npm update @das-forge/core` (в пределах `^0.2.0`) или `npm install @das-forge/core@0.3` (смена второго числа);
3. `npm test`, затем «Обновление» выше: копия, выкатка, `doctor`, `/health`;
4. раздел админки «О системе» показывает установленную и последнюю версии пакета в реестре (кнопка «Проверить обновления»).

Закрытые сборки: разработка идёт в приватном репозитории, в публичный попадают релизы вместе с тегами и CHANGELOG.

## Остановка

`registerGracefulShutdown` перестаёт принимать запросы, закрывает потоки SSE событием `shutdown`, ждёт завершения до `shutdownDrainTimeoutMs`. Для Docker `stop_grace_period` ≥ этого значения.

## Сборка и зависимости

- Образ закреплён тегом `node:26-bookworm-slim`; для воспроизводимости закрепите его digest (`FROM node:26-bookworm-slim@sha256:…`) после первой удачной сборки: digest в среде разработки получить нельзя.
- В CI действия (`actions/checkout`, `actions/setup-node`) указаны по тегу `v4`; замена на SHA коммита — на стороне владельца репозитория.
- Лицензия `libheif-js` (LGPL) требует юридической оценки; список лицензий компонентов показывает раздел «О системе»; проверка — `license-checker`.

## Внимание

- Планировщик живёт в процессе: два экземпляра на одной базе запустят задания дважды.
- Не удаляйте `first-run-admin.txt` из каталога данных, не прочитав пароль; после входа — удалить.
- Потеря `sessionSecret` без `previousSessionSecrets` — все выходят из системы; потеря `totpEncryptionKey` — настройка TOTP заново.

## Проверки защищённости установки

Категория «Hardening» диагностики (`health.hardeningChecks`) ищет то, что не ошибка конфигурации, но ослабляет работающую систему. Только чтение, ничего не меняется.

| Проверка | Предупреждение, когда |
|---|---|
| Process user | процесс запущен от root (POSIX) |
| Permissions | файл базы или ключ сертификата доступен группе и остальным (нужно `600`), каталог данных доступен остальным (нужно `750`); на Windows не проверяется |
| Administrators: second factor | у активных администраторов нет аутентификатора |
| Last backup | запись о резервной копии отсутствует или старше 48 ч (позднейшее из последнего запуска задачи `backup` и самого свежего файла копии, поэтому копия, сделанная вручную, тоже учитывается; приложение передаёт второе через `lastBackupAt`) |
| Audit chain check | цепочка аудита не проверялась дольше 72 ч (задача `alerts-audit-chain` или успешная «Проверить цепочку» на странице «Аудит»); диагностика только читает и сама ничего не запускает |
| Proxy trust | `trustProxy: true` (подделка `X-Forwarded-For`), либо `trustProxy` и `https.mode` не согласованы |
| Heap | занято 85% лимита кучи (ошибка с 95%) |
| Event loop | таймер на 20 мс сработал с опозданием больше 200 мс (ошибка с 1 с) |

Проверки собственных заголовков запросом к себе не делаются: для самоподписанного сертификата пришлось бы отключать проверку сертификата, а код ядра этого не делает (это закреплено тестом `security-invariants`).

### Сеть за прокси

`npm` берёт настройки прокси из своей конфигурации, а встроенный `fetch` Node их не видит. Если в «О системе» или в диагностике реестр npm и `nodejs.org` недоступны, причина показана в сообщении и во всплывающей подсказке значка (`ENOTFOUND`, `ETIMEDOUT`, ошибка сертификата). За прокси запускайте приложение с `NODE_USE_ENV_PROXY=1` и `HTTPS_PROXY=http://адрес:порт`; если прокси проверяет TLS своим сертификатом, добавьте `NODE_EXTRA_CA_CERTS=путь\к\сертификату.pem`. Без сети проверка уязвимостей показывает последний удачный результат с датой.

## Проверка уязвимостей

Категория «Dependencies» диагностики (`health.dependencyChecks`, `health.nodeVersionChecks`; включается `security.dependencyAudit`) отвечает на два вопроса: нет ли в установленных пакетах известных уязвимостей и не вышла ли для вашей ветки Node.js новая версия с исправлениями безопасности.

**Как работает.** Список пакетов берётся из `package-lock.json` рядом с приложением (то, что реально установлено, без пакетов для разработки). Он уходит одним запросом в реестр npm (`POST /-/npm/v1/security/advisories/bulk`, тот же источник, что у `npm audit`); совпадение версии с диапазоном уязвимых проверяет `semver`. Процессы не запускаются, `npm` на сервере не нужен.

| Результат | Статус |
|---|---|
| есть уязвимость `critical` или `high` | ошибка; отдельная строка на каждую (имя, версия, номер GHSA, ссылка); алерт критичный |
| `moderate` | предупреждение |
| `low` | перечислена в сводке, статус «ок» |
| принята в `dependencyAudit.ignore` | не учитывается до даты `until` |

**Без сети.** Реестр недоступен — проверка не падает: показывается последний успешный результат с датой (он хранится в базе) и предупреждением «не удалось обновить»; если успешной проверки ещё не было, — «не проверено» с причиной. Причина пишется в журнал. Пустой результат старше последней успешной проверки не выдаётся за «всё хорошо»: в таком случае статус «предупреждение». Без `package-lock.json` проверка тоже честно сообщает «не проверено».

**Версия Node.js.** Версия сверяется с индексом релизов `nodejs.org` (`dist/index.json`): если для вашей ветки есть более новая версия с пометкой «security», выводится предупреждение. Даты окончания поддержки ветки индекс не содержит, их эта проверка не знает. Без сети — предупреждение «не проверено» и запись в журнал.

**Что делать с находкой.** Обновить пакет (`npm update`, для зависимостей ядра — само ядро), а если исправления нет или уязвимость недостижима в вашем приложении, принять её на срок в `security.dependencyAudit.ignore` с причиной и датой пересмотра. Принятие не прячется: в сводке остаётся «N accepted».

**Расписание.** Диагностика запускается сама раз в сутки (`alerts.doctorSchedule`), включается и переносится в разделе «О системе»; результат с ошибками становится алертом. Для проверки в любой момент — кнопка в «О системе» или команда `doctor`. Данные о пакетах уходят в публичный реестр npm: если внешние запросы с сервера нежелательны, выключите проверку (`security.dependencyAudit.enabled: false`) и сверяйте зависимости в CI.
