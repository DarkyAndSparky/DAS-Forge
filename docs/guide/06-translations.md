# Переводы

Как выбирается язык интерфейса, где лежат тексты ядра и приложения, как подключить своё и как не оставить непереведённых строк.

## Принцип

Ядро поставляет значения **по умолчанию**: русские и английские тексты своих страниц (оболочка, админ-панель, политики, страницы ошибок). Приложение **управляет** ими через подключения: добавляет свои тексты, свои подписи меню, свои пространства имён. Тексты приложения живут в приложении, а не в ядре.

| Что | Где живёт | Как менять |
|---|---|---|
| Тексты интерфейса ядра (оболочка, админка, страницы ошибок) | словари `ru`/`en` внутри модулей ядра | не менять; приложение добавляет своё рядом |
| Подписи меню и тексты модулей приложения | `translations` в контракте `Module` | `moduleRegistry.getTranslations()` |
| Подписи ссылок приложения в меню | `extraNav` с объектом `{ ru, en }` | параметр `renderAppShell` |
| Тексты политик (использование, cookie) | таблица `policy_texts` | администратор в разделе «Политики» |
| Все остальные тексты приложения | пространство имён i18next | `i18n.addNamespace()` |

## Выбор языка

`ui.localeMiddleware({ fallback = 'ru', secure = false })` задаёт `req.locale`. Порядок:

1. параметр `?lang=ru|en` в любом адресе. Выбор запоминается в cookie `das_lang` на год (`SameSite=Lax`, `Path=/`, `Secure` при https);
2. cookie `das_lang`;
3. заголовок `Accept-Language` (первый из `ru`/`en`);
4. `fallback`.

Cookie-parser для этого не нужен. Подключайте middleware сразу после идентификатора запроса, до всего, что рендерит страницы (в workshop: `src/server.js`, `app.use(uiModule.localeMiddleware())`).

```js
import { ui } from '@das-forge/core';
app.use(ui.localeMiddleware({ fallback: 'ru', secure: true }));
```

Оболочка, страницы ошибок, политики и админка читают `req.locale` сами. Атрибут `lang` документа совпадает с языком содержимого.

### Переключатель языка

`ui.langSwitchHtml(locale, { param = 'lang', href })` возвращает одну кнопку с флагом **текущего** языка. Нажатие переключает на другой. Работает без JavaScript: это обычная ссылка с `?lang=`. Оболочка (`renderAppShell`) и страницы ошибок уже содержат кнопку; на своих страницах вне оболочки вставляйте её сами:

```js
`<div class="bar">${ui.langSwitchHtml(loc)}${ui.themeToggleHtml(loc)}</div>`
```

Пример: `examples/workshop/src/pages.js`, функция `pageShell`.

## Тексты ядра

Каждый модуль хранит свои словари рядом с кодом: `ru` и `en` с одинаковым набором ключей.

| Модуль | Где | Содержимое |
|---|---|---|
| оболочка | `ui/shell.js`, словарь модулей | подписи меню, `aria-label` |
| страницы ошибок | `http/error-catalog.js` | `ERROR_CATALOG[ru|en][код]` = заголовок, что случилось, подсказка; `home`, `login`, `requestId` |
| админ-панель | `admin/index.js`, `admin/sections*.js` | словари `T` и `L` по разделам |
| политики | `policy/index.js` | `DEFAULT_TEXTS` (редактируются в админке) |
| модальные окна | `ui/modal.js` | «ОК», «Отмена», «Да» по языку документа |

`i18n.coreNamespaces()` возвращает все эти тексты как пространства имён (`admin-overview`, `admin-audit`, `admin-ops`, `admin-appearance`, `accounts` (страницы входа, сброса пароля и «Аккаунт»), `policy-ui`, `policy-defaults`, `errors`, `email`, `ui`). Пространство `ui` — общие элементы страниц: ссылка «К содержимому», подпись навигации, переключатель языка, кнопка темы, кнопки диалогов подтверждения; ключ переопределяется так же: `setTextOverrides({ ui: { en: { skip: 'Jump to content' } } })`. Их можно передать в `createI18n({ namespaces })`, чтобы приложение видело тексты ядра, а проверка полноты (`missingKeys()`) охватывала и их. Тест `i18n-core-catalog.test.js` падает, если в каком-то пространстве ключи `ru` и `en` разошлись или текст пуст — новый текст ядра без перевода не пройдёт.

Страницы входа и аккаунта переименовываются так же: `accounts.mountAccountRoutes({ texts: { ru: { loginTitle: 'Вход в систему' } } })` или `setTextOverrides({ accounts: { en: { loginTitle: 'Welcome' } } })`; ключи — в `ACCOUNT_TEXTS` (`login*`, `forced*`, `forgot*`, `reset*`, `account*`).

Приложение может заменить отдельные тексты ядра, не копируя словарь: `createAdmin({ texts: { 'admin-audit': { en: { audit: 'Journal' } } } })`. Заменяются только указанные ключи, остальные остаются встроенными. Для всего процесса сразу (админка, страницы ошибок, страницы политик, письма): `i18n.setTextOverrides({ errors: { ru: { 404: { title: 'Нет такой страницы' } } }, email: { en: { alert: (d) => ({ subject, lead, body }) } } })` — у ошибок заменяются отдельные поля кода, у писем целиком сценарий (функция); `createAdmin({ texts })` сильнее общих замен. Пример: тест «app overrides of core admin texts» в `packages/core/test/admin-ops.test.js`.

Незнакомый ключ оболочка выводит как есть: видимая ошибка лучше пустой строки.

## Подписи и тексты приложения: контракт Module

Модуль приложения объявляет `translations: { ru: {...}, en: {...} }` и `navigation: [{ path, label, permission }]`, где `label` — ключ из словаря. Реестр собирает словари всех модулей; два модуля не могут задать один ключ разными значениями (ошибка при регистрации).

```js
// examples/workshop/src/modules/reporting-module.js (фрагмент)
translations: { ru: { reporting: 'Отчёты' }, en: { reporting: 'Reports' } },
navigation: [{ path: '/ui/reporting', label: 'reporting', permission: 'read:basic' }],
```

Ссылки приложения вне модулей передаются в оболочку как `extraNav`; подпись может быть объектом:

```js
{ path: '/ui/reports', label: { ru: 'Отчёты', en: 'Reports' }, permission: 'read:finance' }
```

Элемент с `permission` скрыт, если права нет (по умолчанию доступ закрыт). Для строк вне оболочки есть `ui.translate(moduleRegistry, locale, key)`.

## Модуль i18n (на i18next)

Для всех остальных текстов приложения ядро даёт `@das-forge/core/i18n` на **i18next**: пространства имён, подстановки с экранированием HTML, русские формы множественного числа через `Intl.PluralRules`, запасной язык. Библиотека подгружается при первом создании, при импорте ядра не загружается.

```js
import { i18n } from '@das-forge/core';

const t18 = await i18n.createI18n({
  locales: ['ru', 'en'],
  defaultLocale: 'ru',
  namespaces: {
    app: {
      ru: { hello: 'Привет, {{name}}', nav: { home: 'Главная' } },
      en: { hello: 'Hello, {{name}}', nav: { home: 'Home' } },
    },
  },
});

t18.t('en', 'nav.home');                       // 'Home'
t18.t('de', 'nav.home');                       // язык по умолчанию: 'Главная'
t18.t('en', 'hello', { name: '<img onerror=x>' }); // 'Hello, &lt;img onerror=x&gt;'
const t = t18.translator('en', 'app');         // переводчик, привязанный к языку
```

| Метод | Что делает |
|---|---|
| `createI18n({ locales, defaultLocale, namespaces, i18next })` | асинхронно создаёт экземпляр; `defaultLocale` должен входить в `locales` |
| `t(locale, 'ns:key', vars)` | перевод; неизвестный язык заменяется языком по умолчанию, неизвестный ключ возвращается как есть |
| `translator(locale, ns)` | функция `t(key, vars)` для одного языка |
| `addNamespace(ns, { ru, en })` | добавить или расширить пространство (тексты приложения) |
| `missingKeys()` | `[{ ns, key, missingIn }]` — ключи, которых нет хотя бы в одном языке |
| `middleware()` | кладёт `req.t`, `res.locals.t`, `res.locals.locale` по `req.locale`; подключать после `localeMiddleware` |

Подстановки экранируются (`escapeValue: true`): значение из базы нельзя превратить в разметку.

### Тест на полноту

Чтобы непереведённая строка не прошла незамеченной, добавьте в тесты приложения проверку:

```js
expect(t18.missingKeys()).toEqual([]);
```

Примеры, прогоняемые тестами: `packages/core/test/i18n.test.js`.

## Как сейчас переведён workshop

Все страницы workshop берут тексты из каталога (`examples/workshop/src/messages.js`: i18next, пространство `workshop`, ключи вида `login.title`, группы по страницам — `login`, `forced`, `forgot`, `reset`, `account`, `audit`, `system`, `realtime`, `users`, `home`, `reports`). Страница просит слова по ключу, тексты, нужные браузерному скрипту, передаются в него как JSON (`scriptTexts`), подстановки в диалогах делает небольшая функция `fmt` в браузере. Заголовки окон и пункты меню (`APP_NAV`) тоже двуязычные. Подмены готового HTML словарём нет: строка без ключа не может «остаться английской молча», а полноту проверяет тест. Тексты ошибок, которые возвращает JSON API (`data.message`), остаются на языке сервера: перевод ответов API workshop не делает.

Для нового приложения: тексты через каталог (`req.t('ключ')` или, если страницы строятся синхронно, `i18n.createI18nSync({ i18next, namespaces })` и `i18n.translator(locale, 'пространство')`), оба языка в одном пространстве имён, `missingKeys()` в тесте. Образец — `messages.js` и `test/messages.test.js` в workshop.

## Правила для новых текстов

1. Каждый текст сразу на двух языках. Один язык без второго — ошибка.
2. Не склеивайте фразы из кусков: порядок слов в языках разный. Один ключ — одна фраза с подстановкой.
3. Подстановки — только через `{{имя}}`: так значение экранируется.
4. Заголовок страницы (`<title>`), `aria-label`, подсказки и сообщения об ошибках переводятся так же, как текст страницы.
5. Числа и даты форматируйте через `Intl` с языком запроса, а не вручную.
6. Тексты внутри клиентских скриптов передавайте с сервера (атрибут `data-*` или JSON), а не пишите английскими строками в коде скрипта.
7. Текст ошибки API — код ошибки (`INVALID_UPLOAD`), а человекочитаемая подпись берётся из словаря по коду.

## Как добавить третий язык

1. Добавить код в `locales` у `createI18n` и набор ключей во все пространства.
2. Расширить `localeMiddleware`: сейчас он принимает только `ru` и `en` (регулярное выражение cookie и проверка `?lang=` в `ui/locale.js`).
3. Добавить словари в `ERROR_CATALOG`, словари админки и `DEFAULT_TEXTS` политик; таблица `policy_texts` ограничивает язык значениями `ru` и `en` (ограничение `CHECK`), понадобится миграция.
4. Добавить флаг в `ui/lang-switch.js`.

Пока эти места в ядре жёстко задают два языка: третий язык требует правок ядра, а не только приложения.
