# Разработка ядра

## Принципы

1. Ядро выносит общее, чтобы приложения не изобретали одно и то же; по умолчанию даёт рабочее поведение, приложения настраивают его через коннекторы и опции.
2. Администрирование, оформление и учётная запись общие: приложение подключает разделы ядра и расширяет их (`sections`, `texts`), но не делает собственных страниц пользователей, аудита, состояния системы и резервных копий (см. [Администрирование](05-administration.md)).
3. Сначала готовая зависимость из `docs/internal/dependencies-target.md`; собственный код — только с обоснованием.
4. Безопасность по умолчанию: строгие схемы, проверка на сервере, минимум доверия вводу.
5. Каждое изменение с тестом; отрицательные сценарии обязательны.

## Порты

Приложение платформы: HTTPS на `9N02`, HTTP на `9N01` с обязательным перенаправлением на HTTPS; следующее приложение — на 100 больше (workshop 9002/9001, IT Assets 9102/9101, далее 9202/9201 …). Подробности — в «Конфигурации».

## Версия ядра

Единственный источник — `packages/core/package.json`. Из него `CORE_VERSION` (`packages/core/src/version.js`, экспорт ядра) и `scripts/version.mjs`.

```bash
npm run version:get
npm run version:set -- 0.1.111    # package.json, package-lock.json, метки в документации
npm run version:check             # всё согласовано?
```

Метки `<!--core-version-->0.1.413<!--/core-version-->` в документации расставляет и обновляет `version:set` (команда `stamp`). Приложения берут версию из `CORE_VERSION`, а не копируют число.

## Документация

- `docs/guide/*.md` — источник; `docs/index.html` собирается командой `npm run docs` (`scripts/build-docs.mjs`), руками не правится.
- Документация описывает версию ядра из шапки, а не историю: «когда добавлено» — только в `CHANGELOG.md`.
- Шаблон раздела: Назначение, Требования, По умолчанию, API, Пример (из workshop, с путём к файлу), Настройки, Внимание, Тесты.
- `docs/archive/doc-audit.md` — что не покрыто и на что смотреть; `docs/archive/roadmap.md` — исторический, удаляется по исчерпании.

## Зависимости

Node ≥ 26, ESM, Express 5 (peer), Zod 4, argon2id, `node:sqlite`, Vitest 5, i18next. Тяжёлые зависимости (sharp, jsdom, otplib, ssh2, pino) подключаются лениво; тест `lazy-imports.test.js` следит, чтобы ядро грузилось без них.

## Тесты

```bash
npm test                 # ядро и workshop
npm run test:core
npm run test:template     # шаблон приложения против текущего ядра (копия, установка, свои тесты)
npm run test:e2e          # сценарии в браузере (Playwright, Chromium) для workshop
npm run docker:test      # все тесты в чистом Linux-контейнере (Docker)
```

Новая зависимость ядра: запись в `package.json`, описание назначения в `packages/core/src/admin/dependencies.js` (без него упадёт `dependencies.test.js`), затем `npm run docs`: таблица в «Зависимости» собирается сама.

Новый модуль: файл в `packages/core/src/<модуль>/`, экспорт в `index.js`, тест в `packages/core/test/`, строка в «Модули ядра», пример в workshop, если у модуля есть приложение-сторона.

Состояние защиты и очередь доработок перед первым релизом — в [аудите зрелости](../internal/maturity-audit.md).

### Тесты со случайными данными (fast-check)

Обычный тест проверяет примеры, придуманные человеком. Тест «по свойствам» (`packages/core/test/property.test.js`) сам подставляет сотни случайных входов и проверяет, что утверждение верно для всех: «что записали в CSV, то и прочитали», «читалка xlsx на любом мусоре отвечает результатом или `XlsxError`, а не падает», «числовой формат не бросает исключение на любом коде». При провале fast-check сокращает пример до минимального и печатает seed.

- Библиотека (`fast-check`) — зависимость разработки в корне репозитория, ставится вместе с остальными (`npm install`). Если её нет в каталоге (старая копия без установки), эти тесты пропускаются, остальные идут как обычно.
- Повторить найденный случай: `FC_SEED=<seed> npm test`. Больше прогонов: `FC_RUNS=5000 npm test` (по умолчанию 200; в обычном `npm test` случайность каждый раз другая, это нормально).
- Найденный случайным тестом дефект сначала фиксируется обычным тестом с конкретным примером (так сделано для `'=1` в `csv.test.js`), и только потом чинится.
- Где применять: разбор чужих данных (csv, xlsx, документы, форматы), «запись → чтение», проверки прав («без права X никогда не получить Y»). Где не нужно: страницы, сценарии в браузере, всё, что зависит от базы и сети.

### Инварианты безопасности

`security-invariants.test.js` просматривает исходники ядра и падает, если появилось то, чего быть не должно: `eval`, `new Function`, `child_process`, `md5`/`sha1`, отключение проверки сертификата, `innerHTML`, `VACUUM INTO` со значением в тексте запроса, SQL со вставкой значений. Места, где это осознанно допустимо (константный фрагмент, проверенный идентификатор, доверенный SVG), перечислены в тесте с причиной; новое вхождение нужно проверить и добавить туда. Имена файлов резервных копий, приходящие извне, проходят `assertPlainName` (нет разделителей, `..` и NUL).

### Сценарии в браузере (e2e)

Лежат в `examples/workshop/e2e/*.e2e.js` и запускаются Playwright (`npm run test:e2e` из корня). `e2e/start.js` поднимает workshop на пустой временной базе с известным администратором; порт задаёт `E2E_PORT` (по умолчанию 4399). Первый раз нужен браузер: `npx playwright install chromium`.

| Файл | Что проверяет |
|---|---|
| `admin-users.e2e.js` | создание, правка, сброс пароля и удаление учётной записи администратором |
| `admin-sections.e2e.js` | страницы входа и «Забыли пароль», разделы «Задачи», «Почта», «Конфигурация», вкладка «Входы» и экспорт JSON в аудите, режим обслуживания (503 для посетителей, выключение администратором) |

В CI сценарии выполняются на Ubuntu после `npm test` и `npm run test:template`.

### Тесты на PostgreSQL

Пакет `packages/db-postgres` содержит тесты, которые идут против настоящего PostgreSQL. Пока подключение не задано, они **пропускаются** (в выводе строки `↓ … skipped`: это не ошибка, а отсутствие базы). Чтобы они выполнились:

1. Поставьте PostgreSQL (подойдёт любая поддерживаемая версия) и создайте **пустую пробную базу**: тесты перед каждым запуском удаляют и создают заново схему `public`, поэтому рабочую базу указывать нельзя. Например, в `psql` под администратором: `CREATE DATABASE dastest;`.
2. Поставьте драйвер, не записывая его в проект (он необязательная зависимость): в корне репозитория `npm install pg --no-save`. Любой следующий `npm install` или `npm ci` его уберёт, и команду придётся повторить.
3. Задайте адрес базы и запустите тесты пакета.

Windows, PowerShell (пароль и порт подставьте свои):

```
$env:DAS_TEST_POSTGRES_URL = "postgres://postgres:ПАРОЛЬ@127.0.0.1:5432/dastest"
npm test --workspace @das-forge/db-postgres
```

Windows, `cmd`: `set DAS_TEST_POSTGRES_URL=postgres://postgres:ПАРОЛЬ@127.0.0.1:5432/dastest`, затем та же команда. Linux и macOS: `DAS_TEST_POSTGRES_URL=postgres://… npm test --workspace @das-forge/db-postgres`. Если в пароле есть знаки `@ : / # ?`, замените их на `%40 %3A %2F %23 %3F`.

Успешный запуск не показывает `skipped` у файлов `core`, `admin`, `copy`, `tenancy-store`, `entities-migrate`, `more` (около 50 тестов). Без драйвера `pg` и без сервера у `driver.test.js` и `fts.test.js` часть тестов тоже пропускается. Вариант без драйвера `pg` (через сокет Unix, только Linux и macOS): `DAS_TEST_PG_SOCKET_DIR=/var/run/postgresql DAS_TEST_PG_PORT=5432 DAS_TEST_PG_DATABASE=dastest`. Если тесты падают, пришлите первые красные строки: причина чаще всего в неверном пароле, отсутствующей базе `dastest` или несовпадении версии.

### Замечания по типам («храповик»)

Против чего: код на JS размечен типами не везде, замечаний `tsc` сотни, и без контроля их число растёт. Для чего: новый код не должен ухудшать картину. Как: `npm run typecheck` по-прежнему падает только на настоящих ошибках (неизвестное имя, битый импорт), а число остальных замечаний по модулям сравнивает с `scripts/typecheck-baseline.json`: рост в модуле — ошибка, снижение — подсказка обновить базу. База записывается командой `npm run typecheck -- --update` (на той машине, где стоят все зависимости: числа зависят от установленных типов).

### Синхронные вызовы БД (переход на асинхронный слой)

Против чего: ядро работает с SQLite и PostgreSQL, а синхронные `db.get/all/run/exec/transaction` годятся только для SQLite. Для чего: новый код не должен увеличивать долг. Как: `npm run sync-db` печатает число вызовов по модулям; тест `sync-db-ratchet.test.js` (входит в `npm test`) сравнивает число по каждому файлу с `scripts/sync-db-baseline.json` и падает при росте или при новом файле с такими вызовами. В новом коде используйте `asyncDb(db)`. После перевода модуля на асинхронный слой выполните `node scripts/sync-db-report.mjs --update`, чтобы зафиксировать меньшее число.

## Lock-файл

`npm run lock:check` (`scripts/check-lock.mjs`, шаг CI до `npm ci`) сверяет `package-lock.json` с `package.json` всех рабочих пространств: каждая зависимость есть в lock и её версия удовлетворяет диапазону. Добавили зависимость — выполните `npm install` и закоммитьте обновлённый `package-lock.json`, иначе `npm ci` в CI и Docker упадёт.

## Выпуск

Версия — патч за поставку; запись в `packages/core/CHANGELOG.md` с пометкой «Не проверено», что не удалось выполнить в среде разработки; `version:set`, `version:check`, `npm test`.

## Безопасность репозитория и релиза

Что лежит в репозитории: `SECURITY.md` (порядок сообщения об уязвимости, сроки ответа, что входит в область), `.github/dependabot.yml` (еженедельные обновления npm, GitHub Actions и Docker), `.github/workflows/security.yml` (проверки безопасности) и шаг SBOM в `release.yml`.

| Задача `security.yml` | Что проверяет |
|---|---|
| audit | `npm audit --omit=dev --audit-level=high` (high и critical в рабочих зависимостях) и `npm audit signatures` (подписи реестра у каждого установленного пакета) |
| lockfile | пакеты в `package-lock.json` только из реестра npm по HTTPS и с контрольной суммой (`lockfile-lint`) |
| codeql | статический анализ кода (набор `security-extended`) |
| secrets | `gitleaks` по всей истории: удалённый позже секрет всё равно считается утёкшим |
| image | образ Docker собирается и проверяется Trivy на HIGH и CRITICAL |

Две защиты работают в самом приложении и настраиваются в `auth` и `security`:

- **`/.well-known/security.txt`** (RFC 9116, `security.securityTxt`): исследователь находит, куда написать об уязвимости. Отдаётся только при заданном контакте, срок действия по умолчанию 180 дней от запроса; продлевайте явным `expires`. Те же контакты и ссылка на правила показываются людям на публичной странице «О платформе» (`/about`, раздел «Сообщить об уязвимости»: `mountAboutPage(app, { security: appConfig.security.securityTxt })`; Workshop так и делает). Рядом показывается, как сообщить об уязвимости в самой платформе: закрытое сообщение в репозитории ядра на GitHub (`coreSecurityLink: false` убирает эту строку). Если контактов нет, остаётся только строка про платформу.
- **Вход с нового устройства.** Браузер узнаётся по случайному номеру в cookie `das_device` (в базе только его хеш, `login_devices`), а не по адресу и User-Agent: смена сети не вызывает письма. Первый браузер учётной записи запоминается молча. Вход с другого браузера пишет в аудит `auth.login.new_device` и, если включены почта и `auth.newDeviceNotice`, отправляет владельцу письмо (время, адрес, «Chrome / Windows»). Сбой отправки вход не ломает. Cookie `das_device` перечислена в тексте политики cookie.
- **`auth.hostCookiePrefix`**: cookie сессии `__Host-das_session`. Включайте, когда приложение отдаётся только по HTTPS.

Проверки запускаются на каждый push и pull request и раз в неделю: новые уязвимости появляются без изменений в репозитории. При релизе `release.yml` строит SBOM в формате CycloneDX (`sbom.cdx.json`, рабочие зависимости пакета) и прикладывает его к GitHub Release.

**Шаги вне репозитория (делаются в настройках GitHub и npm):**

1. В `SECURITY.md` ядра контакт уже указан (thedasforgeproject@gmail.com); в `SECURITY.md` вашего приложения (шаблон `templates/app/SECURITY.md`) замените `<SECURITY_CONTACT>` адресом автора приложения; в настройках репозитория включите *Security → Private vulnerability reporting*.
2. *Settings → Advanced Security*: включите Dependabot alerts и Dependabot security updates, secret scanning и push protection, code scanning.
3. *Settings → Branches*: правило для `main` и `dev` (обязательные проверки `test`, `audit`, `lockfile`, `codeql`; запрет force-push; для `main` pull request).
4. Двухфакторная аутентификация на аккаунте GitHub и npm; для организации — обязательная.
5. Публикация без долгоживущего токена: на npmjs.com у пакета включите *Trusted Publisher* (GitHub Actions, репозиторий, файл `release.yml`), после чего секрет `NPM_TOKEN` не нужен.
6. Если репозиторий принадлежит организации, для `gitleaks` нужен секрет `GITLEAKS_LICENSE`; для личного аккаунта не нужен.
7. Закрепите действия на хеши коммитов: теги в workflow можно переписать, хеш нельзя. Выполните в корне `npx pin-github-action .github/workflows/*.yml`; версию рядом оставьте комментарием, Dependabot будет обновлять оба значения. Так же закрепите точные версии `@cyclonedx/cyclonedx-npm` и `lockfile-lint`, когда убедитесь, что шаги работают.

## Подготовка репозитория к публикации

В репозитории уже лежат: [README](../../README.md), [LICENSE](../../LICENSE), [SECURITY.md](../../SECURITY.md), [CONTRIBUTING.md](../../CONTRIBUTING.md), [CODE_OF_CONDUCT.md](../../CODE_OF_CONDUCT.md), [SUPPORT.md](../../SUPPORT.md), шаблоны issue (ошибка, предложение; обычные issue без шаблона выключены, уязвимости ведут на приватную форму), шаблон pull request, `.github/CODEOWNERS` (строки закомментированы). Команда `npm run release:check` не выпустит релиз, пока в `SECURITY.md` и `CODE_OF_CONDUCT.md` остаются заглушки `<SECURITY_CONTACT>` и `<CONDUCT_CONTACT>` или нет перечисленных файлов.

**Что остаётся сделать вам (в самом GitHub и в файлах):**
1. Контакты ядра уже подставлены (thedasforgeproject@gmail.com — адрес проекта DAS-Forge). Для приложения на ядре: заменить `<SECURITY_CONTACT>` в `SECURITY.md` шаблона приложения адресом его автора; личные адреса в репозиторий ядра не вносятся.
2. В `LICENSE` заменить «DAS-Forge contributors» на правообладателя, если нужно имя или организация.
3. В `.github/CODEOWNERS` раскомментировать строки и указать владельца.
4. *Settings → General*: описание, сайт (страница документации), темы (topics), включить Discussions и Issues, выключить ненужное (Wiki, Projects); социальный превью-рисунок (*Social preview*).
5. *Settings → Code and automation → Rules*: защита веток `main` и `dev` (см. выше).
6. Добавить метки `bug`, `enhancement`, `question`, `security`, `good first issue`, `documentation`; метки `bug` и `enhancement` используют шаблоны.
7. Проверить, что ссылки в `.github/ISSUE_TEMPLATE/config.yml` ведут на настоящее имя репозитория (сейчас `DarkyAndSparky/DAS-Forge`).
8. Первый релиз: тег `v0.2.0` после `npm run release:check` и записи в CHANGELOG.

## Публикация релиза

Ядро (`@das-forge/core`) публичное и публикуется на npm. Приложения платформы подключают его обычной зависимостью и обновляют обычным `npm update`.

**Какие версии публикуются.** Каждая поставка при разработке повышает патч-номер (0.1.135, 0.1.136…): это промежуточные сборки, они нигде не публикуются. В npm попадают только релизы: версия `x.y.z` без суффикса с записью в `CHANGELOG.md` и тегом `vX.Y.Z`. Номера между релизами пропускаются — это нормально. Пока основная версия 0, поднятие второго числа (0.2.0 → 0.3.0) означает возможные ломающие изменения, третьего (0.2.0 → 0.2.1) — только исправления и совместимые добавления; запись `^0.2.0` в приложении пропускает только исправления.

**Как выпустить релиз** (раз в этап, а не на каждую поставку):

1. `node scripts/version.mjs set 0.2.0`, затем в `CHANGELOG.md` заголовок `## [0.2.0] — дата` с описанием (ломающие изменения — отдельным списком);
2. `npm run release:check` — проверяет версию, запись в CHANGELOG, лицензию и `publishConfig`;
3. закоммитьте, `git tag v0.2.0`, `git push origin v0.2.0`;
4. workflow `.github/workflows/release.yml` повторяет проверки, прогоняет тесты, публикует пакет и создаёт GitHub Release с текстом из CHANGELOG. Для публичного репозитория в npm записывается provenance (подтверждение, что пакет собран из этого коммита); для приватного — публикация без него.

**Разовая подготовка**

1. Зарегистрируйтесь на [npmjs.com](https://www.npmjs.com/signup) и включите двухфакторную аутентификацию (для публикации она обязательна).
2. Создайте организацию `das-forge` (бесплатна для публичных пакетов): так пакет получит имя `@das-forge/core`. Если имя занято, выберите другое — оно прописано в `packages/core/package.json` и в импортах приложений.
3. Создайте токен доступа (Granular access token: Read and write, только пакет `@das-forge/core`, срок — до года) и сохраните его в репозитории GitHub как секрет `NPM_TOKEN` (Settings → Secrets and variables → Actions).
4. Выпустите первый релиз по инструкции выше.

Закрытые сборки: разработка идёт в приватном репозитории, в публичный попадают релизы вместе с тегами и CHANGELOG.
