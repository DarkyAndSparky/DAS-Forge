# Разработка ядра

## Принципы

1. Ядро выносит общее, чтобы приложения не изобретали одно и то же; по умолчанию даёт рабочее поведение, приложения настраивают его через коннекторы и опции.
2. Администрирование, оформление и учётная запись общие: приложение подключает разделы ядра и расширяет их (`sections`, `texts`), но не делает собственных страниц пользователей, аудита, состояния системы и резервных копий (см. [Администрирование](05-administration.md)).
3. Сначала готовая зависимость из `docs/dependencies-target.md`; собственный код — только с обоснованием.
4. Безопасность по умолчанию: строгие схемы, проверка на сервере, минимум доверия вводу.
5. Каждое изменение с тестом; отрицательные сценарии обязательны.

## Порты

Приложение платформы: HTTPS на `9N02`, HTTP на `9N01` с обязательным перенаправлением на HTTPS; следующее приложение — на 100 больше (workshop 9002/9001, IT Assets 9102/9101, далее 9202/9201 …). Подробности — в «Конфигурации».

## Версия ядра

Единственный источник — `packages/core/package.json`. Из него `CORE_VERSION` (`packages/core/src/version.js`, экспорт ядра) и `scripts/version.mjs`.

```bash
npm run version:get
npm run version:set -- 0.1.111    # package.json, package-lock.json, метки в документации
npm run version:check             # всё согласовано?
```

Метки `<!--core-version-->0.1.274<!--/core-version-->` в документации расставляет и обновляет `version:set` (команда `stamp`). Приложения берут версию из `CORE_VERSION`, а не копируют число.

## Документация

- `docs/guide/*.md` — источник; `docs/index.html` собирается командой `npm run docs` (`scripts/build-docs.mjs`), руками не правится.
- Документация описывает версию ядра из шапки, а не историю: «когда добавлено» — только в `CHANGELOG.md`.
- Шаблон раздела: Назначение, Требования, По умолчанию, API, Пример (из workshop, с путём к файлу), Настройки, Внимание, Тесты.
- `docs/doc-audit.md` — что не покрыто и на что смотреть; `docs/roadmap.md` — исторический, удаляется по исчерпании.

## Зависимости

Node ≥ 26, ESM, Express 5 (peer), Zod 4, argon2id, `node:sqlite`, Vitest 5, i18next. Тяжёлые зависимости (sharp, jsdom, otplib, ssh2, pino) подключаются лениво; тест `lazy-imports.test.js` следит, чтобы ядро грузилось без них.

## Тесты

```bash
npm test                 # ядро и workshop
npm run test:core
npm run test:template     # шаблон приложения против текущего ядра (копия, установка, свои тесты)
npm run test:e2e          # сценарии в браузере (Playwright, Chromium) для workshop
npm run docker:test      # все тесты в чистом Linux-контейнере (Docker)
```

Новая зависимость ядра: запись в `package.json`, описание назначения в `packages/core/src/admin/dependencies.js` (без него упадёт `dependencies.test.js`), затем `npm run docs`: таблица в «Зависимости» собирается сама.

Новый модуль: файл в `packages/core/src/<модуль>/`, экспорт в `index.js`, тест в `packages/core/test/`, строка в «Модули ядра», пример в workshop, если у модуля есть приложение-сторона.

Состояние защиты и очередь доработок перед первым релизом — в [аудите зрелости](../maturity-audit.md).

### Инварианты безопасности

`security-invariants.test.js` просматривает исходники ядра и падает, если появилось то, чего быть не должно: `eval`, `new Function`, `child_process`, `md5`/`sha1`, отключение проверки сертификата, `innerHTML`, `VACUUM INTO` со значением в тексте запроса, SQL со вставкой значений. Места, где это осознанно допустимо (константный фрагмент, проверенный идентификатор, доверенный SVG), перечислены в тесте с причиной; новое вхождение нужно проверить и добавить туда. Имена файлов резервных копий, приходящие извне, проходят `assertPlainName` (нет разделителей, `..` и NUL).

### Сценарии в браузере (e2e)

Лежат в `examples/workshop/e2e/*.e2e.js` и запускаются Playwright (`npm run test:e2e` из корня). `e2e/start.js` поднимает workshop на пустой временной базе с известным администратором; порт задаёт `E2E_PORT` (по умолчанию 4399). Первый раз нужен браузер: `npx playwright install chromium`.

| Файл | Что проверяет |
|---|---|
| `admin-users.e2e.js` | создание, правка, сброс пароля и удаление учётной записи администратором |
| `admin-sections.e2e.js` | страницы входа и «Забыли пароль», разделы «Задачи», «Почта», «Конфигурация», вкладка «Входы» и экспорт JSON в аудите, режим обслуживания (503 для посетителей, выключение администратором) |

В CI сценарии выполняются на Ubuntu после `npm test` и `npm run test:template`.

## Lock-файл

`npm run lock:check` (`scripts/check-lock.mjs`, шаг CI до `npm ci`) сверяет `package-lock.json` с `package.json` всех рабочих пространств: каждая зависимость есть в lock и её версия удовлетворяет диапазону. Добавили зависимость — выполните `npm install` и закоммитьте обновлённый `package-lock.json`, иначе `npm ci` в CI и Docker упадёт.

## Выпуск

Версия — патч за поставку; запись в `packages/core/CHANGELOG.md` с пометкой «Не проверено», что не удалось выполнить в среде разработки; `version:set`, `version:check`, `npm test`.
