# Зависимости

Что ядро тянет за собой, зачем, и как за этим следить. Таблицы ниже **собираются из `package.json`** командой `npm run docs` (`scripts/deps-table.mjs`), поэтому не расходятся с кодом; текст вокруг них — ручной. Решения «брать пакет или писать своё» и история подключений — в [целевых зависимостях](../dependencies-target.md).

## Где это видно в работающем приложении

Раздел админки «О системе» (`/admin/about`) показывает две таблицы: зависимости приложения и зависимости ядра (`@das-forge/core`), для каждой — требуемая и установленная версия, лицензия, а у пакетов ядра ещё и назначение. Кнопка «Проверить обновления» спрашивает у npm последние версии и отмечает отстающие. Обновления зависимостей приложения даются готовой командой `npm install …`; зависимости ядра обновляются вместе с ним (`npm update @das-forge/core`), поэтому для них команда не предлагается. Подробнее — [Администрирование](05-administration.md).

## Правила

1. Новый пакет в ядро — только с записью о назначении в `packages/core/src/admin/dependencies.js`; тест `dependencies.test.js` не пропустит пакет без описания, а `npm run docs` покажет «НЕ ОПИСАН».
2. Тяжёлые и редко нужные пакеты грузятся лениво (колонка «по требованию»); тест `lazy-imports.test.js` следит, чтобы ядро запускалось без них.
3. Версии в `package.json` — не ниже тех, что стоят в проверенном `package-lock.json`; `npm run lock:check` сверяет их.
4. Уязвимости: категория «Dependencies» диагностики doctor сверяет `package-lock.json` с базой советов (advisory) реестра npm, откуда берёт данные и `npm audit` (см. «Проверка уязвимостей» в [Эксплуатации](10-operations.md)); `overrides` в корневом `package.json` закрывают транзитивные пакеты (таблица ниже). Приложению, которое ставит ядро отдельно, нужны такие же `overrides` или свежий `npm audit fix`.

## Лицензии

Лицензии производственных зависимостей проверяет команда `app deps licenses` (она же шаг сборки на GitHub): вердикт `ok` для разрешённых лицензий, `REVIEW` для остальных, `UNKNOWN` когда лицензия не указана. Из 284 производственных пакетов (на 0.1.271) почти все разрешены по умолчанию (MIT, ISC, BSD, Apache-2.0 и подобные). Два семейства пакетов проверены вручную и разрешены явно (`--allow LGPL-3.0,LGPL-3.0-or-later`):

| Пакет | Лицензия | Как используется |
|---|---|---|
| `@img/sharp-libvips-*`, `@img/sharp-*` (через `sharp`) | LGPL-3.0-or-later | готовые двоичные библиотеки libvips, подгружаются как есть, без изменений |
| `libheif-js` | LGPL-3.0 | WASM-декодер HEIC, подключается как библиотека без изменений |

Это решение принято при разборе (G-07), юридическую оценку для вашего способа распространения нужно подтвердить отдельно: LGPL допускает использование библиотеки в программе под другой лицензией при условии неизменённой библиотеки и сохранения лицензионных уведомлений. Новый пакет с LGPL, GPL, AGPL или MPL в эту таблицу сам не попадёт: его нужно разобрать и дописать сюда.
