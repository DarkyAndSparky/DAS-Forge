# Бюджет производительности (G-12)

Замер: node 22, `node:sqlite`, база в памяти, 1 000 000 строк `audit_log` (160 тыс. строк в год при 25 с между записями), после `ANALYZE`. Одна страница = 50 записей. Измерено в песочнице разработки (не на целевом сервере) — порядок величин, не гарантия; повторить можно `node scripts/audit-bench.mjs`.

| Фильтр | План | Время |
|---|---|---|
| последние 50 | первичный ключ | 1 мс |
| `actor` | `idx_audit_log_actor` | 1 мс |
| `action` (частое значение) | `idx_audit_log_action_created` + временная сортировка | 162 мс |
| `action` префикс / содержит | скан в порядке `id` с остановкой на 50 | 0–1 мс, если совпадения частые; ~74 мс, если нет совпадений |
| `entity` + `entityId` | `idx_audit_log_entity` | 1 мс |
| `since`/`until` (сутки) | `idx_audit_log_created_iso` | 3 мс |
| `requestId` | полный скан | 55–63 мс |
| `result` (редкое значение) | полный скан | 57 мс |
| `count` (все / по действию / за сутки) | — | 2 / 5 / 1 мс |

## Решение
Бюджет: страница журнала с любым фильтром — до 0,5 с на 1 млн строк. Укладываемся с запасом, поэтому **схему не меняем**: индексы на `request_id` и `result` ускорили бы запись каждой строки аудита ради выигрыша в десятки миллисекунд. Вернуться к вопросу, если замер на реальных данных покажет > 0,5 с или журнал вырастет на порядок.

Страховка от случайной регрессии: `test/audit-query-plan.test.js` проверяет, что фильтры `actor`, `action`, `entity+entityId`, `since/until` остаются на индексе.

## Не измерено
- Реальный сервер и диск (замер в памяти).
- Заполненные `meta` (в замере `{}`) и параллельная запись во время чтения.
- Страницы админки целиком (`admin/sections.js`): измерены только запросы к аудиту.
