Аудит ядра перед Stage F — находки, требующие доработки

Версия ядра на момент аудита: 0.1.23. Аудит проведён по коду, без запуска сервера (в песочнице нет сети: argon2/sharp/zod недоступны).

Как читать этот файл

  • Стадии — разные фокусы: A безопасность и auth, B данные и надёжность, C runtime и операции, D контракты/тесты/репозиторий/готовность к портированию. Каждая стадия прогонялась независимо, затем дубли объединены (в находке указано «см. также»).
  • Статус проверки: ✔ проверено — я лично перечитал указанный код после отчёта аудитора; ○ по отчёту — найдено при аудите чтением кода, но не перепроверено вторым проходом. Ни одна находка не подтверждена запуском. Находки про поведение Node/SQLite/браузера (отмечены «не проверено запуском») — гипотезы, пока их не воспроизвели.
  • Серьёзность: critical / high / medium / low / info.
  • Статусы работ: см. раздел «Статус исправлений на 0.1.70» ниже сводной таблицы; тексты находок в стадиях сохранены как были при аудите (0.1.23).
  • Пути относительно корня репозитория; core/ = packages/core/src/, ws/ = examples/workshop/src/.

Вывод одной строкой

Портировать рано. Не потому, что ядро плохое, а потому, что обещанное в конфиге и roadmap местами не подключено (CSRF, rate-limit, HTTPS, trust proxy, лимиты тела — только поля схемы), единственный HTTP-тест — фейковый Express, а бэкап/restore небезопасны для живой WAL-базы. Из четырёх приложений технически начать можно только it-assets; остальным не хватает пакетов (email, ldap, network, documents).

Стадия A — аутентификация и безопасность

A01 · high · CSP script-src 'self' ломает все страницы workshop с inline-скриптами

Статус: исправлено в 0.1.25.
  • Доказательство ✔: core/http/bootstrap.js:24-37 (script-src 'self', без nonce); ws/server.js:46 подключает securityHeaders() глобально; ws/pages.js:78,149,191,370,418 — inline <script> на login/account/system/realtime.
  • Почему важно: в браузере с CSP эти страницы не работают, включая логин и TOTP. Реальные приложения будут ослаблять CSP до unsafe-inline и потеряют обещание §4.5h п.5. Тесты это не ловят (см. D01).
  • Исправление: вынести скрипты в assets/*.js под 'self' либо nonce на запрос (res.locals.cspNonce + pageShell). Добавить e2e-тест на заголовок и отсутствие inline-скриптов.

A02 · high · Нет защиты от перебора (rate-limit, lockout)

Статус: исправлено в 0.1.25.
  • Доказательство ✔: rateLimit встречается только в core/config/schema.js; /login* в ws/routes.js:157,226,250 без ограничений; app user unlock не реализован (core/cli/commands/user-admin.js:95-97); docs/roadmap.md:3516 прямо пишет, что express-rate-limit не используется. ○ по отчёту: pending-MFA сессия не сжигается после неверного кода (ws/routes.js:233-236); окно TOTP ±1 (core/auth/totp.js:75-88).
  • Почему важно: пароль и 6-значный TOTP перебираются без лимита; recovery-код — 40 бит, тоже без лимита.
  • Исправление: rate-limit по IP и по логину; счётчик неудач + экспоненциальная пауза в core/auth; сжигать pending-сессию после 3–5 неверных кодов; реализовать user unlock.

A03 · high · CSRF-защиты нет, хотя security.csrf по умолчанию true

Статус: исправлено в 0.1.25.
  • Доказательство ✔: core/config/schema.js:85 (csrf: true); других упоминаний CSRF в core/ и ws/ нет, кроме тестов и CLI. Защита — только SameSite=Lax (core/http/session-middleware.js:35). ○ POST /assets/:id/logo принимает любой Content-Type через express.raw({type:()=>true}) (ws/routes.js:698).
  • Почему важно: Lax не закрывает same-site атаки (поддомены); конфиг создаёт ложное чувство защищённости.
  • Исправление: CSRF-токен в сессии + проверка Origin/Sec-Fetch-Site на всех не-GET; для /logo требовать конкретный Content-Type. Либо убрать поле из схемы до реализации.

A04 · high · HTTPS не реализован, trust proxy не выставляется

Статус: исправлено в 0.1.25.
  • Доказательство ✔: ws/server.js:66 — голый app.listen(port) без host; trust proxy нигде не вызывается; cookie ставится с secure: req.secure (ws/routes.js:207,217,244,265); config/schema.js:32 (trustProxy) читается и не применяется.

  • Исправление: core/http.createServer(app, config) — учитывает host, https-режим (certs), trust proxy, timeouts; Secure принудительно в production; редирект на HTTPS + HSTS.

Стадия B — данные и надёжность

B01 · CRITICAL · Бэкап — copyFileSync живой WAL-базы

Новое требование: отправка логов за пределы машины (проект)

Владелец хочет задавать, куда уходят логи: при взломе хоста локальные логи удаляют. Сейчас: core/logs (pino) пишет JSON-строки в stdout/stderr (logs/logger.js:defaultDestination) или в любой переданный stream; приёмников, буфера и доставки нет. Хеш-цепочка аудита уже умеет anchor(db) и verifyChain(db, {anchor}) (audit/chain.js), но никто не отправляет «голову» цепочки наружу.

Предложение (без новых зависимостей, поверх pino.multistream и встроенных node:net, node:tls, node:dgram, fetch):

"logging": {
  "level": "info",
  "sinks": [
    { "type": "stdout" },
    { "type": "syslog", "host": "logs.example.com", "port": 6514, "protocol": "tls", "ca": "/etc/ca.pem", "streams": ["app","access","audit","security"] },
    { "type": "http", "url": "https://loki.example.com/loki/api/v1/push", "format": "loki", "headers": { "Authorization": "env:LOKI_TOKEN" } },
    { "type": "file", "path": "/mnt/logs-share/das.log" }
  ],
  "buffer": { "maxLines": 10000, "maxAgeSec": 300, "onFull": "drop-oldest" },
  "localFallback": { "path": "data/logs/fallback.ndjson", "maxBytes": 52428800 }
}
  • Приёмники: stdout (для Docker log driver — лучший вариант: драйвер сам отправляет на удалённый сервер), syslog (RFC 5424 по UDP/TCP/TLS), http (JSON/NDJSON, Loki/Elastic/ Splunk HEC/Vector), file (на смонтированный сетевой путь).
  • Поведение при сбое: запись логов никогда не блокирует запрос; ограниченный буфер в памяти, повторные попытки с экспоненциальной паузой, при переполнении — отбрасывание старых строк со счётчиком droppedLogLines в /health; локальный резервный файл с лимитом размера (0600).
  • Секреты в конфиге — только ссылками на переменные окружения (env:NAME); редакция секретов выполняется до отправки (общая для всех приёмников).
  • Маршрутизация по потокам: app, access, audit, security (входы, отказы, смена ролей) — у каждого приёмника список streams.
  • Аудит: событие audit дублируется в приёмник в момент записи; плюс периодическая задача отправляет anchor(db) (id + хеш головы цепочки) наружу; CLI-команда audit verify --anchor <из удалённого лога> проверяет, что хвост не усечён и история не переписана.
  • Бэкапы: та же угроза (L01) — удалённый приёмник бэкапов (SFTP/S3-совместимый или копия на отдельный смонтированный диск) выбирается тем же решением владельца.
  • Тесты: локальный TCP/UDP/HTTP-сервер в тесте, симуляция отказа приёмника (буфер, отбрасывание, восстановление), редакция до отправки, форматы RFC 5424 и Loki.
  • Оценка: 0.1.7x — sinks + stdout/file + буфер; следующая версия — syslog/TLS; следующая — http (Loki/NDJSON) и отправка anchor.
