Аудит проверки входных данных, схем Zod и zero-trust (на 0.1.289; статус после 0.1.293)

Метод: чтение кода и поиск по packages/core/src (grep по req.body, req.query, req.params, JSON.parse, process.env, заголовкам; чтение выбранных функций). Код не менялся, динамических проверок нет (в песочнице нет express, zod, vitest): все выводы NOT VERIFIED на уровне запуска, VERIFIED на уровне чтения кода. Это первый проход; не охвачено то, что перечислено в конце.

Что устроено хорошо (подтверждено чтением)

  • Все 13 POST-маршрутов accounts/index.js (вход, регистрация, пароль, TOTP, коды восстановления) проходят http.validateBody(Схема); схема на сервере всегда перепроверяет вход, ошибка уходит в едином формате VALIDATION_ERROR.
  • Конфигурация (config/schema.js): z.strictObject везде (28 вхождений), опечатка в ключе не проходит молча.
  • Заголовок Host проверяется по списку разрешённых (http/server.js), CSRF сверяет Origin/X-Forwarded-Host только при включённом trustProxy (http/csrf.js).
  • Адреса возврата safeNext (admin/step-up.js) и safeBack (policy/index.js) допускают только путь на этом же сайте, не //host и не \.
  • Все 10 разобранных JSON.parse из БД защищены: либо try/catch с запасным значением, либо проверка каждого поля по типу (announcement, maintenance, task-schedules, schedule-setting, курсор страниц, мета аудита).
  • Запросы к БД только константами и ?; адреса из настроек проходят проверку SSRF (http/outbound.js).

Статус и пересмотр V-01

После 0.1.291 сделано: V-02 (форма всегда текст), V-04 (общий parseId), V-07 (z.email()/z.url()), V-08 (тесты в security-invariants: req.body читается только в четырёх проверенных местах, а в accounts каждый POST с req.body стоит после validateBody). Остаются V-01 и V-06. При втором чтении выяснилось, что формы админки не «без проверки»: у каждой есть своя ручная (String, trim, сравнение с константой, normalizeBanValue, setText), и ни одного места, где значение попадает в SQL или страницу сырым, не найдено. Перевод всех ~50 форм на Zod без изменения поведения вручную без возможности запустить zod и vitest — риск регрессий выше пользы. Предложение: оставить как есть и переводить формы на схемы по мере правок конкретного раздела.

V-06: что сделано (0.1.293)

Сессия: строка, которая не JSON-объект, удаляется, посетитель входит заново (раньше ошибка на каждый запрос). Очередь писем: повреждённое тело сразу failed с кодом BAD_PAYLOAD, без отправки и повторов. Политика паролей: при чтении из БД число принимается только в тех границах, что проверяет set() (минимум 8 знаков и т. д.); иначе берётся значение из конфигурации. Последнее было настоящим пробелом: подменённая запись minLength: 1 молча ослабила бы политику.
