0. АКТУАЛЬНЫЙ ПЛАН (читать в первую очередь при возобновлении работы)

Всё, что ниже раздела 0, — исторический документ Phase 1 (изначальная архитектура, как её спроектировали до начала кодинга) + журнал решений Phase 2 по ходу разработки (разделы 10–17). Он ценен как архив рассуждений, но не отражает текущий план актуально и компактно — например, раздел 2 ниже описывает полный пакетный набор (cli, ui, email, ldap, files, ...) и pnpm-workspace.yaml, тогда как по факту реализован пока только packages/core на npm workspaces (не pnpm — решение изменилось по ходу дела). Этот раздел 0 — единственный источник истины о текущем состоянии; остальное читать для археологии решений, а не как актуальное описание.

Полный, построчный справочник (путь → что внутри → статус ✅/⚠️/пусто), по тому же принципу, что и справочник CLI-команд (§4.1/README/ docs/index.html #cli) — ведётся как отдельная единица документации, обновляется каждым патчем, меняющим набор файлов/папок, а не переписывается с нуля. Источник истины — README.md, раздел "Структура репозитория — полный справочник" и зеркально docs/index.html (#packages); здесь — только верхнеуровневая карта и примечания, не дублирующие построчную таблицу:

1. Принцип (историческое, Phase 1)

DAS-Forge — не фреймворк, диктующий структуру приложения, а набор пакетов общей инфраструктуры. Бизнес-логика, доменные модели и специфичные для приложения схемы БД остаются в приложениях. Ядро не должно знать, что такое Atlas, procure-it и т.д. — оно оперирует только контрактами (ApplicationConfig, Module, DatabaseAdapter, ...).

Хорошая новость по данным

Реальных живых продакшн-данных в текущем виде фактически нет — сейчас это таблицы, наполненные через Excel-импорт, а не боевые системы с историей. Это меняет приоритет: миграция схем — не риск, а шанс спроектировать core/database-конвенции (структура таблиц sessions/audit/users) с нуля правильно, без оглядки на четыре несовместимых легаси-формата. Не нужно закладывать сложный data-migration слой в Phase 1 — это можно будет сделать проще, чем казалось.

Версионирование core между 4 потребителями

Раз @das-forge/* — общие npm-пакеты, а 4 приложения будут обновляться на них не синхронно (it-assets раньше, atlas позже), core с первого релиза живёт по semver: breaking change в контракте (AuthProvider, Module API) — всегда major-бамп, и CHANGELOG.md самого DAS-Forge (тот же паттерн Keep a Changelog, что уже принят для приложений, §6.6.2) — обязателен с первого коммита, не как формальность на будущее.

node:sqlite и многопроцессный доступ — проверить, не считать очевидным

CLI (app backup create, app db integrity) работает в отдельном процессе от запущенного сервера, одновременно обращаясь к тому же файлу БД. Перед тем как фиксировать core/database как финальный контракт (Phase 1) — нужно явно протестировать поведение node:sqlite в этом сценарии (WAL-режим, блокировки при параллельной записи), а не считать "наверное, само справится".

Контракт паролей / миграция легаси-хэшей

Каждое приложение сейчас хранит пароли по-своему (PBKDF2 у procure-it, scrypt у atlas и net-monitor, argon2/bcrypt-микс у it-assets). Core должен поддерживать multi-scheme verify на переходный период:

verifyPassword(hash, plain)
  → detect scheme by hash prefix/format
  → verify with legacy scheme if matched
  → if valid: rehash with argon2id, persist new hash (lazy migration)
  → else: verify with argon2id

Так миграция происходит на первом успешном логине пользователя, без принудительного сброса паролей всей базы.

Базовые роли (RBAC baseline)

Core поставляет три базовые роли, одинаковые по смыслу во всех 4 приложениях. Приложение может добавлять свои роли/права поверх, но эти три — платформенный минимум, не переизобретаются каждым проектом заново:

guest      (без логина, публичный доступ)
  → read-only: дашборды и явно помеченные как публичные разделы
  → не видит Administration вообще, не имеет сессии

operator
  → всё, что guest, плюс:
  → создание/редактирование/изменение бизнес-сущностей (заявки, активы, устройства...)
  → НЕ имеет доступа к Administration (§4.5g) и к management-функциям (backup/users/secrets)

admin
  → всё, что operator, плюс:
  → полный доступ к Administration: backups, cron, secrets, security/bans, users, audit
  → может выдавать роли другим пользователям

authorization.can(user, 'resource:action') резолвит право сначала по роли, потом по точечным override'ам (если приложению нужно выдать конкретному operator доступ к одному разделу Administration — например, admin.health.view, как обсуждали ранее, — без полного admin). Роль — это набор permissions по умолчанию, а не жёстко зашитая проверка if (role === 'admin') в каждом месте кода.

Расширяемая матрица прав — custom-роли поверх базовых трёх

3 базовые роли — минимум, не потолок. Приложение (или админ через UI, не только через код) может определить дополнительные роли как наборы permissions, а не хардкодить новые if:

authorization.defineRole('warehouse-clerk', {
  extends: 'operator',                          // наследование от базовой роли
  grants: ['assets.viewFinancials'],             // точечные добавления
  revokes: ['assets.delete']                     // точечные ограничения
});

Admin UI: Administration → Roles & Permissions — матрица "роль × permission" с чекбоксами (по столбцам — все зарегистрированные модулями permissions, включая fieldPermissions из §4.5j), создание custom-роли через ту же форму, не через правку кода. Хранится в БД (core/database), не в конфиг-файле — иначе смена прав требует деплоя.

First-run bootstrap: администратор создаётся автоматически

При старте core проверяет количество пользователей в БД. Если пользователей ноль (первый запуск после app install / после db migrate на чистой БД):

1. core генерирует учётку с ролью admin (логин по умолчанию — `admin`,
   либо из ADMIN_EMAIL/ADMIN_USERNAME, если задан в .env)
2. генерирует случайный временный пароль (криптостойкий, не "admin123")
3. печатает его ОДИН РАЗ в stdout/лог при первом запуске крупным блоком,
   не сохраняет в plaintext нигде на диске:

   ┌─────────────────────────────────────────────┐
   │  Initial admin account created                │
   │  Login:    admin                              │
   │  Password: 7f2a-9c31-e8b4-... (temp)          │
   │  You MUST change this password on first login │
   └─────────────────────────────────────────────┘

4. учётка помечена флагом mustChangePassword: true — любой запрос,
   кроме смены пароля, редиректится/блокируется, пока пароль не сменён

Это тот же принцип, что и app user create-admin --temp (§4.5g, п.2), но срабатывает автоматически при первом старте, а не только по явной команде — create-admin остаётся резервным путём на случай, если что-то пошло не так (лог с паролем потерян, БД пересоздана без пересоздания консоли и т.п.).

4.2 Конвенции вывода и кодов выхода

Единые для всех приложений на платформе (в этом и весь смысл @das-forge/cli):

  • Формат вывода: человекочитаемый текст по умолчанию, --json — везде, где команда возвращает структурированные данные (для скриптов/мониторинга).
  • Exit codes: 0 — успех, 1 — ожидаемая ошибка (например, pending migrations при db status --strict), 2 — конфигурационная ошибка (невалидный app.config.js), 3 — окружение не готово (doctor нашёл критичные проблемы).
  • Логирование CLI идёт через тот же pino-инстанс, что и сервер, но в pretty-режиме по умолчанию в терминале.
  • Единая обработка ошибок: любая необработанная ошибка команды — это AppError из core, а не голый stack trace в консоли пользователя.

4.3 Backup/restore как оркестрированный workflow

app backup restore <file> — это не один SQL-запрос, а пайплайн, который CLI выполняет пошагово, останавливаясь на первой ошибке:

verify backup → stop writes → restore → integrity check
    → migration check → audit entry → health check → отчёт

Каждый шаг печатается с ✓/✗, при ошибке — откат к состоянию до restore там, где это технически возможно (файловая копия перед restore).

4.4 Команды регистрируются модулями

Как и UI, CLI расширяемый: @das-forge/ldap может зарегистрировать app ldap test-connection, приложение — свои project-level команды (atlas import, assets sync). Core-команды (db/backup/health/doctor/ service) одинаковы во всех 4 приложениях по определению — это и есть единый UX, ради которого всё затевалось.

4.5a Кроссплатформенность и Docker — обязательное требование core

Не опция "было бы неплохо", а требование к каждому модулю core с первого коммита: всё, что попадает в @das-forge/core/@das-forge/cli, обязано работать одинаково в трёх средах — Linux, Windows, Docker — без platform-specific веток в бизнес-коде приложений.

Что это значит конкретно:

  • Пути — только через node:path (path.join, никаких хардкод / или \).
  • Сертификаты/процессы/сигналы — app service install уже разделён на systemd (Linux) / Windows Service (§4), но общий CLI-код (app start, app stop) не должен знать, под чем он работает — платформенная разница инкапсулирована в core/platform/{linux.js,windows.js} с общим интерфейсом.
  • Docker — first-class сценарий, не костыль:
  • templates/node-express-app/ содержит эталонный Dockerfile и docker-compose.yml, которые генерируются/копируются командой app install --docker.
  • app doctor умеет определять, что процесс запущен в контейнере (/proc/1/cgroup или DOCKER_CONTAINER=1 из compose), и меняет смысл некоторых проверок: например, "Node version" проверяется внутри образа, а "port available" — не проверяется вовсе (за это отвечает host).
  • app service install внутри контейнера — no-op с понятным сообщением ("контейнер сам является сервисом, используйте restart: unless-stopped в compose"), а не попытка поставить systemd внутрь контейнера.
  • Volumes: data/, uploads/, backups/ — обязаны быть вынесены в volume в эталонном compose-файле. app doctor в контейнере проверяет, что эти пути смонтированы (не находятся на overlay-слое контейнера) — иначе предупреждает: "данные будут потеряны при пересоздании контейнера".
  • CI: core должен иметь юнит/интеграционные тесты, гоняющиеся в GitHub Actions на матрице ubuntu-latest + windows-latest, а не только на Linux — иначе "работает у автора ядра" не значит "работает у всех 4 приложений".

4.5b Расположение backup — конфигурируемое, не только локальный диск

Это прямо озвученная проблема: если backup лежит на том же диске/сервере, что и сама БД, при отказе диска/сервера теряется всё — и БД, и бэкапы. Core должен закладывать это с самого начала, а не как доработку потом.

Модель

core/backup работает не с одной директорией, а с набором destinations, как минимум одна из которых должна быть локальной (для быстрого restore), а остальные — опционально внешние:

// app.config.js
backup: {
  destinations: [
    { type: 'local', path: './data/backups', primary: true },
    { type: 'network-share', path: '\\\\nas01\\backups\\atlas' },   // Windows UNC тоже валиден
    { type: 'directory', path: '/mnt/external-disk/backups' }        // смонтированный внешний том
  ],
  schedule: '0 3 * * *'
}

Первая версия поддерживает local (в т.ч. путь на смонтированный сетевой диск/шару — с точки зрения Node это просто путь) — то есть техническую проблему "не всё на одном физическом носителе" это уже решает без интеграции с облачными SDK. Тип s3/webdav — расширение на будущее (core/backup/destinations/*.js — тот же паттерн модульных проверок, что и в doctor, добавить новый destination = добавить файл).

Управление расположением — и из CLI, и из веб-панели

app backup destinations list
app backup destinations add --type local --path /mnt/external-disk/backups
app backup destinations remove <id>
app backup destinations set-primary <id>
app backup create --destination <id>       # бэкап в конкретное место
app backup create                          # бэкап во все destinations сразу (по умолчанию)

В @das-forge/ui — экран Settings → Backup с тем же CRUD поверх того же API ядра (backup.destinations.*), UI не дублирует логику, а вызывает те же core-функции, что и CLI.

app doctor проверяет это явно

Новая проверка в категории Storage: если настроен только один destination и он на том же физическом томе, что и сама БД — предупреждение, а не тихое молчание:

Storage
  ✓ backups/ writable
  ⚠ only one backup destination configured, and it's on the same disk as the database
    → consider adding a network/external destination: `app backup destinations add`

4.5c Performance/load-тестирование — отдельная тестовая категория

До сих пор в роадмапе (§8/Phase 2) были только Vitest+Supertest (юнит/ интеграция) и Playwright (e2e/UI). Нагрузочное тестирование — отдельная, явно не описанная категория, добавляем её как полноправный слой:

  • Инструмент: autocannon (Node-нативный, не требует отдельного рантайма типа k6/Go — вписывается в тот же npm test-контур, что и остальные тесты, и не тянет внешних бинарников в CI).
  • Расположение: @das-forge/core поставляет готовые перф-сценарии для своих же эндпоинтов (/health, login, типовой CRUD через db adapter), приложения добавляют свои сценарии по тому же паттерну.
  • CLI: app test:perf [--scenario <name>] [--duration 30] [--connections 50] — печатает p50/p95/p99 latency и RPS, не просто "прошло/не прошло".
  • Пороговые значения (budgets) задаются в app.config.js — сам механизм (exit code 1 при превышении p95, можно включить в CI как gate) фиксируем сейчас, но конкретные числа (20ms/150ms ниже) — placeholder, не согласованный SLA. Реальные budgets выставляются только после первого замера настоящего core на реальном железе, не придумываются заранее: ``js performance: { budgets: { 'GET /health': { p95: '<TBD после первого замера>' }, 'POST /auth/login': { p95: '<TBD после первого замера>' } } } ``
  • Место в роадмапе: добавляется в Phase 2 вместе с юнит-тестами core (перф-сценарии для auth/db с первого коммита, чтобы регрессии по производительности core было видно сразу), не откладывается на конец.

4.5d Гигиена зависимостей — то, что переизобреталось в каждом проекте

Явно озвученная боль: grep лицензий зависимостей и проверка актуальности пакетов делались вручную и по-разному в каждом из 4 проектов. Это ровно тот случай, для которого и затевалась платформа — переносим в CLI как встроенные команды, а не в отдельный опциональный пакет (это операционная, не бизнес-функциональность, место — рядом с doctor):

app deps licenses [--json] [--fail-on <list>]
    → грепает лицензии всех зависимостей (через library, не самописный парсинг package.json вручную),
      по умолчанию флагует copyleft (GPL/AGPL) как предупреждение;
      --fail-on GPL,AGPL — exit code 1 в CI, если такие найдены

app deps outdated [--json]
    → таблица: текущая версия / latest / wanted / есть ли breaking (major bump)

app deps audit [--json]
    → обёртка над `npm audit`, но с единым форматом вывода для всех 4 приложений
    → интегрируется в `app doctor` как категория Dependencies

app deps check [--fix]
    → licenses + outdated + audit одной командой, для регулярного ручного прогона

Реализация — тонкая обёртка над существующими библиотеками (license-checker/аналог для лицензий, npm outdated --json, npm audit --json), а не написание парсера npm-реестра с нуля. Ценность платформы — не в реализации, а в том, что все 4 приложения получают одну и ту же команду с одним и тем же форматом вывода, вместо четырёх раз переизобретённого скрипта.

4.5e @das-forge/email — системные письма как часть контракта, не примитивный send()

Изначально API пакета был описан слишком узко (email.send({to, subject, text, html})). Это транспортный примитив, а нужен набор именованных системных сценариев, одинаковых по контракту во всех 4 приложениях, чтобы Atlas/procure-it/it-assets/net-monitor не реализовывали каждый раз свой текст письма и свою логику "как собрать ссылку с токеном".

Публичный API (высокоуровневый, поверх transport)

await email.sendAlert({ to, title, message, severity })              // системный алерт (напр. диск заполнен, backup failed)
await email.sendPasswordReset({ to, resetUrl, expiresInMinutes })
await email.sendPasswordChanged({ to })                                // уведомление "пароль был изменён" (security)
await email.sendEmailVerification({ to, verifyUrl })
await email.sendAccountBanned({ to, reason, until })                   // бан/блокировка аккаунта
await email.sendAccountUnbanned({ to })
await email.sendUserInvited({ to, inviteUrl, invitedBy })
await email.sendSystemNotice({ to, subject, message })                 // общий служебный канал (fallback для случаев вне списка)

Каждый метод — это шаблон + обязательный набор полей, а не свободный html-текст на усмотрение каждого приложения. Это то же самое соображение, что и с CLI/doctor: одинаковый UX/контракт важнее гибкости.

Структура пакета

email/
├── transport.js         nodemailer под капотом, приложение не видит его напрямую
├── templates/
│   ├── alert.{ru,en}.html
│   ├── password-reset.{ru,en}.html
│   ├── password-changed.{ru,en}.html
│   ├── email-verification.{ru,en}.html
│   ├── account-banned.{ru,en}.html
│   ├── account-unbanned.{ru,en}.html
│   ├── user-invited.{ru,en}.html
│   └── system-notice.{ru,en}.html
├── render.js             подстановка данных + выбор локали (см. §5.6 — те же ru/en)
└── index.js
  • Шаблоны на обоих обязательных языках сразу (тот же принцип, что и в UI/doctor) — язык выбирается по user.locale, как и в интерфейсе.
  • Приложение может переопределить конкретный шаблон (brand/логотип, доп. текст), но не может убрать сам сценарий — то есть кастомизация через templates/overrides/, а не форк пакета.
  • sendAlert — это то же самое событие, что могло бы уйти в realtime.publish() (§3) для UI-уведомлений; на практике alert часто дублируется в оба канала (email + realtime), поэтому core/audit и email.sendAlert используют общую структуру severity (info/warning/critical), чтобы не изобретать два разных enum.
  • Rate-limiting на сами письма (чтобы не заспамить пользователя десятком "password changed" при брутфорсе) — тоже часть @das-forge/email, не забота каждого приложения отдельно.

SPF/DKIM/DMARC — zero-trust применительно к почте (§4.5j, но для email)

Та же логика "не верим на слово" — только здесь не сервер не доверяет клиенту, а получатель письма не обязан верить, что оно реально от домена компании. Без SPF/DKIM/DMARC email.sendAlert()/sendPasswordReset() и т.д. рискуют улетать в спам или быть подделаны (fishing от имени системы — реальная угроза для функций вроде password reset).

  • DKIM-подпись исходящих писем — nodemailer поддерживает DKIM "из коробки" (приватный ключ + селектор в конфиге), @das-forge/email подписывает всё исходящее по умолчанию, если в app.config.js указаны DKIM-параметры.
  • SPF/DMARC — это DNS-записи домена отправителя, не код — core их не может "настроить", но может проверить. Добавляю в doctor (категория Integrations): если email модуль включён, app doctor резолвит SPF/DMARC TXT-записи для домена, с которого отправляются письма, и предупреждает, если их нет или они не покрывают SMTP-сервер, через который реально отправляется почта.
Integrations
  ✓ SMTP reachable
  ⚠ SPF record missing or doesn't include sending server
  ⚠ DMARC record missing (рекомендуется p=quarantine минимум)

Это именно то разделение, что и с retention/breach notification раньше: настройка DNS — действие человека (добавить TXT-запись у регистратора домена), детект, что не настроено — код.

4.5f HTTPS-only и сертификаты — обязательно, включая локальный/LAN-режим

Требование: никакого голого HTTP ни в одном режиме работы. core/http физически не поднимает http.createServer для внешнего трафика — только https.createServer, за одним явным исключением (режим за reverse-proxy, см. ниже).

Три режима работы, три источника сертификата

1. Standalone HTTPS с реальным сертификатом
   → пути к cert/key берутся из app.config.js (свой CA / Let's Encrypt через certbot снаружи)
   → core просто загружает файлы, ничего не генерирует

2. За reverse-proxy (nginx/Caddy терминирует TLS)
   → app.config.js: { server: { trustProxy: true } }
   → core слушает HTTP только на loopback/внутреннем интерфейсе,
     доверяет X-Forwarded-Proto, но снаружи трафик всё равно только HTTPS —
     это не нарушение правила "никакого HTTP", это TLS-termination на границе,
     стандартная практика, а не дыра

3. Локальный запуск / внутри LAN без внешнего reverse-proxy (одна машина, офисная сеть)
   → сертификата взять неоткуда (нет публичного домена для Let's Encrypt)
   → core генерирует self-signed сертификат САМ при первом запуске

Механизм self-signed (режим 3)

  • Библиотека: selfsigned (чистый JS, без нативных биндингов и без зависимости от системного OpenSSL-бинарника — на Windows его наличие не гарантировано, а конфликтовать с версией OpenSSL в самом Node не хочется). Опционально core может использовать системный openssl CLI, если он найден в PATH (быстрее, привычные форматы), но это fallback наверх, не обязательное требование — selfsigned работает всегда и везде, включая Docker-образ без openssl внутри.
  • Сертификат кладётся в data/certs/{cert.pem,key.pem}, попадает под то же правило volume-монтирования, что и data//uploads//backups/ (§4.5a) — иначе при пересоздании контейнера сертификат сгенерируется заново и все закреплённые доверия в браузерах/ОС слетят.
  • В сертификат прописываются subjectAltName: localhost, 127.0.0.1, реальный hostname машины и, если задан, IP из LAN — чтобы открывать и по https://localhost:3000, и по https://192.168.x.x:3000 без второй генерации.

Управление сертификатом — CLI и doctor

app cert info                     срок действия, subjectAltName, self-signed или нет
app cert generate [--force]       (пере)генерация self-signed
app cert renew                    перевыпуск с сохранением тех же SAN
app cert trust                    печатает инструкцию (Linux/Windows/macOS) как добавить
                                   self-signed сертификат в доверенные корневые — сам в системный
                                   trust store ничего не пишет без явного --system флага
                                   (модификация системного trust store — потенциально опасная операция,
                                   должна быть осознанным действием администратора)

app doctor (категория Security, уже была в §4.5) расширяется:

Security
  ✓ certificate valid (expires in 214 days)
  ⚠ self-signed certificate in use — not trusted by default in browsers
  ⚠ certificate expires in 12 days
    → run `app cert renew`

Автоматический перевыпуск: app cert renew вызывается по расписанию (тот же cron-механизм, что и app backup create), а не только руками — self- signed сертификат не должен незаметно протухнуть посреди работы.

DNS-over-HTTPS / DNSCrypt — решено: резолвер уровня @das-forge/network, не общее требование

Подтверждено: речь о сценарии (1) — сервер сам резолвит исходящие запросы через DoH/DNSCrypt, актуально для net-monitor (сетевые проверки/опросы устройств), не про то, что приложения сами отдают DoH наружу (сценарий 2 — не делаем, отдельный тяжёлый сервис не нужен).

Контракт: конфигурируемый резолвер на уровне @das-forge/network, не общее требование для всех 4 приложений (procure-it/atlas не резолвят внешние хосты, которым нужна эта защита):

// app.config.js — только net-monitor
modules: {
  network: {
    resolver: 'system' | 'doh',
    dohEndpoint: 'https://1.1.1.1/dns-query'   // если resolver: 'doh'
  }
}

Реализация — node:dns с кастомным resolver'ом (Node поддерживает это через dns.Resolver + кастомный сокет, либо тонкая обёртка через undici's DoH-совместимый lookup) внутри @das-forge/network, доступно только там, где вообще есть исходящие сетевые проверки.

4.5 health vs doctor — разные инструменты, разная аудитория

Их часто путают, но это принципиально разные проверки, и в core это два разных модуля (core/health и core/health/doctor.js, но с разным API и разной точкой входа).

app health / GET /health — "сервер жив и отвечает правильно"

Быстрая проверка работающего процесса, вызывается часто (мониторингом, балансировщиком, systemd ExecStartPost). Должна отрабатывать за миллисекунды, не открывать новых соединений без необходимости.

Проверяет:

  • процесс отвечает на HTTP
  • БД доступна (простой SELECT 1, не полный integrity check)
  • версия приложения совпадает с ожидаемой (для деплоя)

Вывод (--json или GET /health):

{ "status": "ok", "database": "ok", "version": "26w40-b03", "uptime": 41233 }

При проблеме — "status": "degraded" или "error" + 503 на HTTP-уровне, не 500 (это осознанный сигнал "сервис жив, но не готов принимать трафик").

app doctor — "машина/установка настроена правильно"

Диагностика окружения и конфигурации, запускается человеком при установке, после апдейта, при разборе инцидента. Может занимать секунды, проверяет намного больше и не должна вызываться автоматически на каждый запрос.

Категории проверок (единые для всех 4 приложений, каждый модуль добавляет свои):

Configuration  .env присутствует, обязательные переменные заданы, секреты не дефолтные
Database       connection, integrity_check, migrations up to date, размер файла
Storage        data/, uploads/, backups/ — существуют и доступны на запись
Security       файловые права на .env/certs, сертификаты валидны и не просрочены,
               auth configuration (session secret не дефолтный, argon2 доступен)
Integrations   SMTP reachable (если email включён), LDAP reachable (если включён),
               внешние network-провайдеры (для net-monitor)
Application    ru+en локали присутствуют и полны (см. §5.6), light/dark темы
               зарегистрированы, обязательные модули из app.config.js загружены,
               порт свободен

4.5g Операционные инструменты — CLI + admin-панель, парный контракт

Общий принцип для всего этого блока (как и для backup destinations в §4.5b): CLI и UI вызывают один и тот же core-API, ничего не дублируется. UI — это тонкая обёртка над той же функцией, что и команда. Ниже — 8 инструментов, которых не хватало.

1. Логи: просмотр, экспорт, retention

app logs tail [--follow] [--level error] [--since 1h]
app logs export --since 2026-09-01 --until 2026-09-30 --out logs.ndjson
app logs config set --retention-days 30 --max-size 500MB

core/logging пишет через pino в ротируемые файлы (pino-roll, уровень приложения — не core-зависимость, но core задаёт дефолтную политику). Retention/rotation конфигурируется, а не хардкожено.

Admin-панель: Administration → Logs — живой tail через SSE (тот же core/realtime, что и notifications), фильтр по уровню/дате/модулю, кнопка "Export". Доступ — отдельное право admin.logs.view (не то же, что общий admin).

2. Восстановление доступа администратора (без веб-логина)

app user create-admin --email admin@company.local           # интерактивно спросит пароль, или --temp-password
app user reset-password <email> --temp                       # генерирует временный пароль, требует смены при первом входе
app user unlock <email>                                      # снять блокировку после лишних попыток входа

Работает напрямую через core/database, в обход HTTP/сессий — это единственный путь "почини доступ", когда сам веб-интерфейс недоступен (забыт пароль, все админы заблокированы). В admin-панели этой команды нет и не может быть — по определению, если у тебя есть доступ в панель, эта функция тебе не нужна.

3. Баны и rate-limit — просмотр и снятие

app security bans list [--json]
app security bans unban --ip <ip> | --account <email>
app security bans clear-all --yes

Admin-панель: Administration → Security → Blocked — таблица (IP/аккаунт, причина, время бана, сколько осталось), кнопка "Unban" на каждой строке. И CLI, и UI читают из одного стора банов в core/security (не in-memory — переживает рестарт процесса).

4. Единый реестр периодических задач (cron registry)

Backup schedule, cert renew, deps check и любые задачи, которые зарегистрируют модули — всё через одну точку core/scheduler, а не каждый со своим setInterval:

app cron list                     # что зарегистрировано, расписание, когда следующий запуск
app cron history [--task backup]  # что и когда реально выполнялось, успех/ошибка, длительность
app cron run <task> --now         # запустить вне расписания (напр. "сделай бэкап прямо сейчас")

Admin-панель: Administration → Scheduled Tasks — список задач + статус последнего запуска (✓/✗ + длительность), кнопка "Run now". Пропущенный/ проваленный запуск обязательно триггерит email.sendAlert (§4.5e) — иначе никто не узнает, что бэкап неделю не выполнялся.

5. Секреты — ротация без хаоса

app secrets rotate session-secret         # инвалидирует все текущие сессии — с явным подтверждением
app secrets rotate smtp-password --value <new>
app secrets list [--json]                 # какие секреты сконфигурированы, БЕЗ значений — только имена + "когда последний раз менялся"

session-secret ротация — деструктивная операция (все залогинены выйдут), поэтому CLI требует --yes, а в UI — двойное подтверждение с явным текстом последствия. Значения секретов никогда не отображаются ни в CLI, ни в UI — только факт настроенности и дата последней смены.

Admin-панель: Administration → Secrets — список имён + даты, кнопка "Rotate" с модалкой-предупреждением (используем dialogs.confirm из §5).

6. Метрики — решено: делаем, раз Grafana подтверждена как стек

Снимаю прошлое "отложено" — раз Grafana реально используется/будет использоваться, строить /metrics обоснованно:

GET /metrics     Prometheus text format — RPS, latency (p50/p95/p99),
                  error rate, db pool, event loop lag, memory, активные SSE-соединения

Включается флагом observability: { metrics: true } в app.config.js — не хардкод на все 4 приложения разом, потому что не всем может быть нужно сразу (например, net-monitor и так пишет метрики в себя). UI-страницу графиков в Administration не делаем — раз Grafana уже есть, дублировать её дешёвым встроенным графиком бессмысленно; вместо этого Administration → Metrics — это просто iframe/ссылка на готовый Grafana-дашборд приложения (конфигурируется observability.grafanaDashboardUrl), не велосипед на графиках. doctor (категория Integrations) проверяет доступность /metrics снаружи, если флаг включён.

7. Graceful shutdown / рестарт без обрыва запросов

app restart [--drain-timeout 30]

При SIGTERM/app stop: сервер перестаёт принимать новые соединения, даёт активным HTTP-запросам и открытым SSE-стримам (core/realtime) завершиться в течение drain-timeout, затем принудительно закрывает оставшиеся. Реализуется один раз в core/http, все 4 приложения получают это бесплатно — раньше у каждого был свой (или никакой) обработчик SIGTERM.

Admin-панель: кнопка "Restart application" в Administration → System с тем же drain-механизмом — UI не имеет права дёргать process.kill напрямую, только вызывает тот же core-эндпоинт, что и CLI.

8. Health и Doctor — отдельный экран, не подпункт System

Изначально Health/Doctor были описаны только как CLI-команды (§4.5) — это неправильно оставлять их без UI-эквивалента, раз весь остальной операционный инструментарий (§1–7 выше) уже задуман парой CLI+UI. Health/ Doctor заслуживают своего пункта, а не строчки внутри "System", потому что смотрят их чаще всего (в отличие от, например, secrets).

Administration → Health & Doctor:

  • Верхний блок — живой статус из GET /health (§4.5): зелёный/жёлтый/ красный индикатор, обновляется по SSE или поллингом каждые N секунд — то же самое, что видит внешний мониторинг, но глазами администратора внутри приложения.
  • Ниже — кнопка "Run diagnostics", вызывающая тот же doctor.run(), что и app doctor в CLI, с тем же выводом по категориям (Runtime, Configuration, Database, Storage, Security, Integrations, Application — §4.5), отрендеренным как список с ✓/⚠/✗ вместо текстовой консоли.
  • Проваленные/предупреждающие пункты кликабельны там, где есть авто-фикс (--fix из CLI) — кнопка "Fix" рядом с конкретной строкой, вызывающая ту же fix-функцию, что и app doctor --fix, точечно для одной проверки, а не всего скопом.
  • Historical view: последние N прогонов doctor (когда запускался — вручную или по расписанию, см. п.4 core/scheduler) и как менялся результат — полезно видеть "сертификат вчера был ✓, сегодня ⚠" без пролистывания логов.

Это read-heavy, write-light экран — в отличие от Secrets/Bans, тут почти нет деструктивных действий, поэтому право на просмотр (admin.health.view) может быть шире, чем на остальные разделы Administration — например, выдано не только полным админам, но и дежурным/техподдержке.

9. Просмотр audit log

app audit tail [--follow]
app audit export --since <date> --actor <user> --out audit.ndjson

Admin-панель: Administration → Audit Log — таблица (кто/что/когда/ сущность), фильтры по actor/действию/дате, экспорт в тот же формат, что и CLI-команда (то есть UI — не отдельная реализация экспорта, а кнопка, вызывающая ту же функцию audit.export()).

Сводка: новый раздел admin-панели

Всё это в UI живёт под одним пунктом навигации, который приложение получает бесплатно вместе с AppShell (§5.7):

Administration
  ├── Health & Doctor
  ├── Logs
  ├── Security → Blocked (bans)
  ├── Scheduled Tasks (cron)
  ├── Secrets
  ├── Integrations (API keys, webhook delivery log) — если пакет установлен
  ├── Metrics (ссылка на Grafana-дашборд) — если observability.metrics включён
  ├── Privacy (export/erase, 152-ФЗ/GDPR)
  ├── Roles & Permissions
  ├── Audit Log
  └── System (restart, version)

Доступ к разделу целиком и к каждому пункту — через отдельные permissions (admin.logs.view, admin.security.manage, ...), а не один общий "isAdmin" флаг — это уже вытекает из authorization.can() (§3).

4.5j Zero-trust на границе клиент↔сервер — явный сквозной принцип

Формулирую как правило платформы, а не как разовую защиту: клиент (браузер) — недоверенная сторона всегда, в обе стороны. Это не новая фича, а склейка уже принятых решений (Zod, CSRF, RBAC) в один явный принцип + несколько следствий, которые раньше не были проговорены.

Клиент → сервер: ничему из присланного не верим на слово

  • Валидация на клиенте — только UX, никогда не защита. Та же ApplicationConfigSchema/UserSchema-логика (Zod, §7.5) обязательно повторно прогоняется на сервере — изоморфность Zod здесь не "чтобы не дублировать код", а "чтобы дублирование правил не разъехалось", сама проверка выполняется дважды по определению zero-trust.
  • Права/роль пользователя никогда не берутся из тела запроса. Если клиент прислал { role: 'admin' } в payload — сервер это игнорирует, роль всегда читается из серверной сессии (req.session.user), не из того, что прислал браузер. Это уже подразумевалось RBAC-моделью (§3), но стоит явно: никакое поле в body/query не может влиять на авторизацию.
  • Вычисляемые значения (цены, суммы, итоги) не принимаются от клиента. Прямое следствие для procure-it: если форма закупки присылает totalPrice, сервер игнорирует это поле и пересчитывает сам из quantity × unitPrice по серверным данным о ценах, а не доверяет готовому числу из формы — иначе это открытая дыра "поменяй число в devtools перед отправкой".
  • ID/версии для optimistic locking (уже упоминалось для atlas) — клиент присылает version, сервер проверяет совпадение с текущей версией в БД (409 Conflict при расхождении), но не доверяет version как источнику правды ни для чего, кроме этой проверки конфликта.
  • Клиентское время не авторитетно. Если фронт присылает timestamp события — в audit.log()/бизнес-логике использовать серверное время получения запроса, клиентский timestamp — максимум для отображения ("как видел это пользователь"), не для порядка событий или SLA-расчётов.

Сервер → клиент: не отдаём лишнее, чтобы не полагаться на то, что UI это "просто не покажет"

Это обратная сторона, которую часто упускают: если сервер отдаёт все поля сущности, а UI просто не рендерит некоторые (например, зарплату сотрудника, закупочную цену) — это не защита, это скрытие в devtools на одну вкладку "Network". Правило: API отдаёт клиенту только то, что этому клиенту разрешено видеть, на уровне сериализации, а не рендеринга.

// core/http/serialize.js
serialize(entity, { viewerPermissions })
  → убирает поля, на которые у permissions нет доступа,
    ДО того, как объект уйдёт в res.json()

Каждая сущность в приложении декларирует, какие поля требуют каких permissions (например, asset.purchasePrice требует assets.viewFinancials) — это часть контракта модуля (расширение ModuleRegistrationSchema, §7.5), не решение "спрятать в UI", принимаемое на лету в каждом компоненте.

Токены, которые уходят клиенту и возвращаются обратно

Reset-ссылки, invite-ссылки, email-verification-ссылки (§4.5e) — все уже подразумевались как "ссылка с токеном", но явно: токен должен быть криптостойким случайным, подписанным и с истечением, а не предсказуемым (не userId + timestamp, не последовательный ID). Сервер при приёме такого токена обратно не доверяет содержимому токена напрямую — только смотрит его в своём хранилище (истёк? использован? для кого выдан?), сам токен — просто ключ поиска, не источник правды о пользователе/правах.

Итог как единое правило для контракта модуля

Каждый роут в приложении, пишущий данные, должен отвечать на три вопроса одинаково, независимо от того, что каким образом клиент попытался прислать: "откуда взялась роль?" → из сессии. "откуда взялась цена?" → из БД/расчёта на сервере. "откуда взялось разрешение показать это поле?" → из serialize() по правам смотрящего. Ни один из трёх ответов никогда не "из тела запроса".

4.5h Security-гигиена современного стека — что ещё не проговорено явно

Это то, что обычно не вспоминают, пока не прилетит инцидент. Разбиваю на обязательное в core с первого коммита и обсудить/решить осознанно.

Обязательное — закладываем в core/security/core/http сразу

1. Request ID / correlation ID. Каждый запрос получает X-Request-Id (генерируется, если клиент не прислал), прокидывается через весь pino-логгер и в audit.log(). Без этого разбор инцидента по логам — это grep по времени и надежда, что ничего не наложилось. Тривиально в реализации, критично для отладки в проде.

2. Cookie flags и session fixation. httpOnly, secure (обязательно — у нас HTTPS-only, §4.5f), sameSite: 'lax' по умолчанию — и regenerate session ID при логине (не просто выдать права существующей анонимной сессии) — иначе сессия уязвима к fixation. Это должно быть частью auth.createSession() (§3), не опцией, которую можно забыть включить в конкретном приложении.

3. Лимиты на входящий трафик (anti-DoS на уровне приложения). express.json({ limit: '1mb' }) по умолчанию (переопределяемо на конкретных эндпоинтах — например upload), request timeout (защита от slowloris), лимит на глубину вложенности JSON. Сейчас в архитектуре только express-rate-limit (по количеству запросов) — этого мало, нужен ещё лимит на размер и время одного запроса.

4. Безопасная загрузка файлов (актуально для atlas/procure-it/it-assets — все три работают с файлами/документами/изображениями):

  • проверка реального MIME по содержимому (magic bytes), а не по расширению или Content-Type из запроса (его подделать тривиально);
  • запрет path traversal в имени файла (../../etc/passwd) — генерировать собственное имя на диске, оригинальное имя хранить только в БД; жёсткий whitelist разрешённых типов на уровне app.config.js модуля.
  • Это должно жить в core/files (или отдельно @das-forge/files, уже заявленном в §6) как обязательный слой перед записью на диск, а не проверяться (или не проверяться) в каждом приложении по-своему.

4a. Magic bytes — необходимо, но недостаточно. Файл, у которого заголовок честно соответствует заявленному типу, всё равно может быть вредоносным внутри — JS/TS не даёт типобезопасности на уровне байтов файла точно так же, как не даёт её на уровне данных из запроса (§4.5j — тот же принцип zero-trust, просто на уровень глубже). Конкретные риски, которые magic-bytes не ловит:

  • ZIP-бомба под видом docx/xlsx/pptx. Офисные форматы — это ZIP-архив внутри. Magic bytes скажут "да, это ZIP, всё ок", но внутри может быть архив с огромным коэффициентом сжатия (несколько КБ на диске → терабайты после распаковки), который положит @das-forge/documents/@das-forge/exports при попытке прочитать. Защита: явный лимит на коэффициент сжатия и количество entries при распаковке (например, отказ, если decompressed/compressed > 100 или entries > 1000), и проверка, что внутри реально ожидаемая структура ([Content_Types].xml для docx/xlsx), а не что угодно с правильным ZIP-заголовком.
  • PDF с активным содержимым. PDF может содержать JavaScript-действия, встроенные файлы, launch-actions. Сервер никогда не должен исполнять или рендерить с интерпретацией JS загруженный PDF — только хранить и отдавать как opaque blob, либо явно санитизировать (вырезать /JavaScript, /JS, /Launch объекты) перед сохранением, если @das-forge/documents вообще заглядывает внутрь PDF, а не просто передаёт файл насквозь.
  • Полиглот-файлы (валидны одновременно как два формата — например, ZIP-хвост, приклеенный к валидному JPEG). Здесь помогает не проверка байтов, а пересборка, а не доверие оригинальным байтам: для изображений @das-forge/images (§6, sharp) и так декодирует и перекодирует пиксели заново — это уже сильная защита как побочный эффект, потому что полиглот-хвост, не относящийся к самому изображению, физически не переживает decode→re-encode цикл. Стоит явно зафиксировать это как обязательный шаг, а не опциональную "конвертацию" — любое загруженное изображение проходит через sharp хотя бы раз, даже если формат на входе и выходе совпадает.
  • Antivirus-сканирование (опционально, не для всех инсталляций). Для atlas/procure-it, где через загрузку проходит много документов от разных людей, имеет смысл опциональный слой — вызов ClamAV (демон, внешняя зависимость, поэтому именно опция, а не часть core по умолчанию): ``js // app.config.js files: { antivirus: { enabled: true, socket: '/var/run/clamav/clamd.ctl' } } ` Если демон недоступен, а antivirus.enabled: true — app doctor` (категория Integrations) должен явно на это указать, не проглатывать молча.

5. CSP (Content-Security-Policy) для @das-forge/ui. Раз UI — vanilla JS без бандлера, это даже проще сделать правильно, чем в SPA-стеке: script-src 'self' (+ nonce на инлайн-скрипты, если понадобятся), никакого unsafe-inline/unsafe-eval. helmet уже в core-зависимостях — CSP настраивается через него, но сейчас в документе явно не зафиксирована политика, только сам факт "helmet используется".

6. Password policy + breach-check (опционально offline). Минимум — длина/энтропия через Zod-схему в core/auth. Дальше — вопрос: подключать ли проверку по базе скомпрометированных паролей (k-anonymity API вроде HaveIBeenPwned) — в LAN/изолированной сети это будет требовать исходящего интернет-доступа, что не всегда приемлемо для внутренней инфраструктуры компании. Предлагаю сделать опциональным флагом (auth.passwordPolicy.breachCheck: false по умолчанию), а не обязательным.

7. Clock skew / точность времени — новая проверка в doctor. Audit log и сертификаты (§4.5f) полагаются на корректное системное время. Расхождение времени на сервере — тихая причина "сертификат уже просрочен, хотя вчера был свежий" или "аудит-лог событий в неправильном порядке". Добавить в doctor категорию Runtime: сверка с NTP (если есть исходящий доступ) или хотя бы предупреждение, если системные часы сильно разошлись с временем последнего успешного запроса к внешнему сервису.

Пункты 8–10 — решено

8. 2FA/TOTP — включаем, опционально. core/auth/totp.js (RFC 6238, совместим с Google Authenticator/Authy), auth.require2fa: ['admin'] — включается per-role через ApplicationConfigSchema (§7.5, поле уже заложено), не для всех пользователей по умолчанию. Реализуется в Phase 2 вместе с остальным core/auth, не откладывается на потом.

9. Шифрование БД at rest — уровень ОС. Не усложняем core ради этого (конфликтовало бы с решением "нативный node:sqlite"). doctor (категория Security) выдаёт рекомендацию проверить шифрование диска (BitLocker/LUKS), core сам ничего не шифрует.

10. 152-ФЗ и GDPR — да, актуально, закладываем core/privacy.

4.5k core/privacy — 152-ФЗ / GDPR-совместимость и cookie-уведомление

Раз it-assets/procure-it хранят ФИО и контакты сотрудников — это персональные данные, и (а) по 152-ФЗ, и (б) если у компании есть связи с ЕС (сотрудники/контрагенты-резиденты ЕС) — по GDPR. Важная оговорка: дальше — техническая база, которая нужна в любом случае, но финальное соответствие 152-ФЗ/GDPR (согласия, основания обработки, трансграничная передача данных, DPO и т.д.) — вопрос юридический, не архитектурный; технические возможности ниже нужно будет сверить с юристом/комплаенсом компании, это не заменяет такую проверку.

Модель: субъект данных = сотрудник, запрос обычно инициирует админ/HR

В отличие от публичного SaaS (где юзер сам жмёт "скачать мои данные"), здесь чаще сценарий "сотрудник увольняется/просит удалить данные — HR/ admin выполняет запрос через систему". Оба пути поддерживаются:

// core/privacy — каждый модуль регистрирует, как экспортировать/стереть
// данные конкретного пользователя (расширение ModuleRegistrationSchema, §7.5)
ui.register({
  ...,
  dataSubject: {
    export: async (userId) => ({ assets: [...] }),      // модуль отдаёт свой кусок данных
    erase: async (userId, { mode }) => { ... }           // mode: 'anonymize' | 'delete'
  }
});

privacy.exportUserData(userId)   // собирает export() со всех модулей в один JSON
privacy.eraseUserData(userId, { mode })

По умолчанию mode: 'anonymize', не 'delete' — потому что audit log (§3) обязан сохранять целостность истории событий (кто/что/когда), а жёсткое удаление сломало бы аудит. Анонимизация заменяет идентифицирующие поля (ФИО, email) на "Удалённый пользователь #<id>", но оставляет сам факт события в истории. Полное 'delete' — доступно явным флагом, когда это действительно требуется юридически.

CLI и Admin UI

app privacy export --user <email> --out export.json
app privacy erase --user <email> [--mode anonymize|delete] --yes

Administration → Privacy (или как раздел карточки пользователя в Users): кнопки "Export data" / "Erase data" с тем же двойным подтверждением, что и у Secrets rotation (§4.5g/п.5) — необратимое действие, особенно в режиме delete. Каждое действие пишется в audit.log() — сам факт запроса на приватность тоже часть аудита.

Cookie-уведомление — в core, обязательно

Даже для внутренних приложений с одними только сессионными cookie (никакой аналитики/рекламы) пользователей стоит проинформировать, что куки используются — это встроено в @das-forge/ui как обязательный лёгкий баннер (ui/cookie-notice), не полноценная consent-платформа:

// defineAppUI
cookieNotice: {
  text: 'notice.cookies',   // i18n-ключ, платформенный дефолт на ru/en уже есть
  linkTo: '/privacy-policy'  // опционально
}

Баннер информативный ("мы используем куки для работы сессии"), не gate-ит функциональность и не требует явного "Согласен" — потому что единственные куки в системе строго необходимы для работы (сессия), а не трекинг/реклама.

Решено: аналитика внутренняя, сторонних cookie нет. Это упрощает картину до изначального варианта — события считаются на своей стороне через /metrics + Grafana (п.6 выше), никакого стороннего SDK (Google Analytics/Яндекс.Метрика и т.п.) не подключается, значит данные сотрудников никуда не утекают третьей стороне, и cookie для аналитики физически не появляется. Информационного ui/cookie-notice достаточно, полноценный consent management (cookieConsent) не нужен — оставляю этот абзац в документе как объяснение, почему было бы иначе, если бы решение было другим, но для текущей архитектуры это закрытый вопрос.

Retention policy — technical enabler, не решение "сколько хранить"

Архитектура не решает юридический вопрос "сколько хранить карточку уволенного сотрудника" — это решает компания/юрист. Но должна дать механизм, которым это решение потом исполняется автоматически, а не руками:

// расширение ModuleRegistrationSchema (§7.5)
dataSubject: {
  export: z.function(),
  erase: z.function(),
  retentionDays: z.number().int().positive().optional()   // NULL = бессрочно, решает приложение/юрист
}

core/scheduler (§4.5g/п.4) добавляет задачу privacy.enforceRetention() — на каждую сущность с истёкшим retentionDays вызывает erase(userId, { mode: 'anonymize' }) автоматически, или, если авто-анонимизация рискованна для конкретного модуля, флагует на ручной пересмотр (app privacy review-queue) вместо тихого действия. Конкретное число дней — не наше архитектурное решение, только то, что оно есть куда положить и что-то с ним само происходит, когда истекает.

Breach notification — technical enabler для скорости, не замена процесса

72-часовое окно по GDPR (ст. 33) — это про то, что человек (DPO/ ответственный) обязан уведомить регулятора, архитектура это не делает за него. Но может радикально сократить время до момента "человек узнал":

app security incident declare --severity critical --summary "..."

Триггерит email.sendAlert() (§4.5e) на список ответственных из app.config.js (security.incidentContacts), немедленно, а не когда кто-то случайно заметит аномалию в audit log. Сам audit.log() (§3) уже даёт неизменяемую историю для последующего разбора "что произошло и когда" — это уже часть архитектуры, просто не была явно привязана к процессу breach notification. Дальнейшие юридические шаги (кого и как уведомлять) — вне кода.

Реестр обработки (ст. 30 GDPR) — генерируется из кода, не пишется руками

Раз каждый модуль уже декларирует dataSubject/fieldPermissions как часть контракта (§7.5) — реестр обработки можно вывести из этих деклараций автоматически, вместо того чтобы вести отдельный Word/Excel документ, который неизбежно разъедется с реальным кодом:

app privacy registry [--json] [--out registry.md]

Обходит все зарегистрированные модули, печатает: какие данные (по fieldPermissions), кто может видеть (по permission), есть ли экспорт/удаление (dataSubject), retention (если задан). Это не заменяет юридическую часть реестра (основание обработки, цели, сроки хранения по закону) — те поля добавляются как дополнительные метаданные в декларации модуля (legalBasis, purpose — строки, которые заполняет разработчик по итогам согласования с юристом), но структура и актуальность реестра теперь гарантированно не расходится с кодом, потому что является кодом.

DPIA и DPO — вне архитектуры, оставляю как есть

Не пытаюсь предложить "техническое решение" для них — DPIA требует человеческого суждения о приемлемости риска, DPO — это назначение роли в компании. Ни то ни другое не автоматизируется и не является частью @das-forge/*.

Из всего списка §4.5h пункты 1–10 теперь все зафиксированы как решения, ничего не осталось в подвешенном состоянии.

4.5i Защита доступа к CLI и Admin UI — сетевая изоляция важнее ещё одного пароля

Это два разных периметра, и решения для них разные.

CLI

CLI по определению выполняется на самой машине (или внутри контейнера) — это не сетевой сервис, у него нет "внешнего" доступа, который можно перехватить по сети. Реальная защита CLI — это уже решённая ОС-задача, core её не дублирует:

  • права на файлы (app.config.js, .env, data/) — только владелец/ сервисный пользователь;
  • кто может зайти на сервер по SSH/RDP — вопрос инфраструктуры, не core;
  • команды вроде app user create-admin (§4.5g) и так требуют локального shell-доступа — это уже достаточный барьер для serverless-класса угроз.

Единственное, что стоит добавить в core: команды, меняющие security-критичные вещи (app secrets rotate, app user reset-password), пишут в audit log от имени "cli/<os-user>", а не анонимно — чтобы при разборе инцидента было видно, что действие пришло с консоли, а не через UI, и каким ОС-пользователем.

Admin UI — три уровня защиты, не взаимоисключающие

Уровень 1 (обязательный, дёшево): отдельный bind-адрес для Administration. core/http умеет поднимать /administration/* на отдельном порту/ интерфейсе, отличном от основного публичного трафика:

// app.config.js
server: {
  port: 3000,                          // публичная часть приложения
  admin: { port: 3443, bindHost: '127.0.0.1' }  // Administration — только на loopback/внутреннем интерфейсе
}

По умолчанию bindHost для admin — не 0.0.0.0. Это не "заменитель" аутентификации, а снижение поверхности атаки: чтобы достучаться до /administration, нужно либо быть на самой машине, либо иметь доступ к внутреннему интерфейсу — а не просто знать URL. doctor (Security) уже проверяет это как отдельный пункт: "admin interface bound to 0.0.0.0 — consider restricting".

Уровень 2 (рекомендуемый для LAN/офиса): VPN-оверлей, например Tailscale. Это ровно то, о чём ты думаешь, и это правильное направление — но это вопрос деплоя, не что-то, что core должен жёстко зашивать. Core не должен знать про конкретно Tailscale (это была бы лишняя зависимость и vendor lock-in для тех, кто использует WireGuard/OpenVPN/просто корпоративный VPN). Вместо интеграции — core делает так, чтобы это хорошо работало:

  • admin.bindHost (см. выше) можно указать как Tailscale-адрес машины (100.x.x.x) — тогда Administration физически недостижима вне Tailscale-сети, без единой строчки Tailscale-специфичного кода в core;
  • в docs/deployment/ — гайд "как повесить Administration за Tailscale/ WireGuard", а не код в core.
  • Плюс такого подхода: Tailscale/WireGuard уже дают identity (кто именно подключился по VPN) — это дополнительный слой поверх обычного логина, бесплатно, без реализации в приложении.

Уровень 3 (задел на будущее, НЕ проектируем сейчас): mTLS клиентские сертификаты на /administration/*. Идея зафиксирована на случай, если Уровней 1+2 когда-нибудь станет мало (например, внешний доступ к Atlas без VPN) — тогда core уже умеет управлять сертификатами (§4.5f) и это расширяется до клиентских. Но для текущего масштаба (4 внутренних приложения, всё в LAN) это ощутимый operational overhead (выпуск/отзыв сертификатов на каждого админа) ради угрозы, которая Уровнями 1+2 уже достаточно снижена — не проектируем детально, пока не понадобится.

Решение по умолчанию

Уровень 1 включаем всегда (это бесплатно и делается на уровне core/http без доп. UX). Уровень 2 (VPN/Tailscale) — просто гайд в docs/deployment/, ничего не пишем в коде. Уровень 3 — не делаем, пока не появится конкретный сценарий, где 1+2 недостаточно.

5. @das-forge/ui — vanilla JS admin platform

Решено: без фреймворка. React-вариант из более ранней части обсуждения отменён этим решением.

5.1 Технологический подход

  • Web Components (customElements.define) как единица инкапсуляции — Shadow DOM даёт изоляцию стилей без CSS-in-JS и без сборщика.
  • Загрузка нативными ES-модулями (<script type="module">), без бандлера в dev-режиме. Для production — лёгкий build step (esbuild) только для минификации/склейки, не обязателен для разработки.
  • Состояние — простые ES-классы + EventTarget/CustomEvent, без Redux/MobX.
  • Роутинг — тонкая обёртка над History API (ui/router.js), паттерн как в express: router.register('/users/:id', handler).
  • Данные с сервера — обычный fetch + тонкий ApiClient с обработкой 401/419 (истекшая сессия) на уровне ядра, а не в каждом экране.

5.1a DOM — явно про рендеринг, не только разметку

Прямая манипуляция DOM (innerHTML, appendChild руками) на масштабе таблицы из 500 активов — боль и источник XSS, если не экранировать строки вручную. Используем lit-html — это не фреймворк, а отдельная библиотека тегированных шаблонов (~5 КБ), именно то, что держит дух "vanilla JS": пишешь html\<div>${value}</div>\`, библиотека сама диффит и обновляет только изменившиеся узлы DOM, **автоматически экранирует** интерполированные значения (защита от XSS "бесплатно", не руками в каждом компоненте). Это единственная внешняя зависимость в @das-forge/ui`, и она осознанно выбрана как самая маленькая из существующих, а не написана с нуля — DOM-диффинг с нуля это уже reinventing a framework в чистом виде (сами предупреждали себя об этом риске в критическом разборе).

5.5 Темизация

Только через design tokens, жёстко запрещён хардкод цвета в компонентах приложений:

background: var(--ui-background);
color: var(--ui-foreground);

theme/ поставляет theme-light.css, theme-dark.css, слушает prefers-color-scheme и хранит выбор пользователя.

5.6 Локализация и темы — ОБЯЗАТЕЛЬНАЯ часть платформы, не опция

Это не "фича, если руки дойдут" — платформа физически не даёт приложению обойтись без этого:

  • ru и en обязательны для каждого приложения на DAS-Forge. Core валидирует app.config.js (ui.locale.supported) и отказывается стартовать, если в списке меньше двух локалей или отсутствует ru/en. Приложение может добавить третий/четвёртый язык, но не может уйти в моно-язык.
  • Платформенные ключи (common.*, navigation.*, validation.*, auth.*, errors.*) поставляются на обоих языках самой платформой — приложению не нужно заново переводить "Сохранить"/"Отмена". Приложение обязано добавить свои ключи (atlas.*, assets.*, ...) минимум на ru+en — это проверяется на этапе app doctor (см. §4.4) и падает как ошибка конфигурации, а не варнинг.
  • Приоритет определения языка пользователя: user.locale (профиль) → application default → browser Accept-Language → en.
  • Светлая/тёмная/системная тема обязательны для каждого приложения — theme.js всегда регистрирует light, dark, system; отключить тёмную тему приложение не может, только задать свою палитру через design tokens (theme: { primary: '#...' } в defineAppUI). system слушает prefers-color-scheme и переключается автоматически без reload.
  • Оба требования проверяются в app doctor как часть категории Application (пример вывода — §4.4).

5.7 Что каждое приложение получает бесплатно

Sidebar, header, user menu, breadcrumbs, theme switcher, language switcher, notifications, command palette, dialogs/drawers/forms/tables — приложение пишет только бизнес-экраны поверх контракта, задавая свой brand/navigation через defineAppUI({...}), как и раньше обсуждалось.

6. Опциональные пакеты

Причина осознанная, не забывчивость: не каждому серверу (procure-it, it-assets, net-monitor — они не обрабатывают изображения) нужно тащить sharp (нативный биндинг с бинарниками под платформу) и libheif-js (Emscripten/WASM). 6.5 @das-forge/integrations — обмен данными между приложениями

Это ровно тот сценарий: procure-it закупил → it-assets должен получить предзаполненную карточку (дата покупки, гарантия, тип устройства, организация) → если это сетевое оборудование, net-monitor подхватывает его на мониторинг → net-monitor знает актуальный IP/статус и должен писать это обратно в it-assets. Три независимые БД (у каждого приложения своя, это фича, не баг — единая БД на 4 приложения была бы куда более хрупким решением), значит нужен явный слой интеграции, а не "просто дёрнем таблицу соседнего приложения".

Модель: webhooks наружу + Integration API внутрь, не общая шина

Учитывая масштаб (4 внутренних приложения, не сотни сервисов), полноценная message-queue (Kafka/RabbitMQ) — избыточна и добавляет ещё один инфраструктурный компонент, который надо администрировать. Вместо этого:

Producer (procure-it)                    Consumer (it-assets)
      │                                         │
      │  событие: purchase.completed            │
      ▼                                         │
core/integrations/webhooks.emit()               │
      │                                         │
      │  HTTP POST + HMAC-подпись               │
      └───────────────────────────────────────► /api/integrations/v1/webhooks/procure-it
                                                 │
                                          core/integrations/webhooks.receive()
                                                 │
                                          it-assets: создаёт ЧЕРНОВИК актива
  • Исходящая часть (webhooks) — core/integrations/webhooks.emit(event, payload). HMAC-подпись тела (общий секрет между парой приложений, управляется как ещё один тип секрета из §4.5g/п.5), retry с backoff при недоступности получателя, delivery log (кто, когда, статус, сколько попыток) — видно в Administration.
  • Входящая часть (Integration API) — /api/integrations/v1/*, аутентификация не пользовательской сессией, а scoped API-ключом (app integrations issue-key --for net-monitor --scopes assets.network.write) — то есть net-monitor физически не может через этот ключ поменять, например, цену закупки актива, только те поля, на которые у ключа есть scope. Это тот же принцип наименьших привилегий, что и в RBAC (§3).
  • Оба конца — опциональный пакет @das-forge/integrations, а не часть core: инсталляция с одним procure-it (без it-assets) не должна тащить этот слой вообще.

Конкретные потоки для твоего кейса

1. procure-it → it-assets: предзаполнение при закупке

событие: purchase.completed
payload: { poNumber, itemType, purchaseDate, warrantyMonths, organization, vendor }

it-assets создаёт черновик актива (не сразу "боевую" запись) — кто-то физически принимает оборудование и подтверждает совпадение с закупкой (серийный номер и т.п. закупка ещё не знает). Это осознанное решение: автоматически создавать подтверждённые записи по данным закупки — риск получить в системе то, что по факту не приехало/приехало другое. Черновик → человек проверяет → confirm.

2. it-assets → net-monitor: постановка на мониторинг

событие: asset.created  (только если assetType relies on network, напр. категория "network equipment")
payload: { assetId, assetType, organization, sourceRef: { app: 'it-assets', id } }

net-monitor получает черновик устройства для мониторинга — MAC/начальный IP, если известен на этом этапе, ещё не обязателен, discovery донаберёт.

3. net-monitor → it-assets: обратная синхронизация "живых" данных

PATCH /api/integrations/v1/assets/{id}/network-status
{ currentIp, lastSeenAt, status: 'online'|'offline'|'unreachable' }

Это периодический вызов (не событие "по факту изменения" — IP-мониторинг опрашивает по расписанию через core/scheduler, §4.5g/п.4), с API-ключом, у которого только scope на network-status, ничего больше в карточке актива net-monitor трогать не может.

sourceRef — простая cross-app трассируемость, без распределённых ID

Не строим единый генератор ID на 4 приложения (лишняя сложность и точка отказа) — вместо этого каждая запись, пришедшая через интеграцию, хранит происхождение:

{ "sourceRef": { "app": "procure-it", "id": "PO-1234" } }

Этого достаточно, чтобы из it-assets кликнуть "открыть закупку" (ссылка собирается из sourceRef), и чтобы при повторной обработке того же webhook (retry) распознать дубликат — идемпотентность по (app, id, eventType), а не по времени получения.

Admin-панель и CLI

app integrations keys {issue,list,revoke}
app integrations webhooks {list,retry,delivery-log}

Administration → Integrations: список настроенных пар приложений, активные API-ключи (со scope, без самого значения ключа — тот же принцип, что и Secrets в §4.5g/п.5), лог доставки webhook'ов с возможностью "Retry" вручную на конкретном проваленном событии.

Где в роадмапе

Раньше Phase 6 (когда портированы минимум 2 приложения) смысла не имеет — интеграцию не с чем тестировать до этого момента. Ставлю это отдельной фазой сразу после того, как it-assets и procure-it оба на core (после текущей Phase 6), до полного портирования net-monitor — так первую связку (procure-it→it-assets) можно обкатать раньше, чем добавлять третью сторону.

6.6 Паттерны, найденные в реальном коде, но ещё не в архитектуре

Прошёлся по всем 4 билдам грепом — вот что уже реализовано (в 2+ проектах независимо друг от друга, то есть реальная повторяющаяся потребность, а не гипотеза), но не попало в документ раньше.

1. Maintenance windows → обобщаем до core/maintenance

В net-monitor уже есть полноценный механизм: окна обслуживания, во время которых мониторинг продолжает работать, но алерты подавляются (isInMaintenance() проверяется прямо в scheduler перед отправкой алерта). Паттерн шире одного net-monitor: та же идея нужна и остальным приложениям — "идут плановые работы/restore из backup — не спамить email-алертами и не писать лишний шум в audit как аномалию". Переносим в core:

maintenance.declare({ name, startTs, endTs, scope: 'all'|['deviceIds'] })
maintenance.isActive(scope)

@das-forge/email.sendAlert() (§4.5e) и core/audit (аномальные события) автоматически проверяют maintenance.isActive() перед тем, как шуметь. CLI: app maintenance {declare,list,cancel}. Admin UI: баннер "Идут плановые работы" в шапке (§5), пока активно окно — не отдельный экран, а часть AppShell, потому что это должно быть видно на любой странице.

2. Единый источник версии + страница «О системе» → core/version + ui/about

В it-assets и net-monitor независимо изобретён один и тот же паттерн: VERSION — единственный source of truth (plain text, не package.json, чтобы не тащить валидный JSON ради одной строки), скрипт sync-version.js раскидывает её по package.json/README-бейджу/docker-compose.yml/ Service Worker cache name. В procure-it — свой changelog.js, парсящий CHANGELOG.md (формат Keep a Changelog) для страницы "О системе", с явным комментарием в коде: "здесь нет дублирующего списка изменений вручную — именно дублирование уже приводило к рассинхрону". Это ровно тот случай, для которого и нужна платформа. Переносим в core:

core/version
  ├── VERSION file convention (не package.json.version)
  ├── version.sync()     — CLI: app version sync — раскидывает по местам,
  │                         которые задаёт app.config.js (README, compose, sw.js, ...)
  └── changelog.parse(CHANGELOG.md, { limit })   — Keep a Changelog формат

@das-forge/ui получает готовую страницу About (ui/about): версия, список последних N релизов из changelog.parse(), ссылка на полный CHANGELOG.md — доступна без прав (после логина, но не требует ролей выше guest), и её же можно вывести без логина, если приложение решит (это осознанное решение приложения через ui.register, не решение платформы).

3. Глобальный поиск и печатные виды → в @das-forge/ui Module Contract

it-assets реализовал cross-tab глобальный поиск (global-search.js, debounce 280ms) с нуля, procure-it и it-assets — отдельные "печатные" виды (qr-print.js, печать карточки заявки через window.print()). Оба паттерна общеплатформенные, добавляем в @das-forge/ui (§5.4 UI Module Contract):

ui.register({
  ...,
  search: {
    provider: async (query) => [...],   // модуль возвращает свои результаты
    label: 'assets.search'
  }
})

Общий search-box в AppShell агрегирует результаты всех зарегистрированных провайдеров с одним debounce на уровне платформы (не по одному в каждом модуле, как сейчас). Печать — ui/print даёт единый print-friendly stylesheet + компонент <ds-print-view>, чтобы не писать window.print() и вёрстку "для печати" в каждом приложении заново (QR-карточка актива, печатная форма заявки — один и тот же механизм). Внутри search.provider модуль обычно использует db.createFtsIndex() (полнотекстовый поиск, выше) для нечёткого поиска по тексту, и/или db.queryByExample() (точный поиск по заполненным полям формы фильтра) — оба уже готовые примитивы core/database, провайдеру не нужно писать SQL-запрос с нуля.

4. @das-forge/exports — уточнение по опыту procure-it

Уже заявлен в §6 как опциональный пакет, но procure-it показал конкретный паттерн, который стоит закрепить как часть контракта, а не оставить на усмотрение каждого приложения: имя файла экспорта включает применённые фильтры и дату (Реестр_заявок [org, month, статус]_2026-09-30.xlsx). API пакета получает это как встроенную возможность:

exports.toExcel(rows, { filenameContext: { org, month, status }, columns })

— а не оставляем каждому приложению собирать имя файла руками через конкатенацию строк.

5. Пробел, а не паттерн: нет ни одной брендированной страницы ошибки

Ни в одном из 4 приложений нет отдельной human-readable страницы для 404/500 при прямой навигации в браузере (core/errors, §3, пока подразумевает только JSON error-mapping для API). Если пользователь руками вобьёт неправильный URL в адресную строку — сейчас, вероятно, голый Express-дефолт или пустой JSON. Добавляем в core/http: для запросов с Accept: text/html — рендерить ui-страницу ошибки (единую, брендированную через тот же defineAppUI({ brand }), что и остальной интерфейс), для остальных — как и раньше, JSON.

6.5a Внешние интеграции (Bitrix24, 1С) — опциональные адаптеры, не ядро

Это другое по природе, чем §6.5 (там — связь между нашими 4 приложениями). Здесь — связь с внешними системами, которые живут по своим API и своим правилам, значит отдельные опциональные адаптеры поверх той же @das-forge/integrations-инфраструктуры (scoped API keys, delivery log — переиспользуются), а не новая подсистема:

@das-forge/integrations
      ├── core (webhooks, scoped keys, delivery log — §6.5)
      └── adapters/
          ├── bitrix24.js    REST API Битрикс24: задачи/хелпдеск, алерты в чат/канал
          └── 1c.js          обмен номенклатурой/артикулами с 1С:Бухгалтерия

Bitrix24 — решено: входящий вебхук. 1С:Бухгалтерия — ⚠️ BLOCKED, способ обмена пока не настроен в компании. Названия/артикулы товаров не бьются между 1С и it-assets/procure-it — классическая проблема сопоставления справочников. Но протокол обмена (HTTP-сервисы 1С / OData / выгрузка файлами — зависит от версии и конфигурации 1С в конкретной компании) сейчас не определён вообще, не просто "не выбран из вариантов". Это явный блокер для детального проектирования adapters/1c.js — пока не настроен хоть какой-то способ выгрузки/обмена на стороне 1С, здесь можно зафиксировать только общую схему, не конкретный код:

core/scheduler → adapters/1c.js → fuzzy-match (артикул/название)
                                        → очередь на подтверждение человеком в UI
                                        → confirm → запись в it-assets/procure-it

Сопоставление всегда с подтверждением человеком, никогда не автоматическое слепое — цена ошибки (спутать два разных товара) слишком высокая. Как только появится рабочий способ обмена с 1С (сначала нужно решить это на уровне компании/1С-программиста, не DAS-Forge) — протокол подставляется в уже готовую схему выше, сам паттерн (периодический импорт → fuzzy-match → подтверждение) не изменится независимо от конкретного транспорта.

Оба адаптера — опциональны, не тянутся в core и не нужны net-monitor/ atlas, если там нет такой интеграции. Детальный контракт каждого адаптера проектируется отдельно, когда понятен конкретный API/протокол на стороне Bitrix24/1С в этой компании — сейчас фиксируем только место в архитектуре и общий паттерн (REST/webhook адаптер поверх @das-forge/integrations, сопоставление с подтверждением человеком для 1С).

7.5 Контракты v1 (Phase 1, зафиксировано)

Важное разделение инструментов, прежде чем смотреть код: Zod валидирует данные (конфиг, вход, сущности). Поведенческие интерфейсы (DatabaseAdapter, AuthProvider, SessionStore — наборы методов) — не данные, значит не Zod-схема, а лёгкий duck-typing assert + JSDoc. Смешивать эти два инструмента — ложное чувство защищённости (z.function() в Zod проверяет только "это функция", не сигнатуру и не поведение).

Ещё одно следствие того, что @das-forge/ui — vanilla JS в браузере: Zod изоморфен, одна и та же схема валидирует форму и на клиенте (перед отправкой), и на сервере (в Express-роуте) — без дублирования правил.

DatabaseAdapter / AuthProvider / SessionStore (поведение → НЕ Zod, duck-typing assert)

// core/database/contract.js
export function assertDatabaseAdapter(adapter) {
  for (const m of ['connect', 'migrate', 'transaction', 'close']) {
    if (typeof adapter[m] !== 'function') {
      throw new Error(`DatabaseAdapter: отсутствует метод ${m}()`);
    }
  }
}

// core/auth/contract.js
export function assertAuthProvider(provider) {
  for (const m of ['createSession', 'destroySession', 'hashPassword', 'verifyPassword']) {
    if (typeof provider[m] !== 'function') {
      throw new Error(`AuthProvider: отсутствует метод ${m}()`);
    }
  }
}

export function assertSessionStore(store) {
  for (const m of ['get', 'set', 'destroy', 'touch']) {
    if (typeof store[m] !== 'function') {
      throw new Error(`SessionStore: отсутствует метод ${m}()`);
    }
  }
}

Эти assert-функции вызываются один раз при старте приложения (в createApp(), §3) — если кто-то подключит кастомный DatabaseAdapter/AuthProvider (например, для теста с in-memory реализацией), ошибка контракта всплывёт сразу при старте, а не где-то в середине рантайма непонятным TypeError.

Это и есть выход из Phase 1 — с этими схемами и assert-функциями можно идти в Phase 2 писать core/config, core/database, core/auth без домысливания на ходу.

11d. core/privacy — export/erase данных субъекта (0.1.6)

§4.5k, техническая база под 152-ФЗ/GDPR (окончательное юридическое соответствие — вопрос комплаенса, не архитектуры).

  • exportUserData({db, findUserByIdFn, moduleRegistry, userId, auditLogFn, actor}) — собирает запись пользователя (core/auth) + dataSubject.export(userId) каждого модуля, зарегистрированного через core/modules. Один упавший модуль не прячет данные остальных — его результат заменяется на { error: <message> }, выполнение продолжается
  • eraseUserData({..., mode}) — по умолчанию mode: 'anonymize', НЕ 'delete': core/audit's audit_log append-only (нет update() вообще) и обязан сохранять целостность истории — анонимизация переписывает ТОЛЬКО запись пользователя (core/auth's anonymizeUser()), прошлые audit-записи с оригинальным username не трогаются задним числом. 'delete' (core/auth's deleteUser(), настоящий hard delete) — только явным флагом, вызывающая сторона (CLI, в будущем — admin-panel) отвечает за подтверждение ДО вызова. Каждый модуль вызывается через dataSubject.erase(userId, {mode}) до изменения записи пользователя — модуль может успеть прочитать ещё не тронутую запись, если это ему нужно. 11e. core/certs — self-signed сертификаты (0.1.7)

§4.5f. readCertInfo() — чистый node:crypto (X509Certificate, доступен с Node 15.6+), без зависимостей: subject/subjectAltName/ self-signed (через checkIssued(self) — корректная криптографическая проверка, не строковая эвристика "issuer === subject")/дни до истечения. generateSelfSignedCert() — через selfsigned (npm ^5.5.0, проверено на npmjs.com по стоячему правилу свежести зависимостей; v5 — async-only, переписан на нативный WebCrypto). writeCertFiles() — data/certs/{cert.pem,key.pem}, приватный ключ — права 0600, переустанавливаются и при перезаписи (--force). certChecks() — doctor-категория, закрывающая пробел, явно оставленный открытым в core/health §11b ("ждут несуществующих пока core/certs").

Найден и исправлен реальный баг при прогоне: purgeExpiredPendingAuthenticators() сравнивал ISO-строку (new Date().toISOString(), формат "2026-10-07T12:34:56.789Z") с SQL-вым datetime('now') (формат "2026-10-07 12:34:56" — пробел вместо T, без миллисекунд и Z). Отдельно проверено, что больше нигде в кодовой базе нет такого же смешения форматов (sessions.js сравнивает корректно — парсит expires_at через new Date() перед сравнением, а не сырой строкой в SQL).

Прогнано вживую целиком (zod-free stand-in для schema.js): полный цикл enrollment (неверный код не активирует, верный — активирует, TTL истекает и не активируется даже верным кодом, purge удаляет истёкшую запись), два одновременных TOTP-фактора у одного пользователя (каждый проверяется своим секретом), все три исхода §18 (запрет с одним активным фактором и mfaRequired, разрешение с двумя, разрешение без mfaRequired, not_found), миграция legacy-секрета (включая проверку, что смигрированный секрет реально проходит verifyTotpLogin, и идемпотентность повторного ensureAuthTables()), полный цикл recovery codes (формат, одноразовость, regenerate инвалидирует старый набор целиком), и все три новые CLI-команды через реальный createCli() на реальной БД.

11i. Второй настоящий npm test — найденные баги (0.1.10)

Второй реальный прогон тестов (Windows, теперь с argon2/selfsigned реально установленными, не только zod): 266 тестов, 255 прошли, 11 упали в 3 файлах (auth.test.js ×5, authenticators.test.js ×2, certs.test.js ×4). Три разных реальных причины:

  1. migrateLegacyTotpSecrets() (auth/schema.js) безусловно читала users.totp_secret, предполагая, что CREATE TABLE IF NOT EXISTS users (...) в этом же вызове всегда даёт полную схему — но IF NOT EXISTS ничего не делает, если users уже существует (ровно так и устроена sessions-fixture в auth.test.js: создаёт свою минимальную users (id, username) до первого вызова ensureAuthTables()). Запрос падал "no such column: totp_secret". Исправлено: проверка PRAGMA table_info(users) перед миграцией, без легаси-колонки — миграции нечего делать, тихий выход
  2. Реальный security-баг в recovery-codes.js's verifyAndConsumeRecoveryCode(): if (await verifyPassword(...)) проверял истинность ОБЪЕКТА { valid, scheme, needsRehash } (verifyPassword() никогда не резолвится в boolean), который всегда truthy — первая непогашенная recovery-запись "совпадала" независимо от кода, так что неверный код принимался, а заодно гасилась чужая валидная запись. Исправлено на проверку result.valid
  3. generateSelfSignedCert() игнорировала days — selfsigned v5 не читает опцию days вообще (сверено с актуальным исходником на GitHub), только notBeforeDate/notAfterDate (объекты Date); без них — молчаливый дефолт 365 дней. Из-за этого daysRemaining всегда выходил ~365, валя и readCertInfo-тест, и certChecks's warn/ok тест. Исправлено: days → notAfterDate перед вызовом
  4. Не баг кода — 2 из 4 certs.test.js падений (mode & 0o777 === 0o600) оказались Windows/NTFS-ограничением: там нет POSIX permission bits, chmod() лишь переключает read-only атрибут, Stats.mode синтезирует 0o666/0o444. writeCertFiles() как писала 0o600, так и пишет — верно для POSIX. Точная mode-проверка вынесена в it.skip на win32, не ослаблена повсеместно

Как и в 0.1.9: все три кодовых бага были в точности там, где no-network песочница не может поймать настоящее поведение реальных библиотек (node:sqlite's взаимодействие с предсуществующей таблицей, argon2's реальный тип результата, selfsigned's v5 breaking change в API валидности). Два из трёх (totp_secret-guard, recovery-code логика) живо провалидированы вручную против настоящего node:sqlite в этой сессии; selfsigned's API сверен напрямую с актуальным исходником на GitHub, а не по памяти.

11q. Первый настоящий прогон examples/workshop/test/routes.test.js — найден и исправлен баг харнесса (0.1.21)

Пользователь впервые реально прогнал npm test на Windows с полным набором зависимостей (argon2 включительно). packages/core — 277/279 (2 ожидаемых skip), зелено. routes.test.js — 27 из 37 упали, и ВСЕ 27 — 401 там, где тест ожидал другой код (включая косвенные провалы в TOTP-хелпере — TypeError: ... toUpperCase в base32Decode, потому что /totp/enroll/start тоже вернул 401, а хелпер читал .secret из тела 401-ответа).

Диагноз: баг не в routes.js, а в самом тестовом харнессе (createFakeApp()). В реальном приложении req.user выставляется ровно в одном месте — http.sessionMiddleware({authProvider}), смонтированном ГЛОБАЛЬНО в server.js, перед любым роутом. Фейковый app в тесте эмулировал только цепочку handler'ов КОНКРЕТНОГО роута (то, что передано как аргументы app.get(path, requireAuth(), handler)), но никогда не прогонял то, что в реальности монтируется один раз глобально через app.use() — так что req.user оставался undefined для каждого запроса, и requireAuth() закономерно всегда возвращал 401, независимо от того, был ли в куках реально валидный session-cookie. Этот харнесс существует с 0.1.12 (Stage B) — баг дожил до первого реального запуска файла, не был пойман раньше только потому, что раньше файл не выполнялся вообще (барреля-импорт блокировал это в песочнице все эти версии).

Исправление:

  • createFakeApp() получил настоящий app.use() — внутренний dispatch() теперь прогоняет зарегистрированные через него middlewares ПЕРЕД цепочкой конкретного роута, в том же порядке монтирования, что у Express/server.js
  • makeFakeAuthProvider() получил реальный verifySession: (id) => auth.verifySession(db, id) — чистая node:sqlite-логика, argon2 не нужен и стенд-ин не требуется (в отличие от hash/verify пароля, которые остаются SHA-256 стенд-ином по той же причине, что и раньше)

11r. Второй настоящий прогон routes.test.js — гонка в dispatch() (0.1.22)

После 0.1.21 пользователь прогнал тесты второй раз: routes.test.js с 27 провалов до 2. Оба разобраны, ни один не в routes.js.

Баг №1 — гонка в тестовом харнессе: recovery codes тест падал с res.body === undefined, хотя handler точно отработал. Корень: реальные middleware ядра вызывают next() обычным statement'ом (Express-стиль), никогда не return next(). Прежний dispatch() ждал завершения через await возвращаемого значения каждого handler'а — для синхронного middleware это undefined сразу же после того, как он СИНХРОННО вызвал next() и вернулся, не дожидаясь того, что next() в это время успел запустить асинхронно дальше по цепочке. Две независимые "цепочки" получались: awaited-цепочка (быстро резолвится в undefined) и реальная работа (резолвится позже). Пока терминальный handler был синхронным или async-без-реального-ожидания — обе успевали закончиться в один микротаск-тик, гонка не проявлялась. auth.generateRecoveryCodes() делает 8 РЕАЛЬНЫХ argon2-хэшей — настоящие обращения к пулу потоков libuv — и awaited-цепочка стабильно финишировала раньше настоящей работы.

Исправление: dispatch() больше не доверяет промис-цепочке next() как сигналу завершения — res.json()/res.send() сами резолвят отдельный промис finished (так же, как Express следит за объектом ответа, а не за промисами из middleware), и dispatch() ждёт именно его. Ошибка в цепочке по-прежнему долетает — перехватывается на ближайшем уровне next() и реджектит тот же finished.

Баг №2 — баг в самом тесте: a write on another resource (asset create) падал на expect(entry).toBeTruthy(). Причина: core/audit's entity_id — колонка TEXT (log.js хранит её как String(entityId) намеренно, entity id может быть UUID, не только числом), mapper.js всегда возвращает entityId строкой. Тест сравнивал её строгим === с числовым id ассета — никогда не совпадёт. Поведение core/audit корректно; поправлен тест (String(created.res.body.id)).

Честно про проверку: обе гонки прогнаны напрямую вживую — отдельный скрипт воспроизвёл СТАРУЮ версию dispatch() (синхронные middleware перед медленным async-терминальным handler'ом с реальной setTimeout-задержкой) и показал тот же res.body === undefined; та же сцена против НОВОЙ версии — тело корректно заполнено, ошибка из handler'а по-прежнему долетает. Все 4 сценария sessionMiddleware/ requireAuth/requirePermission из 0.1.21 перепроверены против новой механики dispatch() — по-прежнему верны, включая медленный async-терминальный handler за requireAuth(). 17.1 Пересмотр (0.1.23) — финальное решение перед Stage F

В песочнице по-прежнему нет сети (см. §12–§16), поэтому фактический текущий номер версии drizzle-orm на npmjs.com здесь надёжно не проверить: веб-поиск в этой сессии дал противоречивые данные (один источник утверждает "стабильный 1.0 вышел в середине 2025", другой — что последняя статически закэшированная версия страницы релизов Drizzle показывает только 1.0.0-beta.2). Раздувать решение по непроверенному номеру версии — тот же риск, что уже один раз привёл к находке с vitest/node:sqlite (см. §13–§15): сначала проверить руками, потом доверять.

Решение: не добавлять drizzle-orm в зависимости @das-forge/core сейчас, вне зависимости от того, вышел ли уже стабильный 1.0. Причина важнее версии пакета: DatabaseAdapter (см. packages/core/src/ database/adapter.js) — это duck-typing контракт на 8 методов (run/get/all/exec/transaction/createFtsIndex/ queryByExample/close), сознательно не завязанный на SQLite API, и он уже сегодня, без единой строчки изменений, допускает Drizzle-backed Postgres-адаптер — реализовать его можно будет позже, в отдельном опциональном пакете (@das-forge/db-postgres или аналогично, по аналогии с @das-forge/email, §4.5e), не трогая @das-forge/core.
