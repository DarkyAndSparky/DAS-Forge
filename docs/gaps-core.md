# Упущения при разработке ядра (на 0.1.261)

Метод: статический просмотр кода и конфигурации по правилам из `engineering-rules.md` (grep и чтение выбранных файлов). Тесты и браузер в этой проверке **не запускались**; всё ниже получено чтением кода и помечено **PARTIALLY VERIFIED**. Ничего не исправлено, это только список.

## Что уже в порядке (подтверждено чтением)
- Таймауты: SMTP (connection/socket), LDAP, SFTP-бэкап, syslog-приёмник, проверка версий пакетов.
- TLS по умолчанию проверяется (`rejectUnauthorized: true`), отключение даёт предупреждение в health.
- Очередь писем захватывает строку атомарно (`UPDATE … WHERE status=… AND locked_at=…`), есть повторы с `retryBaseMs/retryMaxMs`.
- Редакция чувствительных ключей в журнале аудита и логах; нет `eval`/`new Function`/`child_process`.
- CI: тесты, e2e, `npm audit`, подписи пакетов, lockfile-lint, CodeQL, gitleaks, Trivy; CODEOWNERS и dependabot есть.

## G-04: разбор мест «прочитать, потом записать» (0.1.268)

Автоматический поиск нашёл 25 функций, где есть чтение и запись без транзакции. Что с ними:

**Исправлено (транзакция с блокировкой записи):** `setUserRole`, `changeUserRole`, `setUserDisabled`, `removeUser`, `requirePasswordChangeForAll`, `removeAuthenticator`, `registration.add`, `bans.ban`, `bans.lift`; в `pseudonymize` вставка стала `ON CONFLICT DO NOTHING`.

**Уже безопасно (сама запись проверяет условие):** `consumePasswordResetToken`, `verifyAndConsumeRecoveryCode`, `verifyTotpLogin`, `registration.consume`, `enqueue`/`processDue` почтовой очереди, `recognizeDevice` (`INSERT OR IGNORE`), `createDbLastRunStore` (upsert).

**Разобрано во втором проходе (0.1.269):** `privacy/incidents.update` читал запись и писал её целиком, теперь в транзакции. Безопасны и оставлены: `directory.link` (`INSERT OR REPLACE`), `verifyTotpEnrollment` (повторная активация ничего не портит), `passwordExpired` (однократная запись, если пусто), `session-store` (каждая операция одиночная или идемпотентная), `notifications` (вставка и подрезка независимы, частичная запись безвредна), `alerts` (память процесса для паузы между повторами, повтор по ключу из двух процессов допустим по замыслу), `sessionRows` (только чтение, поиск дал ложное срабатывание). Миграции `migrateLegacyTotpSecrets`/`sealExistingTotpSecrets` идут при старте до приёма запросов, не разбирал глубже.

Оговорка: SQLite в одном процессе выполняет запросы последовательно, так что гонка возможна только между процессами (сервер и CLI) или через `await` между чтением и записью.

## G-05: двойной клик и ключи идемпотентности (0.1.269)

Решение: серверный механизм ключей идемпотентности не строю. Там, где двойное действие настоящее, оно уже закрыто ограничением в базе (логин уникален, адрес в заявке на регистрацию один живой токен, запуск резервной копии под межпроцессной блокировкой), а общий «склад результатов» без потребителя был бы фасадом. Вместо этого одна защита на клиенте: форма с методом POST отправляется один раз (повтор в течение 8 секунд гасится). Это закрывает неприятный случай «второй клик показал ошибку, хотя первый всё сделал». Если появится внешний вызывающий (API, вебхук) с повторами, ключ делается для него отдельно.
