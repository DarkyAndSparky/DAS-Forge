# 0012. Дескриптор сущности: один источник истины для данных, API, форм и прав

Статус: **решения владельца получены 2026-11-20** (1, 2, 4 приняты; по пункту 3 принято «да», детали ждут ответов); код не написан
Дата: 2026-11-20

## Контекст
Новое приложение сегодня собирается из сотен строк вручную: таблица, проверка входных данных, маршруты, страницы, права, аудит, экспорт описываются в разных местах и расходятся. Цель платформы — собрать приложение из описаний сущностей и небольшого числа своих маршрутов. Ядро по-прежнему даёт механизм, смысл остаётся за приложением (ADR-0001), работает на SQLite и PostgreSQL (ADR-0010), страницы не используют `innerHTML`.

## Решение
Сущность описывается **чистым JS-объектом без побочных эффектов** (`defineEntity`, `field.*`), который не зависит от БД и Express и поэтому может читаться генератором, тестами и клиентским кодом.

1. **Состав дескриптора:** `name` (латиница, camelCase; ключ в API и аудите), `table`, `label` (ru/en, единственное и множественное), `fields`, `permissions` (только через существующие `requirePermission`; прав «для всех» нет), `list` (колонки, сортировка, размер страницы), `features` (`audit`, `softDelete`, `optimisticLock`, `history`, `attachments`), `hooks`, составные `unique`/`index`.
2. **Типы полей (минимум):** `text`, `longText`, `int`, `decimal`, `money` (целые минорные единицы), `bool`, `date`, `datetime` (UTC), `enum`, `ref`, `json`, `file`. Каждый тип задаёт: колонку SQLite и PostgreSQL, схему Zod 4, ввод, формат в списке, формат экспорта, сортировку и фильтр. Приложение регистрирует свой тип (`registerFieldType`) с тем же набором свойств.
3. **Проверка при старте:** понятная ошибка с путём к полю, уникальность имён сущностей и таблиц.
4. **Хуки:** `before/after` для `create`, `update`, `delete`, асинхронные; исключение откатывает транзакцию. Ядро даёт только точки, смысл приложения.
5. **Новый код только асинхронный** (`asyncDb`); синхронный слой не расширяется (проверяет храповик 0.1.358).

## Границы (что дескриптор НЕ делает)
Это защита от превращения дескриптора в ORM.
- Нет связей «один ко многим» с вложенной загрузкой, нет наследования, нет собственного языка запросов. Сложный запрос это обычный SQL приложения.
- Нет вычисляемых колонок в БД: вычисляемое поле только для чтения, считается в хуке.
- Нет автоматического удаления и смены типа колонок: безопасные изменения (новая таблица, nullable-колонка, индекс) выводятся сами, остальное руками (B3).
- Любую операцию CRUD приложение может заменить своим обработчиком; добавить свою операцию (`actions`).
- Мультиарендность закладывается с первого дня (раздел ниже).

## Что из этого следует (последующие ADR/пакеты)

## Проверка ввода в двух местах (решение владельца, 2026-11-21)

Ввод сущности проверяется дважды, намеренно: (1) «ворота» на Zod, построенные из того же дескриптора, работают первыми на сыром вводе — строгая схема отсекает неизвестные поля, неверные типы, огромные строки и числа до хуков, блокировок и базы; (2) полная проверка `entity.validate` (правила, значения по умолчанию, преобразования). Ввод должен пройти обе. Причина: защита от перегрузки и специально составленных серий запросов. Ворота никогда не строже дескриптора для допустимого значения (тест на 2000 случайных входов). Убирать любой из слоёв нельзя; в коде это помечено комментарием `VALIDATION IS IN TWO PLACES ON PURPOSE`.

## Мультиарендность (решение в принципе, детали ждут ответов)
Модель: **одна база, общие таблицы, колонка `tenant_id`** (не отдельная база и не отдельная схема на организацию).
1. Каждая таблица сущности получает `tenant_id` (внешний ключ на `tenants`), если сущность не объявлена глобальной (`tenant: 'global'`, например справочники ядра). Значение по умолчанию «без арендатора» запрещено.
2. **Фильтр по арендатору обязателен на уровне слоя доступа сущностей**: каждый запрос чтения, обновления и удаления добавляет `tenant_id = ?` сам; обработчик приложения не может его выключить, а запись без арендатора отклоняется. Тест «нельзя прочитать чужую запись» для каждой операции каждой сущности.
3. **PostgreSQL дополнительно:** row-level security по `current_setting('das.tenant_id')`, чтобы ошибка в коде не открыла чужие данные. SQLite: только фильтр слоя доступа (RLS там нет), это документируется как более слабая гарантия.
4. **Всё, что хранит данные организации, помечается арендатором:** аудит (`tenant_id` в записи, просмотр журнала только своей организации), вложения и квоты, настройки, пользователи и роли (права действуют внутри арендатора), задачи и вебхуки, ключи API.
5. **Определение арендатора запроса:** из сессии пользователя (пользователь принадлежит арендатору), не из заголовка или параметра, которые подставит клиент.
6. **Роль «оператор платформы»** вне арендаторов: создаёт организации, видит сводки, но чтение данных арендатора только через явное, записанное в аудит действие.
7. Раздельные ключи шифрования и квоты на арендатора: вторым этапом.

## Ответы владельца по мультиарендности (2026-11-20) и принятая модель
- **Несколько организаций на пользователя: да.** Пример: группа компаний, у каждой свой бухгалтер, а системный администратор обслуживает всех.
- **Организация определяется отдельной группой.** Принятое толкование (подтвердить): есть **группа доступа**, она связывает пользователей с набором организаций и ролью внутри них. Эффективный доступ пользователя это объединение его групп. У пользователя есть **активная организация** (или «все мои») в сессии, выбираемая переключателем; фильтр слоя доступа берёт множество разрешённых организаций из групп, а не из заголовка или параметра клиента.
- **Оператор платформы это обычный администратор** (роль `admin`, право `admin.access`): создаёт организации и группы и видит все организации. Отдельной роли не вводим. Остальные роли действуют только внутри организаций своих групп. Действия администратора над данными организаций пишутся в аудит, как и любые другие.
- Следствие для IT Assets: нынешнее `users.org_id` (одна организация, пусто = без ограничения) заменяется членством в группах; см. `docs/internal/it-assets-port-analysis.md`.

## Пробел дескриптора, найденный в IT Assets
Поля, набор которых зависит от значения другого поля (тип устройства), и схема которых правится администратором в работающем приложении. Требование к B1: **варианты по значению поля** (`variants`), дополнительные поля вариантов хранятся в JSON-колонке, схема варианта может задаваться данными (с проверкой Zod при записи). Также нужны типы `secret` (шифрование на диске), `ip`, `mac` и ссылки на записи с текстовыми идентификаторами.

## Последствия и риски
Дескриптор может раздуться до ORM: держим только перечисленное, остальное через хуки и замену обработчика. Расхождение SQLite и PostgreSQL: таблица типов в тестах прогоняется на обоих драйверах. Генерируемые страницы хуже ручных: компоненты B4 и ручная замена любого обработчика.

## Выкатка и откат
Новый экспорт, существующие приложения не затрагиваются; откат: не использовать.
