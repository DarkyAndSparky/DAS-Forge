# 0010. Адаптация под PostgreSQL

Статус: принято (вариант 1, поэтапно); дата решения 2026-11-14
Дата: 2026-11-13

## Контекст
Владелец проекта просит добавить в работу адаптацию ядра под PostgreSQL (для приложений, которым станет мало одного файла SQLite).
В дорожной карте (§17.1, заморожена) записано, что контракт `DatabaseAdapter` уже достаточен для Postgres-адаптера «без единой строчки изменений». Проверка по коду это не подтверждает.

**Что нашлось:**
- Контракт синхронный: `db.get/all/run/exec/transaction` возвращают значения сразу (`node:sqlite`). Драйвер PostgreSQL (`pg`) только асинхронный.
- В `packages/core/src` 367 вызовов `db.get/all/run/exec` в 55 файлах (больше всего `auth` 14, `audit` 7, `admin` 6, `scheduler`, `health` по 4, `accounts`, `cli`, `database` по 3). Все они написаны как синхронные.
- `atomic(db, fn)` требует синхронный `fn` и берёт блокировку записи (`BEGIN IMMEDIATE`); в Postgres это `BEGIN` плюс `SELECT … FOR UPDATE` или advisory lock.
- Диалект SQLite в самом SQL: `AUTOINCREMENT` (12), `PRAGMA` (35), `datetime()/strftime()` (24), `lastInsertRowid` (9), `INSERT OR …` (2), FTS5 и виртуальные таблицы (3), `COLLATE NOCASE`/`GLOB` (1), плейсхолдеры `?` (в Postgres `$1`).
- Миграции и резервные копии привязаны к файлу SQLite (`snapshotTo`, `VACUUM INTO`): для Postgres это `pg_dump`.

Вывод: контракт «достаточен» только на уровне названий методов; по сути Postgres потребует сделать слой доступа к данным асинхронным.

## Варианты
1. **Асинхронный контракт во всём ядре** (`await db.get(…)`, SQLite-адаптер тоже отдаёт промисы). Один контракт, два драйвера. Цена: переписать 367 вызовов и все функции, которые их содержат, сделав их асинхронными (затронет публичный API: `auth.createUser`, `bans.ban`, `audit.log`…), тесты и три приложения-примера. Работа на много версий, большой риск регрессий; нужен `await` везде, где сейчас «просто работает».
2. **Два слоя: синхронное ядро и отдельный асинхронный доступ для Postgres.** Нет: два набора кода одной логики расходятся.
3. **Оставить SQLite для ядра, Postgres только для данных приложения** (приложение само ходит в Postgres через `pg`, ядро хранит учётки, аудит и настройки в SQLite). Ядро не трогаем. Цена: два хранилища, нет общей транзакции, шкала упирается в один процесс и один файл.
4. **Синхронный драйвер Postgres через воркер** (`Atomics.wait` + `worker_threads`, как делают некоторые обёртки). Контракт сохраняется, но блокирует цикл событий на каждый запрос и ломает масштабирование ради которого Postgres нужен. Не рекомендуется.

## Подробный порядок работ (вариант 1)
1. Асинхронный контракт `DatabaseAdapter` + тест соответствия, один набор тестов на оба драйвера.
2. Слой диалекта: плейсхолдеры, автоинкремент (`GENERATED … AS IDENTITY`), время (`now()`), `RETURNING id` вместо `lastInsertRowid`, `ON CONFLICT` (уже совместим), регистр (`citext` или `lower()`).
3. Полнотекстовый поиск: `tsvector` + GIN (аналог FTS5), русская конфигурация.
4. Транзакции: `BEGIN` + `FOR UPDATE`/advisory lock вместо `BEGIN IMMEDIATE`; пул соединений.
5. Миграции и резервные копии: `pg_dump`/`pg_restore`, проверка версии схемы, блокировка миграции (advisory lock).
6. Модули по очереди: `database`, `auth`, `accounts`, `audit`, `security`, `admin`, `scheduler`, `health`, остальные; после каждого — прогон тестов владельцем.
7. Отдельный пакет `@das-forge/db-postgres` (зависимость `pg` не входит в ядро), подключается опцией; без него ядро не меняется.

## Безопасность и эксплуатация
Подключение по TLS (`sslmode=verify-full`), пароль только из секрета, не из конфигурации; отдельная роль с минимальными правами; таймауты запросов и пул с лимитом; журнал аудита (цепочка хэшей) требует одной транзакции с записью события, как сейчас.

## Выкатка и откат
Опция в конфигурации (`database.driver: sqlite | postgres`), по умолчанию `sqlite`. Перенос данных скриптом SQLite → Postgres с проверкой количества строк и цепочки аудита. Откат: вернуть `sqlite` и файл (до переноса сохраняется копия).

## Переходный период
Пока часть модулей синхронная, старый код (`db.run`) не ждёт открытую асинхронную транзакцию. Поэтому транзакцию держим короткой и без посторонних `await` кроме обращений к базе. После шага 5 это ограничение исчезает.

## Не проверено
Версия драйвера `pg` и совместимость с Node 26 не проверялись (нужна проверка на npmjs.com при начале работ). Оценка объёма взята из подсчёта вызовов, а не из пробной реализации.
